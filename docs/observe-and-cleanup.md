# Observe and cleanup

**Status:** the core in `src/observe/` is wired into the apply driver (`src/apply/observe.ts`, `cleanup-proposal.ts`, `leftovers.ts`, `run-records.ts`, `runCleanup` in `driver.ts`), into `./alz apply` (`observe`, `propose-cleanup`, `approve` of a proposal, `cleanup`, `verify-cleanup`, `report`) and into the console's step 7, **Check and clean up**, for the AWS Terraform row of the journey matrix (`config/acceptance/journeys.json`). The Azure Terraform and AWS CDK rows refuse with `CLEANUP_NOT_SUPPORTED` until their own slices. Every check is a read as the DISCOVERY identity. The one mutation, the targeted destroy of an approved proposal, runs under the pilot contract and its gates (`docs/act-pilot-plan.md`, "Cleanup of pilot-created resources"; commands in `docs/act-pilot-apply.md`, "Cleanup"). ACT stays DISABLED: the shipped pin is empty, and agents never initiate an observe, a proposal, an approval or a cleanup.

Every result in this repository is **synthetic**: the tests run a fake `terraform` and a fake `aws` program. In a lifecycle report each stage carries its own evidence mode: the execute step is `LIVE` only when the owner's `record-live` attestation covers that exact apply evidence, and every other stage is `SYNTHETIC` until an attestation form exists for it, so a report is `MIXED` at best today and `LIVE` never by declaration.

## What it answers

| Step | Question | Module |
| --- | --- | --- |
| Observe | After an apply, does every resource the plan left in place exist in AWS, under the identifier the engine recorded, and is nothing else carrying this run's tag? | `blueprint.ts`, `verify.ts` |
| Cleanup | Afterwards, is every resource either gone, or kept by a named owner for a stated reason? | `disposition.ts` |

## Blueprint

`blueprintFromTerraformState` reads `terraform show -json` of the state after the apply and the sealed plan's redacted changes.

- **What it records:** each managed resource's address, type, ARN and the provider's `id`. Both identifiers are kept because Cloud Control names some types by one and some by the other.
- **What it never copies:**
  - any other attribute value. Tests check this with canary values;
  - the `id` of types whose id is a credential identifier, such as `aws_iam_access_key`;
  - the state text in a parse error.
- **Data sources and outputs:** skipped.
- **`missing`:** every address the plan says should exist afterward (created, updated, replaced or unchanged) that the state does not hold.
- **`origin`:** `NOT_IN_PLAN` marks a resource that is in the state but that the plan never mentioned.

### CloudFormation (the CDK engine)

`blueprintFromCloudFormationResources` reads `describe-stack-resources` of the stack after the execution (as DISCOVERY, once, `src/apply/engines/cdk.ts`) and the sealed change list.

- **Addresses are logical ids**, types are CloudFormation types (`AWS::S3::Bucket`), `id` is the physical id and `arn` is the physical id when it is an ARN (an SNS topic) or the ARN derived from it for the types the independent reader knows (UNVERIFIED (9) in `docs/act-pilot-apply.md`); other types keep `arn: null`.
- **Nothing else is copied:** no status reason, timestamp or drift information. A row that is not well formed is skipped, not guessed; a `DELETE_COMPLETE` row is not in the stack.
- **`missing`:** every logical id the change set created, updated, replaced, imported or left dynamic that the stack does not hold.
- **The unit** comes from the stack tags the change set carried (UNVERIFIED (8)); the blueprint record names it so the sweep can run.
- **A nested stack** (`AWS::CloudFormation::Stack`) that appears in the stack is `CONTAINS_OTHERS`: never proposed, and the engine refuses one at the seal. The same rule covers every stack container under the Terraform engine (below).
- **The stack itself** is the unit's container (`blueprint.container`, by the pinned stack's id in the pinned account and region): it carries the unit's tags, so the tag sweep lists its ARN, and the observation and the leftover check know it as the container, never as a stray or a leftover. It is never a proposal entry.

**The CDK cleanup** is one UPDATE change set from the removal template: the sealed template minus exactly the approved logical ids (`removalTemplateOf`, `src/apply/engines/cdk.ts`), written into the work copy under the one name `alz-cleanup-template.json`, created by CHANGESET with the stack's own tags passed back unchanged, its change list compared with the proposal (exactly a removal of those ids: `protectedDeletionIn` and the scope check, before any approval is consumed), and executed by APPLY and watched like an apply. The stack is never deleted, and there is no delete argument list on any surface. Refused by name before any change set exists: an approved id that is not in the template; an identity or access object (`CLEANUP_PROTECTED_IDENTITY` in the engine, the identity rule of `src/apply/cleanup-proposal.ts`, reported as `PROPOSAL_SCOPE_MISMATCH`); a resource whose `DeletionPolicy` keeps it, is not a plain word the engine can judge (an intrinsic), or is `Snapshot` by CloudFormation's default for the type when none is written (an RDS cluster; an RDS instance whose `DBClusterIdentifier` is not a non-empty string or a `Ref` to a logical id, so `null`, an empty string or `AWS::NoValue` counts as outside a cluster) (`CLEANUP_RETAIN_POLICY`: the removal would leave something behind, unapproved and untracked); a resource or output that stays and still refers to an approved one by `Ref`, `Fn::GetAtt`, `DependsOn` or `Fn::Sub` (`CLEANUP_DEPENDENT_REFERENCED`); and a removal that would leave the stack with no resource (`CLEANUP_WOULD_EMPTY_STACK`: CloudFormation does not hold an empty stack, UNVERIFIED (11); the stack's last resources go with the stack itself, and retiring it is the owner's separate decision). A stack a person has not protected after its first create, or one not in a stable state, is refused as an update would be. **Residual risk, stated plainly:** what the change set would do beyond the list is known only after CloudFormation has computed it, so the width check (`cleanupScopeProblem`) and the policy check on what CloudFormation would take along (`protectedDeletionIn`) run after CHANGESET created the removal change set. When they refuse, nothing is executed and no approval is consumed, but that change set is left in CloudFormation, unexecuted and `AVAILABLE`, for a person to clear; the refusal says so. So does every other refusal after CHANGESET created it (a change set, stack, template, tag or capability check that fails, reported as `TARGET_NOT_IN_CONTRACT` or `APPLY_FAILED`; a creation CloudFormation reports `FAILED`, which also stays listed): the engine marks a refusal thrown after the create call, and the driver appends the same sentence whatever the code. No surface may delete a change set, and the pilot's authority is not widened to do so. No IAM object is ever in a removal (every `AWS::IAM::*` is `PROTECTED_IDENTITY`), and no stack, nested stack, stack set, custom resource or macro is: the proposal keeps a nested stack, a stack set and a custom resource as `CONTAINS_OTHERS` (the blueprint records a `Custom::` row under its own type), the assembly check refuses each at the seal and again when the cleanup prepares, and the removal template refuses one by name whatever list reaches the engine.

## Independent verification

`observeBlueprint` is independent of the engine:

- It asks the AWS Cloud Control API (`cloudcontrol get-resource`) whether each resource exists under its primary identifier (`CLOUD_CONTROL_TYPES`). A CloudFormation-typed entry (the CDK engine) is read under its own type name with the physical id as the identifier, for the same set of types (`cloudControlMappingOf`); a CloudFormation type outside that set is `NOT_CHECKABLE`, never assumed. A type whose only Cloud Control read returns application data or secret contents (`DATA_BEARING_TYPES`: a Lambda function, whose read handler returns its environment variables and needs `kms:Decrypt`; an SSM parameter; a Secrets Manager secret) is never read: it is `NOT_CHECKABLE` with `DATA_BEARING_READ_EXCLUDED`, and no call is sent (owner decision 2026-10-27, issue #39 comment 6440801434, item 2). Such a resource is not a setting of another resource. A cleanup proposal lists a run-created one as `UNVERIFIABLE`, with its own risk sentence, and it still needs the contract's human approvals. After the cleanup the leftover check reports it `UNKNOWN` (basis `NOT_INDEPENDENTLY_CHECKABLE`, reason `DATA_BEARING_READ_EXCLUDED`). It never borrows another resource's absence, so the record stays `INCOMPLETE`. The product has no step that confirms its deletion.
- It lists resources tagged with the run's deletion unit (`resourcegroupstaggingapi get-resources`, read with `src/teardown/readers.ts`) to find resources the blueprint does not name.

The caller runs the AWS CLI as the read-only DISCOVERY identity through the bounded runner. Only existence is recorded. A failure is recorded as an error class (`ACCESS_DENIED`, `THROTTLED`, `CREDENTIALS`, `TYPE_NOT_SUPPORTED`, `CLI_ERROR`), never as the cloud's message.

| Verdict | Meaning |
| --- | --- |
| `VERIFIED` | Every resource is present. Nothing planned is missing, nothing unexpected carries the tag, and the tag listing was complete. |
| `PARTIAL` | As `VERIFIED`, except that some types cannot be checked on their own, or the run carries no unit tag. Unchecked types are named, never assumed present. An example is a bucket setting such as `aws_s3_bucket_versioning`, which is not a separate cloud resource. |
| `INCONCLUSIVE` | A check could not decide (access, throttling, credentials, or a paginated listing), or the blueprint names no resources so nothing was checked. Nothing is known to be wrong. |
| `FAILED` | A resource is absent, a planned resource is missing from the state, or an unexpected resource carries the run's tag. |

**The unit tag:** a pilot run stamps its deletion unit on everything it creates (`src/apply/unit.ts`; the operator's provider configuration declares the tags and `seal` verifies them in the plan, docs/act-pilot-plan.md item 6). The blueprint record carries the unit, so the observation lists resources carrying it and reports `inventory: COMPLETE` when the listing covered every page; a tagged resource the state does not name is `unexpected` and the verdict `FAILED`. A run whose engine seals no unit (CDK) reports `inventory: NOT_AVAILABLE` and reaches `PARTIAL` at best.

## The Azure reader

For the Azure Terraform row the same checks read Azure Resource Manager (`src/observe/azure-rest.ts`), in process, as the DISCOVERY identity. No `az` CLI runs, so no credential ever reaches a process argument list, a child environment, a log or an evidence digest:

- The DISCOVERY identity's federated token (`ALZ_DISCOVERY_ARM_OIDC_TOKEN_FILE`) is exchanged once, in the body of one HTTPS POST to `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token` (client credentials with a client assertion), for an access token scoped to `management.azure.com`. Both tokens live in memory for one observation and are dropped with it; they never appear in a record, a message or an error. Failures are recorded as classes (`CREDENTIALS`, `ACCESS_DENIED`, `THROTTLED`, `HTTP_ERROR`, `HOST_REFUSED`, `UNEXPECTED_RESPONSE`, `READER_CLOSED`). A closed reader exchanges no token again and reads nothing.
- Requests are GETs to `https://management.azure.com` only: the provider's API versions once per resource type (stable versions only; a type offered only in preview is `TYPE_NOT_SUPPORTED`), one resource by its ARM id (`200` whose `id` is the one asked about → present; `404` → absent; anything else → unknown with a class), the subscription's resources and resource groups carrying the `alz-unit` tag, every page. Nothing lists what a resource group holds: a pilot cleanup never deletes a group, so its contents are not a deletion decision. The one gate every request passes binds the method to the host: a POST goes only to this tenant's token endpoint, a GET only to `management.azure.com`, both over `https:` with no port and no userinfo. A listing's `nextLink` is followed only when it continues exactly the listing that was asked for: an allowed ARM URL with the same path as written, before URL normalization (the same subscription and collection; a `..` or `.` segment, a percent escape, a backslash or a control character in the link is drift even when it would normalize to the same path) and the same query (every original parameter, the tag filter and the API version among them, with exactly the same values the same number of times, keys compared case-insensitively) plus paging parameters (`$skiptoken`, `$skip`, `$top`), each once. A link anywhere else (another host, plaintext, a port, the login host), to another subscription or collection, or one that drops, changes or repeats the filter or the API version or adds any other parameter, ends the listing as incomplete and is never followed, so the bearer never leaves over any other path and a page can never widen or narrow the inventory while the result reads complete. A page that is not an object with an array `value` of items each carrying a non-empty `id` fails the listing, and a page that names its continuation under any other key (`@odata.nextLink`) is incomplete: a malformed answer never reads as "nothing here" or as the last page. Only existence and identifiers are kept, and one property: for a resource found outside the contract's location, that location as ARM's programmatic name (`observedLocation`), so a location remediation can bind and recheck it.
- **Where each resource is** (owner decision of 2026-10-28): the reader is given the contract target's `location` and, for each resource it finds, compares the `location` its ARM answer names (normalized: `East US 2` is `eastus2`) in process, and records it only for a resource found elsewhere (`observedLocation`, the programmatic name, with the resource's creation identity `observedResourceGuid` when its answer carries `properties.resourceGuid`), for Terraform and Bicep alike. Another location makes the resource `DIFFERENT_FROM_DESIRED` (`LOCATION_NOT_IN_CONTRACT`) and the observation `FAILED`; a virtual network whose answer names none is `UNKNOWN` (`LOCATION_UNREADABLE`). The region is read from the resource's own answer only, never from its resource group. An Azure target that names no location is refused (`CONTRACT_INVALID`).
- An ARM id is sent exactly as written or not at all: an id with an empty, `.` or `..` segment, a backslash, a percent escape or whitespace is `NOT_AN_ARM_RESOURCE_ID` (URL parsing would rewrite it, and a `404` for the rewritten path would read as this resource's absence), and the request path is asserted equal to the id before it is sent. The proposal refuses such an id outright (`OWNERSHIP_AMBIGUOUS`): a state that holds one is reviewed by hand.
- ARM ids are case-insensitive, so the unit-tag sweep folds case for Azure only. AWS identifiers are compared exactly: an ARN that differs from a known one only in case names another resource (queue, topic and function names are case-sensitive) and stays a stray.
- **A resource group is never deleted by a pilot cleanup** (owner decision 6408600057, 6408642348). A group is recognized by the ARM id the state recorded (`/subscriptions/<id>/resourceGroups/<name>`), whatever Terraform type created it (`azurerm_resource_group`, `azapi_resource`, a module's own type), and by the `azurerm_resource_group` type even without an id. Whether this run created it and whatever it holds, the proposal keeps it with ownership `RETAINED_GROUP`, `retainedBy: PILOT_OWNER` and the reason that its deletion is a separate, reviewed action (environment retirement, which every record and report leaves outstanding). The containment-based group deletion of an earlier version (list the group's members, delete it when they are all this run's) is removed with no legacy path: the reader has no group listing, the observation record has no `groups` field (a record written with one is refused on read-back; observe again), and the cleanup lists nothing before the destroy. A subscription (by id or alias), a management group, or an entry of type `azurerm_subscription`, `azurerm_subscription_alias`, `azurerm_management_group` or `azurerm_management_group_subscription_association` is never proposed either (`CONTAINS_OTHERS`): nothing here can list what deleting it would take.
- **AWS: anything in the IAM or identity service is never deleted**, directly or as a dependent (`PROTECTED_IDENTITY`, owner policy #39, reviews 6411551942 B2 and 6412182848). The rule is one anchored prefix check (`isAwsIdentityType`), not a list, over the whole identity family in its four namespaces: Terraform `aws_iam_` (roles, policies, attachments of every kind including `aws_iam_policy_attachment` and the `*_exclusive` types, users, groups, instance profiles, identity providers, service-linked roles, access keys, login profiles, SSH keys, signing certificates, MFA devices, the account password policy and alias), `aws_ssoadmin_` (IAM Identity Center assignments, permission sets and their policies) and `aws_identitystore_` (workforce users, groups and memberships); the Cloud Control provider's `awscc_iam_`, `awscc_sso_` and `awscc_identitystore_`; CloudFormation `AWS::IAM::`, `AWS::SSO::` and `AWS::IdentityStore::` (case-exact); and no `Custom::` namespace of its own, because a custom resource is judged by what it carries (below). Credentials are kept with the identity they belong to, in both engines, and a credential's id is never copied into a record. Kept by the pilot owner; a run that created an application role still gets its other resources cleaned up. An identity's ARN (`arn:aws:iam::...`, any partition) recorded under any other type as its identifier is unclassifiable, and for the wrapper types that can carry anything (`terraform_data`, `null_resource`, `AWS::CloudFormation::CustomResource`, `Custom::*`; every stack container of the table below is scanned too, but the container rule keeps it first) so is one found in any attribute the state holds, as a whole value or an element of a list (`holdsIdentityArn`, judged in place by the blueprint, which copies no attribute): the proposal is refused for a person to review, and a destroy plan that touches the entry stops. The scan enters at most 32 nested objects or lists (`SCAN_DEPTH`, `src/observe/blueprint.ts`); width is unbounded. Attributes nested deeper cannot be scanned in full, so the entry is flagged the same way and refused rather than proposed (fail closed, review 6412896598 B2). A `null_resource` or `terraform_data` whose destroy-time provisioner deletes something by plain name cannot be seen from the state at all; whether such wrappers belong in the pilot is an owner decision.
- **AWS: anything that deploys a CloudFormation stack or a provisioned product is never deleted** (`CONTAINS_OTHERS`, kept by the pilot owner; reviews 6412896598 B1 and 6432262110 B1, owner decision 6431744115). Deleting such a resource deletes everything the stack holds, IAM roles and other identities among it, and none of that is in the engine's state: a `template_body` names types, not ARNs; a `template_url`, a Serverless Application Repository application or a product's template is not in the state at all; the outputs may be empty. So the rule is by type, one anchored prefix check per family over the one table in `src/observe/aws-containers.ts` (`isAwsContainerType`), which the test table iterates. The families, each as the Terraform `aws_` type, the Cloud Control provider's `awscc_` type and the CloudFormation type: a CloudFormation stack, stack set or stack instance (`aws_cloudformation_stack*`, `awscc_cloudformation_stack*`, `AWS::CloudFormation::Stack*`); a Service Catalog provisioned product (`aws_servicecatalog_provisioned_product`, `awscc_servicecatalog_cloud_formation_provisioned_product`, `AWS::ServiceCatalog::CloudFormationProvisionedProduct`); a Serverless Application Repository application (`aws_serverlessapplicationrepository_cloudformation_stack`, `awscc_serverlessapplicationrepository_*`, `AWS::Serverless::Application`, `AWS::ServerlessRepo::*`); a SageMaker project (`aws_sagemaker_project`, `awscc_sagemaker_project`, `AWS::SageMaker::Project`); a Proton environment or service (the whole `aws_proton_`, `awscc_proton_` and `AWS::Proton::` namespaces); an Elastic Beanstalk environment (`aws_elastic_beanstalk_environment`, `awscc_elasticbeanstalk_environment`, `AWS::ElasticBeanstalk::Environment`, a fail-safe); an SSM Quick Setup configuration (the whole `aws_ssmquicksetup_`, `awscc_ssmquicksetup_` and `AWS::SSMQuickSetup::` namespaces); a DataZone environment (`aws_datazone_environment`, `awscc_datazone_environment`, `AWS::DataZone::Environment`); Control Tower (the whole `aws_controltower_`, `awscc_controltower_` and `AWS::ControlTower::` namespaces; review 6433014148 B1). This table is defense in depth with a named reason, not a completeness proof: completeness comes from the leaf allowlist below. A container is kept whatever its identifier or attributes say, with its reason and `retainedBy`, directly or as a dependent of a destroy plan (`protectedDeletionIn` stops the plan before any approval is consumed, naming the family); a run that created one still gets its other resources cleaned up. Every container is also a wrapper for the ARN scan above.
- **AWS: only a reviewed leaf type is ever proposed** (delegated owner decision 6433391052, item 1; the design review after five review rounds showed that no deny list of "types that deploy a stack" can be proven complete). After the backend, container and identity rules and the ARN scan, a type is ordinary only when it is on the closed allowlist in `src/observe/aws-leaf-types.ts` (`AWS_LEAF_TYPES`), by exact, case-exact name: one table across the `aws_`, `awscc_` and CloudFormation namespaces, each entry with what it is, a one-line reason why it is a leaf (it deploys no stack, product, project, environment or nested deployment), and its basis (the pilot's own journeys; exactly the owner's decision 6431744115 item 3 on authorization-adjacent objects; or a common leaf). Every type of an entry marked data-bearing carries a material-risk note the approvers read, and a test keeps the two lists in step. An attachment or setting that modifies another resource (an S3 bucket's settings and policy, an SQS queue's policy, a Lambda permission, a KMS grant, an RDS role association, an Organizations policy attachment, and their Cloud Control and CloudFormation forms) names its parent in the table, and one rule applies: it is proposed only when the resource it modifies, read from its own identifier, is deleted by the same proposal; otherwise it is held (`TYPE_UNREVIEWED` with its own reason), because a planned create can overwrite what a kept resource already had (design review 6434540427, B3). A Lambda permission's identifier does not name its function, so it is always held. An entry may also admit only some objects of its types: an Organizations policy is a leaf only when it is a service control policy (owner decision 6440801434, item 3), read from the policy ARN the state recorded (`arn:aws:organizations::<account>:policy/o-<org>/service_control_policy/p-<id>`, `serviceControlPolicyProblem`). Any other kind (resource control, tag, backup, AI services opt-out, chat applications, declarative and future kinds), a missing or unreadable ARN, or a recorded id the ARN does not name is held as `TYPE_UNREVIEWED` with a reason that names it, by the proposal and by `protectedDeletionIn`; other kinds need their own authorization and tests. A CloudFormation policy's physical id is its id alone, so a CDK-created policy is always held. An attachment follows the parent rule, so it is deleted only with a run-created service control policy the same proposal deletes. Any other well-formed type the run created is `TYPE_UNREVIEWED`: excluded, listed with its type, `retainedBy: ENVIRONMENT_OWNER`, never deleted directly or as a dependent (`protectedDeletionIn` stops a destroy plan that would take it along, naming the type), while the run's allowlisted resources are still cleaned up. The leftover check records it `INTENTIONALLY_RETAINED` on the basis `UNREVIEWED_TYPE` and stays `INCOMPLETE` while one remains (a record that claims `COMPLETE` or `KNOWN_ADDRESSES_CONFIRMED` with one is refused), so a person deletes or keeps it by hand; a type joins the allowlist only by review, with its reason. A type field that is not a well-formed Terraform or CloudFormation type is unclassifiable and refuses the proposal. Not seeded, on purpose: the EKS access entries and Verified Permissions types and `terraform_data`/`null_resource` (open owner questions), Organizations delegated administrators, Lake Formation permissions and the Redshift cluster IAM role set (held for the owner; design review 6434540427). The whole-proposal `OWNERSHIP_AMBIGUOUS` refusals are unchanged.
- **Identity and authorization objects are never deleted**, directly or as a dependent (`PROTECTED_IDENTITY`). By Terraform type: every `azuread_*` object, every `azurerm_role_*` and `azurerm_pim_*` type (role assignments and definitions, PIM eligibility and assignment schedules, role management policies), every `azurerm_*_policy_assignment`, `azurerm_*_policy_exemption` and `azurerm_policy_*` type, `azurerm_management_lock`, user-assigned identities and federated credentials. By id, whatever type recorded it (`azapi_resource`, a module's type): any id with a `/providers/` pair under the **whole** `Microsoft.Authorization` namespace (role assignments and definitions, PIM schedules, policy assignments, definitions, set definitions and exemptions, locks) or `Microsoft.ManagedIdentity`, at any scope. Every `/providers/` pair of an id is judged (`armTypePairsOf`), not only the first or the last: a role assignment scoped to a workspace (`.../workspaces/law/providers/Microsoft.Authorization/roleAssignments/<guid>`), a PIM request at resource scope, and a tracked resource under an authorization scope are all caught. This retains more and deletes less than a role-only rule: a run-created lock is kept by the pilot owner and said so, never deleted; a run-created policy object is kept unless the exception below applies.
- **Run-created policies are the one exception** (owner decision "Unpin the ACT decision", item 2 (c), #39; `src/observe/run-created-policies.ts`). The identity rule above runs first and keeps every object; a reviewed policy type is then carved out of it only when the sealed plan created it (`CREATE`, not imported, in the plan) and every condition holds. **AWS**: a customer-managed policy (`aws_iam_policy`, `awscc_iam_managed_policy`; never an AWS-managed `arn:aws:iam::aws:policy/...`) goes when nothing this cleanup keeps still attaches it; an inline policy (`aws_iam_role_policy`, `aws_iam_user_policy`, `aws_iam_group_policy` and the `awscc_` forms) goes when every principal it is on is a principal this run created; an attachment (`aws_iam_role_policy_attachment` and the user and group forms) goes when its principal is one this run created and the policy it attaches is a run-created customer-managed policy this cleanup deletes too. So an attachment of a run-created policy to a pre-existing principal is held, and the policy with it. A link to one of the pilot's own roles (DISCOVERY, STATE, STATE_WRITE, APPLY, CHANGESET) is held whatever else holds. The principals themselves (roles, users, groups) stay protected. The blueprint reads the principal names and one policy ARN of these types from the state (`policyLink`, never a document); a link it cannot read exactly, and every CloudFormation form (a stack resource has no properties in the blueprint), is held. The exclusive attachment types are never carved out, and a run-created policy one of them attaches is held with it. The leftover check cannot read IAM policies independently (no Cloud Control mapping under DISCOVERY), so a deleted policy is reported `UNKNOWN` for a person to confirm. **Azure**: `azurerm_policy_definition` and `azurerm_policy_set_definition` at the target subscription's own scope, and `azurerm_subscription_policy_assignment`, `azurerm_resource_group_policy_assignment` and `azurerm_resource_policy_assignment` at that subscription, a resource group in it or a resource in it, judged by the parsed id. A management-group scope, a built-in definition, another subscription, an exemption, a lock, a role assignment, or an id that does not parse in full stays `PROTECTED_IDENTITY`. Every reviewed type names a material risk. Held entries keep the identity rule's class and reason, so a proposal never depends on which identity variables were set where it was made. On the destroy plan, `protectedDeletionIn` lets a carved-out entry through only when the verified proposal lists it and its blueprint entry still meets the carve-out.
- **Deployment history is never deleted** (`PROTECTED_DEPLOYMENT`, owner direction 6408777768): every `azurerm_*template_deployment` type and, whatever type recorded it, any id with a `/providers/` pair of `Microsoft.Resources/deployments` at any scope: a resource group's, a resource's (`.../sites/s/providers/Microsoft.Resources/deployments/d`), a subscription's or a management group's (`/providers/Microsoft.Management/managementGroups/mg/providers/Microsoft.Resources/deployments/d`). It is recorded retained with its reason; no deployment risk note exists any more, because none is ever proposed.
- **Indirect deletion is refused before anything is consumed.** After the engine's `plan -destroy` of exactly the approved addresses, `protectedDeletionIn` (`src/apply/cleanup-proposal.ts`) classifies every planned change by its blueprint entry (type and recorded id) or, for an address the state does not hold, by its type alone, with the same rules the proposal applies. A plan that would delete, update or otherwise touch a resource group, an identity or authorization object, deployment history, the state backend or a scope, whether the proposal named it or the engine added it as a dependent, refuses `PROPOSAL_SCOPE_MISMATCH` naming the policy and the class, with nothing destroyed and no approval consumed. The generic scope check (exactly the approved addresses, every one a delete) runs after it.
- Leftover bases name the API that answered: `ARM_ABSENT` / `ARM_PRESENT` for Azure, `CLOUD_CONTROL_ABSENT` / `CLOUD_CONTROL_PRESENT` for AWS.
- The reader resolves a resource's API version by its own type, the last `/providers/` pair of its id (an extension resource's type sits after its scope's), so a role assignment on a workspace is read under `Microsoft.Authorization`, not under the workspace's provider.
- **ARM ids are parsed by position** (`src/observe/arm-id.ts`, review 6410149770 B3), the way ARM reads them: `subscriptions/<guid>`, `resourceGroups/<name>`, then `providers/<Namespace>` followed by `<type>/<name>` pairs, repeated for each extension scope. A segment is a keyword only in a key slot: a resource group or a storage account named `providers` is an ordinary name, so `/subscriptions/<id>/resourceGroups/providers/providers/Microsoft.Authorization/roleAssignments/<guid>` is a role assignment and is kept. The reader and the cleanup classifier share the one parser. **Anything the parser cannot consume in full fails closed**: a trailing slash, an empty segment, a type with no name, a namespace without a dot, a bad subscription id, a blank id. Such an entry is never "not protected": the proposal refuses it (`OWNERSHIP_AMBIGUOUS`, a person reviews the state by hand), `protectedDeletionIn` stops a destroy plan that would touch it, and the reader records it `NOT_AN_ARM_RESOURCE_ID` (which never makes an entry eligible for deletion on its own: an ARM-shaped id must parse before it can be proposed). The same holds for an id that is not an ARM path at all: only the azurerm types that record a data-plane URL are judged by their type alone, and only when the URL is the family that type records (`DATA_PLANE_TYPES`: storage containers, blobs, queues, tables, shares and their contents on `https://<account>.blob|dfs|file|queue|table|web.core.windows.net/...`; key vault keys, secrets and certificates on `https://<vault>.vault.azure.net/...`; managed HSM keys on `https://<hsm>.managedhsm.azure.net/...`) and the path has no `providers` segment. Every other type with a non-ARM id, every `azapi_*` type among them, and an id under the `https://management.azure.com` host, one with a leading space, a bare GUID or any other URL, is refused the same way (reviews 6410591513 NB-A and 6411080437 B1). A managed HSM role assignment or role definition is `PROTECTED_IDENTITY` by type (`azurerm_key_vault_managed_hardware_security_module_role_assignment` and `_role_definition`) and by any id form (`https://<hsm>.managedhsm.azure.net///RoleAssignment/<guid>`, `.../keys/RoleAssignment/<guid>`, `.../providers/Microsoft.Authorization/roleAssignments/<guid>`, and the RoleDefinition forms), whatever type recorded it: kept by the pilot owner while the run's other resources are cleaned up.
- **Provider and feature registrations are kept, never proposed** (`CONTAINS_OTHERS`, NB-B): `/subscriptions/<id>/providers/<Namespace>`, `/subscriptions/<id>/providers/Microsoft.Features/providers/<Namespace>/features/<name>` and a provider-level scope such as `/providers/Microsoft.Marketplace` parse as a provider block with no type/name pair (`isArmRegistrationId`). Such a block is accepted only where a registration or a provider-level scope lives: as the first block at subscription scope (the `Microsoft.Features` form follows it with one more block) or at tenant scope; under a resource group or after a resource (`.../resourceGroups/rg/providers/Microsoft.Compute`, `.../workspaces/law/providers/Microsoft.Resources`) ARM has no such object and the id is unparseable, refused like any other. They are subscription-wide settings other deployments rely on, so the proposal still forms, the run's ordinary resources are cleaned up, and the registrations are recorded intentionally retained by the pilot owner. The reader does not ask about them (`NOT_AN_ARM_RESOURCE_ID`: they have no resource API version of their own). An authorization pair under such a scope (`/providers/Microsoft.Marketplace/providers/Microsoft.Authorization/...`) is still `PROTECTED_IDENTITY`.
- Checkable: a resource group, or a resource under a provider namespace at subscription or resource-group scope in the target subscription. Not checkable: an id outside the subscription (`OUTSIDE_TARGET_SUBSCRIPTION`), a data-plane URL such as a key vault secret (`NOT_AN_ARM_RESOURCE_ID`), or an entry with no id.
- Protected on Azure, whoever created it: the backend storage account named by any environment's `<storage-account>/<container>/<key>` in every form its id takes (the account name, an ARM id under `/storageAccounts/<account>`, or a data-plane URL `https://<account>.blob|dfs|file|queue|table|web.core.windows.net/...`, which the azurerm provider uses for containers and blobs), every `azurerm_storage_*` entry naming it, and the resource group that holds it when the state names the account's ARM id (`PROTECTED_BACKEND`); every identity and authorization object as above (`PROTECTED_IDENTITY`); deployment history (`PROTECTED_DEPLOYMENT`); every resource group (`RETAINED_GROUP`). Each kept entry names who keeps it: `retainedBy: PILOT_OWNER` for these protected classes and for scopes, `ENVIRONMENT_OWNER` for a pre-existing, replaced, imported or unplanned resource. The retention owner follows from the ownership class, so a proposal whose `retainedBy` says otherwise is malformed.
- Tests (`test/apply-cleanup-azure.test.ts`, `test/ui-channel.test.ts`) run a scripted Azure Resource Manager with canary token values and prove that the values appear in no recorded request URL, record, result or error, that only the token POST and GETs to the two hosts are sent and a link anywhere else is never followed, that a rewritable id is never requested, and that the observation, proposal, protections, cleanup and leftover check behave as on AWS, that a group, an identity or a deployment this run created is kept with its owner and reason, that a destroy plan taking one along stops before any approval is consumed, and that a forged proposal naming one never executes. Synthetic evidence only.

## Cleanup disposition

`cleanupDisposition` runs the same existence check after cleanup. Each resource ends in exactly one of these states:

| Disposition | Meaning |
| --- | --- |
| `DELETED` | The cloud says the resource no longer exists. |
| `RETAINED` | It is kept by a named owner, for a reason of at least ten characters. |
| `LEFTOVER` | It still exists and nobody kept it. |
| `UNPROVEN` | The check could not decide, or the type cannot be checked. It is never called deleted. |

- **Verdicts:**
  - `LEFTOVERS` when a resource of this run still exists and nobody kept it. That includes a resource still carrying the run's unit tag that the state never named.
  - `CLEAN` only when all of these hold:
    - the blueprint names at least one resource;
    - every resource is `DELETED` or `RETAINED`;
    - no planned resource was left unmapped;
    - no kept resource is reported gone;
    - a complete tag listing found nothing else of this run.
  - `INCONCLUSIVE` otherwise, with `unresolved` saying why. Completion is never reported in that case.
- **Timing:** the tagging API can keep listing a resource for a short time after it is deleted. A check run straight after a destroy can therefore report `LEFTOVERS` that clears on a later run. That fails closed.
- **Scheduled deletion:** a resource that deletes on a schedule, such as a KMS key in `PendingDeletion`, is read through its per-type state property (`CLOUD_CONTROL_TYPES[...].pendingDeletion`). It is `UNPROVEN` here and `DELETION_PENDING` in the leftover check, never deleted and never a plain leftover.
- **Which blueprint to use:** the one recorded when the journey was observed. A blueprint rebuilt from the state after a destroy is empty, and an empty blueprint is never `CLEAN`. A pilot run reports `INCONCLUSIVE` until the apply path tags its resources with a deletion unit.
- **Refused retention decisions:** a decision for a resource that is not part of this journey, a decision without an owner or a reason, or a resource kept twice.

## The run records

The driver and the commands keep the journey's records in the apply ledger (`.runs/apply/evidence/`), each bound to the one before it by hash. None holds an attribute value, a state document, a credential or a cloud error message.

| Record | Written by | Bound to | Replaced? |
| --- | --- | --- | --- |
| `<artifact>.apply.evidence` | the apply | the sealed plan | never |
| `<artifact>.blueprint.evidence` | the apply, from a `state pull` as STATE when it ends | the apply evidence hash | never |
| `<artifact>.observation.evidence` | `observe` | the blueprint hash | each observation |
| `.runs/apply/cleanup/<proposal12>.cleanup-proposal.json` | `propose-cleanup` | the apply evidence, blueprint and observation hashes | a new proposal is a new file |
| `<proposal>.cleanup.evidence` | `cleanup` | the proposal hash | never (a proposal runs once) |
| `<proposal>.leftovers.evidence` | `verify-cleanup` | the proposal hash and the cleanup evidence, when it exists | each check |

## The proposal

`buildCleanupProposal` (`src/apply/cleanup-proposal.ts`) turns the records into the exact list a cleanup may delete. The file it writes is a reviewable copy, not the authority: `runCleanup` reads the blueprint and the observation back from the ledger, requires them to hash to what the proposal names, rebuilds the proposal from them and the sealed plan's change list, and requires the rebuilt proposal to hash to the one handed in, before anything is reserved or any approval is consumed. It fails closed with `PROPOSAL_INVALID`, `OBSERVATION_INCONCLUSIVE` or `OWNERSHIP_AMBIGUOUS` when the apply was not `SUCCEEDED`, a planned resource never reached the state, the observation is `FAILED` or `INCONCLUSIVE`, or a resource's origin cannot be told. A run-created resource the Azure reader found outside the contract's location is `LOCATION_MISMATCH`: no ordinary cleanup, and the one governed alternative is the location remediation (`buildLocationRemediationProposal`, a proposal of kind `LOCATION_REMEDIATION`; `docs/act-pilot-apply.md`, "Location remediation"). Each resource in the state ends in one ownership class: `RUN_CREATED` (deleted), `PRE_EXISTING`, `REPLACED_PRE_EXISTING`, `IMPORTED` and `NOT_IN_PLAN` (kept by the environment's owner, with the reason), and the protected classes a pilot cleanup never deletes, kept by the pilot owner: `PROTECTED_BACKEND` (the state bucket or storage account and its settings, and the group that holds it), `PROTECTED_IDENTITY` (the pilot's roles and the OIDC trust; on Azure every identity and authorization object), `PROTECTED_DEPLOYMENT` (`Microsoft.Resources/deployments`), `RETAINED_GROUP` (every Azure resource group) and `CONTAINS_OTHERS` (a subscription or management group; on AWS a stack container). On AWS a run-created resource whose type is not on the reviewed leaf allowlist is `TYPE_UNREVIEWED`, kept by the environment's owner with its type named. Every kept entry carries `retainedBy` (`PILOT_OWNER` or `ENVIRONMENT_OWNER`, implied by the class) and a reason. When anything protected is kept, the risks tell the approvers that those objects stay and that retiring the environment is a separate, reviewed action that remains outstanding. Material risks, such as a bucket with objects or a key, are named for the approvers. The approvals required are the contract's for that environment; they are signed under the cleanup domain, so an apply approval never authorizes a cleanup and a cleanup approval never authorizes an apply.

## The leftover check

`verifyLeftovers` (`src/apply/leftovers.ts`) asks Cloud Control about every proposed resource after the cleanup, or before it to see what a cleanup would face. Each ends `CONFIRMED_DELETED`, `INTENTIONALLY_RETAINED` (with the owner who keeps it and the reason), `STILL_PRESENT`, `DELETION_PENDING` or `UNKNOWN` (unresolved: a missing, denied or failed read is never recorded as a deletion), with a next action for a person. A setting whose parent is confirmed gone counts as gone (`PARENT_ABSENT`); a setting whose own check cannot run and whose parent is not confirmed gone is `UNKNOWN`, also when it was already absent at proposal time. The record's disposition is `COMPLETE` only when every proposed deletion is confirmed gone or retained by name **and** a complete sweep by the run's deletion-unit tag found nothing else of this run outside the state. When the run carries no unit tag the sweep is `NOT_AVAILABLE` and the most the record says is `KNOWN_ADDRESSES_CONFIRMED`: the named resources are settled, resources outside the state were not searched for, and the cleanup is not independently complete (the #235 contract). `INCOMPLETE` otherwise. The validator refuses a `COMPLETE` without a complete sweep. A `COMPLETE` record reads "approved resources deleted; protected objects intentionally retained (n, kept by ...); full environment retirement ... remains outstanding" and never says the environment is deleted: a retained resource group that still carries the unit tag is a known identifier of the run, not a leftover.

## The report

`./alz apply report` builds the lifecycle acceptance report (`src/apply/lifecycle-report.ts`) from the records: stages execute, observe, propose, cleanup and leftovers, each `PASS`, `FAIL`, `INCONCLUSIVE` or `NOT_RUN` with the hash of the record it rests on. Each stage carries its evidence mode (`SYNTHETIC` or `LIVE`) and the report's mode (`SYNTHETIC`, `MIXED`, `LIVE`) is derived from them. `passed` is derived from the stages and the validator refuses a declared pass, a declared mode, a `LIVE` stage other than the execute step, a `LIVE` execute step without the owner's attestation of this very apply evidence, or any raw state, output or secret field. The journey matrix and `config/release/status.json` cite the report's tests for the `act:aws-terraform` gate. The leftovers stage passes only on `COMPLETE`; `KNOWN_ADDRESSES_CONFIRMED` is `INCONCLUSIVE` with the missing sweep named, so a run without a unit tag never passes.

The report keeps three states apart in `acceptance`, derived from the stages and the proposal and recomputed by the validator: `resourceCleanup` (`COMPLETED` only when the leftovers stage passed; `NOT_RUN`; `INCOMPLETE`), `retained` (what the proposal kept, counted by ownership class and by the owner who keeps it), and `environmentRetirement`, which is always `OUTSTANDING`: retiring the environment (its resource group, identities and grants, deployment history, the state backend) is a separate, reviewed action no run report claims. The `statement` of a passing report reads "approved resources deleted; ... intentionally retained ...; environment retirement outstanding"; a statement that reports the environment deleted, or omits that retirement is outstanding, is refused.

## Not covered here

- **Untaggable types.** A created resource whose type carries no tags (a bucket's versioning setting, a role assignment) is listed as untagged in the sealed artifact and is covered by the per-resource checks only; a sweep cannot find an orphan of such a type.
- **The CDK engine** seals no unit (its change set view carries no tags), so its cleanup is `KNOWN_ADDRESSES_CONFIRMED` at best until it has a tag reader.
- **AWS CDK.** It has no tag reader and no cleanup adapter; the commands refuse with `CLEANUP_NOT_SUPPORTED` and nothing runs.
- **Azure resource groups, identity and authorization objects, and deployment history.** Never deleted by a pilot cleanup, directly or as a dependent (`RETAINED_GROUP`, `PROTECTED_IDENTITY`, `PROTECTED_DEPLOYMENT`), whoever created them; each is recorded retained by the pilot owner with its reason. Retiring the environment (the group and what the pilot bootstrapped) is a separate, reviewed action and every record reports it outstanding.
- **Azure resources without an ARM id.** A key vault secret, a key, a certificate or anything else whose state `id` is a data-plane URL cannot be read by the Azure reader: it is `UNVERIFIABLE` (`NOT_AN_ARM_RESOURCE_ID`) in the observation, proposed as such, and `UNKNOWN` after a cleanup unless a confirmed-gone parent speaks for it, so a run that created one never reaches `COMPLETE` without a person's confirmation.
- **Live acceptance.** Running the journey against a real account, the owner's `record-live` attestation, and the teardown of the pilot accounts are the owner's, under `docs/act-pilot-plan.md`. No test here is live evidence.

Tests: `test/observe-blueprint.test.ts` (the core), `test/apply-cleanup.test.ts` (the driver and records, including forged proposals), `test/apply-cleanup-cli.test.ts` (the commands and the report) and `test/ui-channel.test.ts` (the console journey). All use a fake AWS CLI and a fake Terraform, so they are synthetic evidence. The blueprint parser is also checked against real `terraform show -json` and `terraform state pull` output from Terraform 1.16.4.
