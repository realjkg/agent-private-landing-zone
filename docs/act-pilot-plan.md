# PLAN: ACT pilot for the internal reference build (customer zero)

Status: approved by the repository owner on 2026-10-11 (amendment in `AGENTS.md`), amended by a recorded owner decision on 2026-10-12 (a person may run the pilot at the terminal or in the console wizard, one channel per workflow; authority items 1, 8 and 10, execution hosts), and amended by the owner's decisions of 2026-10-25 (issue #39, comment 6404130971: cleanup of pilot-created resources is under this same contract and its gates; see "Cleanup of pilot-created resources"), and amended by the owner's decision of 2026-10-27 (issue #39, comment 6442856302: the DEV-only scope extends to Azure Terraform; authority item 9 and "DEV-only scope"). The path is implemented and tested with a fake engine (a fake `terraform`, and a fake `aws` for the CDK engine) and, for Azure and Terraform only, with a real Terraform binary against an emulator (`docs/act-pilot-simulation.md`); no live run has happened and ACT is disabled until the pilot contract is pinned. Operations live in `docs/act-pilot-apply.md`. This is the single authoritative PLAN for the pilot; changing its scope or authority model requires a new PLAN.

## Purpose

Prove the product can take a previewed change from dev through QA to production on our own infrastructure, with evidence that passes the governance and production-conformance gates. This is not general availability, not a customer feature, and not a way to widen what agents may do.

## Authority model (the contract the driver enforces)

1. The operator authorizes. An interactive human gate approves each apply: a person typing each exact phrase at the terminal, or a person answering the same phrases in the console wizard after pasting the one-time session token the console printed in the terminal where it was started. Agents, the console's job table, and automation never initiate one, and nothing is ever typed or answered for the person.
2. An apply runs only the sealed plan that was previewed and approved (for the CDK engine, the sealed CloudFormation change set, which is created and never executed until the apply): the plan hash, manifest hash, channel and target must match the approved artifact (for CDK also the state of the stack the change set was made against, and the template the change set holds). Nothing is regenerated between approval and apply. A release counts as applied only when the engine's own result and the resulting state agree (CDK: the execute call, the stack and the change set), never from the state alone. QA promotes a release that succeeded in DEV, and production promotes a release that succeeded in QA, never a dev execution plan: it needs a separate production-target preview, sealed and approved on its own, and its release identity must equal the one a successful QA apply recorded, which in turn follows a successful dev apply.
3. Approvals are authenticated, not recorded. An approval is an Ed25519 signature by a key on an allowlist, over a statement that binds the exact artifact hash (which covers the plan, the target, the channel and the pinned contract's hash, so the provider, region and tenant), environment, target (account, backend, workspace), expiry, and a one-time nonce. A typed name is never proof. The requester of a change is authenticated the same way (owner decisions of 2026-10-27, issue #39, comments 6432115178, 6432129534 and 6432161993, and the approved PLAN): at seal the requester signs the artifact hash, the environment and a nonce with their own allowlisted key under a separate signature domain (`src/apply/approval.ts`, subject `REQUEST`), the requester id is bound into the artifact hash every approver signs, and the driver verifies that signature before any approval; the request nonce is recorded, not consumed, because replay is prevented by the artifact ledger (an artifact applies once; a second apply is refused as `ARTIFACT_ALREADY_APPLIED`); any allowlisted key may request for any environment, and a plan without a requester signature is refused everywhere. In DEV and QA the same person may request and approve. Production requires three distinct people: two distinct verified approvals, and neither may be the requester, so an approval from the requester's key or from any key sharing the requester's id is refused (`APPROVER_IS_REQUESTER`). The rule is a code constant per environment (`REQUESTER_MAY_APPROVE`), never a contract field or a flag. The same quorum governs a cleanup (owner decision of 2026-10-27, issue #39, comment 6440801434, item 1: cleanup must not be the lower-assurance destructive path): a cleanup proposal has its own requester, who signs the proposal's hash, the environment and a nonce with their own allowlisted key under the separate `CLEANUP_REQUEST` signature domain when the proposal is made (`./alz apply propose-cleanup --requester ID --key KEY.pem`); the requester id is bound into the proposal hash every cleanup approver signs; the signature is verified by `approve` before anything is shown, by the driver at the cleanup gate and again before the approvals are consumed; and the approval set is judged by the same check and the same constant as an apply (`verifyApprovalSet`, `approverIsRequester`). A production cleanup therefore needs the requester plus two distinct approvers, neither of them the requester by id (case-insensitive) or by key under any id; DEV and QA behave as an apply does. A request signature of one kind never verifies as the other, so an apply's request cannot be carried onto a cleanup or back, and a cleanup proposal made before cleanup requesters existed (schema 1) is refused everywhere. Replayed, expired, or mis-bound approvals are refused.
4. Separate identities (Terraform's four; the CDK engine's three, DISCOVERY, CHANGESET and APPLY; an engine spec lists its own, and an identity the engine does not use is refused when configured), injected through the `ALZ_<IDENTITY>_<VAR>` path used by the runner: DISCOVERY (provider reads), STATE (state read and lock), STATE_WRITE (state write and lock, used only by apply), and APPLY (provider writes). CHANGESET (CDK only) creates and describes change sets and cannot execute one; APPLY alone executes. None inherits operator credentials and none falls back to another; in particular APPLY is never used as a state fallback. The backend must write state and coordinate locking, so STATE stays read-only for state content and STATE_WRITE is the only identity that can change state.
5. State locking stays on. State and plan files are sensitive material: the sealed plan is encrypted at rest and never written to evidence in the clear.
6. A kill switch stops a pilot apply or cleanup, and the driver's behavior on partial failure is defined before the first dev apply.
7. Every apply writes encrypted evidence: who approved, what artifact, what ran, the result, and the redacted output.
8. The console's fixed job table does not gain an apply job, and the catalog validator still refuses one. The console's pilot wizard is a separate door: `src/cli/ui-channel.ts` runs the same commands as the terminal through dialogs, only for a request that carries the session token, and it is the only console module that touches `src/apply`. The Operations card for the pilot stays a handoff.
9. ACT remains DISABLED unless the pilot release contract enables it. A flag or environment variable alone must not. A contract may narrow the pilot to DEV only (`"enabledEnvironments": ["DEV"]`, with only the DEV target and DEV approvals) for AWS Terraform (ACT-DEV-1, owner decision of 2026-10-23, `docs/act-dev-1.md`) and for Azure Terraform (owner decision of 2026-10-27, issue #39, comment 6442856302: "Clear paths to ACT enablement in both Azure and AWS for dev"). The exception is DEV only and has the same pilot plan, contract, pin and gates. Any other provider or engine, and any scope that names QA or PROD, needs the full three-stage contract, and the validator refuses it (`src/apply/contract.ts`). The DEV-only scope enables nothing by itself: ACT stays disabled until the owner's reviewed pin commit.
10. A pilot workflow runs wholly in one channel, `CLI` or `UI`, chosen at the start and never mixed. The channel is set by the calling code, never by a flag or a file, is sealed into the plan and therefore into the artifact hash every approver signs, and `approve` and `apply` refuse with `CHANNEL_MISMATCH` when invoked through the other channel, before anything is consumed. Choosing a channel changes who may type a phrase, not what any gate checks.

## Execution hosts

- **Operator terminal:** the apply command refuses unless stdin and stdout are terminals. Credentials come from the operator-controlled host.
- **Console wizard (UI channel):** the same commands, started from the console on the operator's machine, bound to the loopback address. Each request must carry the session token printed at console start (never in the page, a link or a log), come from the console's own origin, and be a small JSON body. The wizard's dialogs ask the same exact phrases. The approver's key stays a file on that machine, checked as the terminal checks it, and is never uploaded or shown. Credentials still come from the environment of the terminal that started the console. GitHub OIDC is not assumed to exist on an arbitrary terminal.
- **GitHub:** human approvals are captured and verified before the apply job is dispatched; the job receives only the sealed artifact reference and the verified approvals. STATE_WRITE and APPLY authenticate through separate environment-bound federated identities. A GitHub required-reviewer list needs only one reviewer, so it does not satisfy the two-person production rule on its own.

## Pilot prerequisites

Supplied by the owner and listed in `docs/act-pilot-apply.md` ("What the owner supplies"). Missing real values block qualification and apply, not implementation; tests use explicit fixtures. Fake-engine tests are not real-engine qualification.

## Scope

- One internal environment chain (dev, then QA, then production), one provider (the pinned contract's `provider`: Azure or AWS, each with its own spec; the static production contract lists exactly Azure/Terraform, AWS/Terraform and AWS/CDK, with no inference or wildcard), one engine (the pinned contract's `engine`: Terraform, or CDK with AWS only, each with its own spec), chosen at Gate 0 from the engines that pass real-engine qualification.
- No customer environments, no multi-tenant console, no new feature that lacks existing wired code.

### GCP release path (approved PLAN, not implemented)

The owner approved a GCP release path on 2026-10-27 (issue #39, comment 6433121154), to go live after AWS Terraform and Azure. It uses the Terraform engine with the `hashicorp/google` provider and the `gcs` state backend, one project per environment, each with its own versioned state bucket. Its four identities are Workload Identity Federation principals, each impersonating its own service account, with no key files (`iam.disableServiceAccountKeyCreation` is enforced on the pilot projects). `google-beta` is refused. GCP is not yet a provider the contract accepts and not yet in the static production contract or `config/release/scope.json`: slices S0 to S7 build it in order, and until they land a `GCP` contract is refused. The DEV-only scope exception covers AWS Terraform and Azure Terraform only (authority item 9): a GCP contract is a three-stage contract, and a DEV-only GCP scope would need its own owner decision. ## Where it lives

The apply driver and its pieces are in `src/apply/` (contract, approval, identities, sealed plan, driver, one engine spec per engine in `engine-spec.ts` and `engines/` (Terraform, with its pinned surface in `terraform.ts`, and CDK in `engines/cdk.ts`), and one provider spec per provider in `provider.ts` and `providers/`: Azure with the AzureRM backend and AWS with the S3 backend), the human entries are `src/cli/apply.ts` (the terminal) and `src/cli/ui-channel.ts` (the console wizard's only bridge, mounted by `src/operator-ui/server.ts`, with the wizard in `src/operator-ui/app/pilot/`; a person-level walkthrough is `docs/act-pilot-walkthrough.md`), release admission checks the same contract pin in `src/qualification/release-admission.ts`, and the boundary tests are `test/apply-boundary.test.ts` and `test/teardown-driver-denials.test.ts`.

## Out of scope

- Enabling ACT for agents, or for any path that lacks the interactive gate.
- Customer or multi-tenant use.
- Any change to model, tool, or approval authority for agents.
- Any destroy other than the cleanup below: a destroy of the state backend, of the pilot's identities, of resources this pilot did not create, or of a whole workspace.

## Cleanup of pilot-created resources

Recorded owner decisions (2026-10-25, issue #39, comment 6404130971). Cleanup of what a pilot apply created is part of this PLAN and runs under the same contract, pin and gates; it does not enable ACT (the shipped pin stays empty) and a live teardown still needs the owner's separate authorization.

1. **Identity.** The cleanup delete is executed by the existing APPLY identity. There is no new CLEANUP role. The delete is bound in code to the approved cleanup proposal's exact resource list (`src/apply/driver.ts` `runCleanup`): the engine plans a destroy limited to those addresses (`src/apply/terraform.ts`, the cleanup adapter, the one place a targeting flag or `-destroy` appears in the apply path), and the plan's change list must be exactly those addresses, every one a delete, before any approval is consumed. A dependent the engine adds, an address the state no longer holds, or any other action refuses with `PROPOSAL_SCOPE_MISMATCH` and nothing is consumed. The proposal file itself is never trusted for that list: before anything is reserved, `runCleanup` reads the blueprint and the observation back from the ledger, requires them to hash to what the proposal names, rebuilds the proposal from them, the sealed plan's change list and the pinned contract, and requires the result to hash to the proposal handed in. A proposal edited and re-hashed to add a protected identity, the state backend, a resource this run did not create, or to drop an entry, is `PROPOSAL_INVALID` before any approval is consumed (`test/apply-cleanup.test.ts`).
2. **Authorization.** The same signed flow as an apply, over a new artifact: the cleanup proposal (`src/apply/cleanup-proposal.ts`), identified by its hash, built from the run's own records (the apply evidence, the blueprint the engine's state gave when the apply ended, and a fresh independent observation), each bound by hash. It uses the same approver allowlist, quorum, requester rule (authority item 3: in production the requester plus two distinct approvers, neither the requester), expiry, nonce and replay protection, kill switch and typed phrases. Approvals are Ed25519 signatures over the proposal's hash under a separate signature domain (`src/apply/approval.ts`, subject `CLEANUP`), so an apply approval can never authorize a cleanup and a cleanup approval can never authorize an apply, whatever hash either names. A proposal executes once (`.cleanup.evidence` ledger under its hash).
3. **Ownership and scope.** A resource is proposed for deletion only when the sealed plan created it, the engine's state still holds it, and the independent observation found it (or it is a setting the independent reader cannot read alone). On AWS a resource is proposed only when its type is also on the reviewed leaf allowlist (`src/observe/aws-leaf-types.ts`, delegated owner decision 6433391052), and an attachment or setting only together with the resource it modifies; any other type the run created is kept, named and left to the environment's owner (`TYPE_UNREVIEWED`), and the leftover check cannot report `COMPLETE` while one remains. Pre-existing, imported, replaced, unplanned and protected resources are excluded and listed with their reasons and with who keeps them (`retainedBy`: the pilot owner for a protected class, the environment's owner otherwise). Tags are never ownership evidence. Protected, whoever created them and whatever the plan said (owner decisions 6408600057, 6408642348, 6408777768): the state backend in every form its identifier takes and the group that holds it (`PROTECTED_BACKEND`); every identity and authorization object, on Azure by Terraform type or by the ARM type of the id (`PROTECTED_IDENTITY`); deployment history, `Microsoft.Resources/deployments` by type or by id (`PROTECTED_DEPLOYMENT`); **every resource group** (`RETAINED_GROUP`: a pilot cleanup deletes approved, run-owned resources only, never the group, whatever it holds; the group is recorded as intentionally retained by the pilot owner, and its deletion is a separate, reviewed action); a subscription or management group (`CONTAINS_OTHERS`). The containment-based group deletion of an earlier version is removed with no legacy path. After the engine's targeted destroy plan, `protectedDeletionIn` refuses a plan that would delete any of these, directly or as a dependent, before any approval is consumed. No proposal is made from an apply that did not succeed, from a planned resource the state never recorded, or from an observation that could not decide or found something unexpected: a person reviews by hand.
4. **Verification.** After a cleanup, the same read-only boundary (AWS: Cloud Control through the aws CLI; Azure: Azure Resource Manager read in process, the DISCOVERY identity's federated token exchanged in an HTTPS body and never placed in a process argument, a log or evidence; both under the DISCOVERY identity) checks every proposed resource: confirmed deleted, intentionally retained, still present, deletion pending, or unknown. Completion (`COMPLETE`) is reported only when every proposed deletion is confirmed gone and a complete sweep by the run's deletion-unit tag found nothing else of this run; the cleanup's own exit code is never taken as proof, and a missing, denied or failed read stays unresolved (`UNKNOWN`), never a deletion. A passing record reads "approved resources deleted; protected objects intentionally retained" and never "entire environment deleted". A run that carries no unit tag cannot be swept, so its record says at most `KNOWN_ADDRESSES_CONFIRMED`, which is not completion and does not pass the lifecycle report.
5. **Report.** `./alz apply report` writes the lifecycle report (`src/apply/lifecycle-report.ts`) from the run's records: stages execute, observe, propose, cleanup and leftovers, with `passed` derived and recomputed by its validator. Each stage carries its own evidence mode: the execute step is `LIVE` only when the owner's live record (`./alz apply record-live`) covers the same apply evidence; the other stages are `SYNTHETIC` until an owner attestation exists for them, so the report's mode, derived from the stages, is `MIXED` at best and never `LIVE` by declaration. The report keeps three states apart (`acceptance`): resource cleanup completed, resource group and protected objects intentionally retained (counted by class and by owner), and full environment retirement, which is always reported outstanding.
6. **Deletion unit.** One pilot state container (the contract's backend and workspace for one environment) is one deletion unit, named by the product's one tag scheme (`src/teardown/unit.ts`, `src/apply/unit.ts`: `alz-managed-by=alz`, `alz-unit=<unit>`, `alz-build=<pilot build id>`). The product writes nothing into the operator's project: `prepare` tells the operator the exact tags, the operator's own provider configuration declares them (AWS `default_tags`, Azure `tags`), `seal` verifies in the plan that every created resource whose type carries tags carries exactly them and refuses a missing, foreign or computed tag (`UNIT_TAG_MISSING`, `UNIT_TAG_FOREIGN`, `UNIT_TAG_UNVERIFIABLE`), and the sealed artifact binds the unit and the list of created resources no tag can reach, so approvers see both. The observation and the leftover check sweep by the unit tag; a tagged resource the state does not name fails the observation and keeps the cleanup incomplete. A tag stays a pointer, never ownership evidence. An engine without a tag reader (CDK) seals no unit and its cleanup is `KNOWN_ADDRESSES_CONFIRMED` at best.

Operations are in `docs/observe-and-cleanup.md`; the console steps in `docs/act-pilot-walkthrough.md` ("Check and clean up").

## Process

- Lanes may run in parallel only inside DO and on disjoint paths. Convergence and the production decision are serialized.
- Push in batches. Documentation changes ride with the code they describe and are never merged on their own; they run no heavyweight gate. The manual dispatches above are the heavyweight runs, and each is justified by its gate.
- A failed gate returns to the affected lane. A change to this authority model stops the iteration and creates a new PLAN.
