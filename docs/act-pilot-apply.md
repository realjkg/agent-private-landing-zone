# Pilot apply: operator runbook

Status: implemented and tested **with a fake engine only** (a fake `terraform`, and a fake `aws` for the CDK engine). It has never been run against a real Terraform engine, the real AWS CLI, CloudFormation, a real Azure subscription or a real AWS account, and the qualification and identity separation it depends on are only attested, by a person, once they complete the real-engine run below (G2); nothing in the code proves them. A fake-engine test pins logic, not behavior. Live apply stays blocked until the owner supplies the values at the end of this page and that evidence exists.

The plan is `docs/act-pilot-plan.md`. The preview driver this builds on is `docs/destroy-preview-driver.md`.

## Authority

The operator authorizes, the driver enforces, and agents never initiate. ACT stays DISABLED globally. It is enabled for the pilot only while `config/act-pilot-contract.json` is valid, has `enabled: true`, and its `authorize` entry lists the operation for the environment (see "The contract is the authorization"). The Operations catalog shows the command (`./alz apply`) as a handoff and its job table never runs it. A person can instead run the whole workflow in the console's Pilot apply wizard (`docs/act-pilot-walkthrough.md`); that is the UI channel (see "Channels"). `test/apply-boundary.test.ts` pins that nothing the broker, agents, orchestration or the catalog can reach imports the apply path, and that from the console side only `src/cli/ui-channel.ts`, mounted by the console server, does.

An apply runs exactly the sealed artifact that was previewed and approved (for Terraform, the plan file: `terraform apply <planfile>`; for CDK, the sealed CloudFormation change set: `aws cloudformation execute-change-set` for that change set's ARN). Nothing is regenerated between approval and apply. There is no `-auto-approve`, `-target`, `-replace`, `-refresh=false` or `-lock=false`, and locking stays on. Each stage (DEV, QA, PROD) is a separate target-bound sealed plan with its own approvals, bound to the qualified release through `releaseIdentity` (project files, lock file, engine and provider versions, shared inputs); see "Promotion". The earlier stage's manifest hash is not needed, because manifests are target-bound.

## What a person, a terminal and a signature each prove

A terminal is not authentication. Every subcommand needs a terminal on stdin and stdout, and that only means a person, or a script holding a pseudo-terminal, is typing; it proves nobody. The console wizard's dialog terminal is the same thing by another route: it reports a terminal only for a request that carried the one-time session token, and a person answering a dialog in a browser proves as little as a person at a keyboard. Typed confirmations prevent mistakes (the wrong target, the wrong plan). They are not identity.

Signatures are the authentication. An approval is an Ed25519 signature, by a key in the contract's `approvers` list, over the artifact hash, environment, exact target, expiry and a one-time nonce. The requester is authenticated the same way: at seal, the requester signs the artifact hash, the environment and a one-time nonce with their own allowlisted key (`--requester ID --key KEY.pem`, under the separate `REQUEST` signature domain, so a request never verifies as an approval and an approval never as a request), the requester id is part of the artifact hash every approver signs, and the sealed plan and the review bundle carry the signature (`verifyRequestSignature`, checked by `approve` before anything is shown and by the driver before any approval, and again before the approvals are consumed). A requester may request only in the environments their allowlist entry names, the same `environments` that govern approving: seal, `propose-cleanup` and `propose-removal` refuse anything else before a plan or proposal is made, and `approve`, the driver and the removal refuse a request signature whose requester's entry does not name its environment (`REQUESTER_NOT_ALLOWED`); a plan without a requester signature, or one sealed before requester signatures existed (schema 1), is refused everywhere. A typed name is never proof. The key is a file you name (mode 0600), never read from the environment. Whoever holds an approver's private key is that approver, so approver key custody is an operational control, not something the code enforces: each approver should keep their key on their own device, and the contract's allowlist is reviewed in the commit that changes it. The code cannot tell whether one person holds two keys.

An approver does not need the operator's evidence key, the vault or the sealed plan. They need the review bundle (below), the contract, and their own key file.

Production's rule is three distinct people: two distinct allowlisted approvers with two distinct keys, both signing the same artifact, and neither of them the requester. An approval from the requester's key, or from any key listed under the requester's id (compared case-insensitively), is refused as `APPROVER_IS_REQUESTER` and nothing is consumed; `approve` refuses it before asking for the phrase, and the driver refuses it again. In DEV and QA the same person may request and approve (`REQUESTER_MAY_APPROVE` in `src/apply/approval.ts`, a code constant, never a contract field or a flag). A cleanup follows the same rule through the same check (see "Cleanup"). It is still not a check on who runs `apply`: the operator's account name has no bearing, and the same person holding several keys defeats it. Approvals are consumed once, before the engine runs; the request nonce is recorded in the evidence and never consumed, because the request binds one artifact and the ledger applies an artifact once, so a plan given back after `KILL_SWITCH_AFTER_APPROVALS` keeps its request signature for new approvals.

## Who is inside the trust boundary

The operator who runs the commands is the same user ID as the process, and holds the evidence key, the working tree and the contract, and sets the identity variables. For key material that operator is inside the trust boundary. The committed contract, the hashes bound at seal, the encryption and the ledger make a change reviewable and tampering detectable by anyone who does not hold the key; they do not stop the operator, who could re-encrypt evidence, forge qualification evidence, edit the ledger, or commit an edited contract. The contract's review is reviewable, not enforced, against a writer with that user ID. The identity checks below catch mistakes and crafted environments, not the operator. Independence comes from the second approver, the contract reviewed in version control, and the cloud-side role assignments, not from this code. The encrypted recovery files and evidence protect against other accounts and backups, not against the operator.

## Commands

Every subcommand refuses before reading any file unless it has a terminal on stdin and stdout (at the terminal, the real one; in the console wizard, the dialog terminal of a request that passed the session-token check). There are no flags that force, skip or pre-answer anything; an unknown flag is an error. `qualify` is terminal-only in practice: the wizard runs `preflight`, `prepare`, `seal`, `approve` and `apply`.

| Step | Command | Who |
| --- | --- | --- |
| Prepare | `./alz apply prepare --environment DEV\|QA\|PROD --project PROJECT_DIR [--aws-cli-version X.Y.Z]` | Operator. Writes the seal request and the artifact manifest for one project, so nobody authors them by hand. See "Preparing the request and manifest". Local and offline: runs no engine, assumes no role, seals, approves and enables nothing. |
| Qualify | `./alz apply qualify --request REQUEST.json --manifest MANIFEST.json` | Operator, once per adapter or engine version, DEV only. See "Qualifying against a real engine". |
| Seal | `./alz apply seal --request REQUEST.json --manifest MANIFEST.json --requester ID --key REQUESTER_KEY.pem` | The requester, an allowlisted id with that entry's own key file (read as an approver's key is: mode 0600, Ed25519, never the environment); a stranger or another entry's key is `REQUESTER_NOT_ALLOWED` or `REQUESTER_KEY_MISMATCH` before any engine runs. Types the target, then (Terraform only, which runs providers and modules) `RUN PROJECT CODE`; the CDK engine runs no project code and asks for the target only. Prints the artifact hash, the sealed plan path, the review bundle path and the redacted change list (address, type, action). |
| Approve | `./alz apply approve --bundle REVIEW_BUNDLE.json --key APPROVER_KEY.pem --approver ID` | Each approver, separately, with no evidence key. The bundle's requester signature is verified first and the requester is shown; for PROD the requester's own id or key is refused (`APPROVER_IS_REQUESTER`) before the phrase. Reviews the changes, types `APPROVE <DEV, QA or PROD> <first 12 characters of the artifact hash>`. Prints a signed approval; no secret. |
| Apply | `./alz apply apply --request REQUEST.json --manifest MANIFEST.json --sealed SEALED_PLAN --approval A.json [--approval B.json]` | Operator, with the evidence key (it loads the sealed plan from the vault). Types one line: `APPLY <DEV, QA or PROD> <first 12 characters of the artifact hash> <account> \| <backend> \| <workspace>`. Prints redacted evidence. |
| Preflight | `./alz apply preflight --environment DEV\|QA\|PROD [--contract CONTRACT.json]` | Anyone at a terminal, before the first seal. Read-only and offline: checks the contract's shape (a draft or example that is not enabled or authorized too), whether it is enabled and authorizes APPLY in the environment, that each identity the engine needs is configured, distinct, fallback-free and aimed at the environment's account, that the engine's program is in an approved tool directory, the kill switch, and whether the engine is qualified for seal and apply. Readiness is defined once, in `src/apply/readiness.ts` (`assessReadiness`), and the three decisions once (`actDecisions`): preflight prints the READY items with the AUTHORIZED entries and the per-run APPROVED requirement beside them, and the console's readiness step and status block read the same output. A financial controls item is reported (`UNVERIFIED`, advisory): nothing checks a budget or cost cap yet, and it never stops a run. The qualification item runs the same record and evidence checks as seal and apply, so preflight never says ready where seal would refuse `ENGINE_NOT_QUALIFIED`.

Every item has a `state`:
- `READY`.
- `MISSING`: absent.
- `INVALID`: present but wrong, or evidence that no longer matches this machine.
- `UNVERIFIED`: not yet proven on the real cloud.
- `UNAVAILABLE`: a tool not installed here.
- `BLOCKED`: a stop put in place on purpose, the kill switch.

Each item that is not ready also names who can fix it: `OWNER`, `OPERATOR` or `TOOL`. The report's `next` is the first item that is not ready, in journey order, never a later one. "Identity separation attested on the real DEV backend" is `READY` only when the qualification evidence records the person's attestation; otherwise it is `UNVERIFIED`. Prints names, never values; exit 2 if anything is not ready. Setup of the accounts it checks is in `docs/act-pilot-bootstrap.md`, separate from any apply. |
| Status | `./alz apply status [--environment DEV\|QA\|PROD] [--sealed SEALED_PLAN]` | Anyone at a terminal. Read-only: the three decisions from `actDecisions` (AUTHORIZED: each `authorize` entry and its hash; READY: the readiness items for the environment named; APPROVED: the requester and quorum each run needs), the contract hash and kill switch, and whether an artifact was applied (with the contract and authorization hashes it was sealed under). |
| Remove working files | `./alz apply propose-removal --sealed SEALED_PLAN --requester ID --key REQUESTER_KEY.pem`, `./alz apply approve --bundle REMOVAL_PROPOSAL.json ...`, `./alz apply remove-workspace --proposal REMOVAL_PROPOSAL.json --sealed SEALED_PLAN --approval A.json ...` | Requester, approvers, operator: the same proposal, quorum and kill-switch path as a cleanup. Removes one run's preparation files and the driver's abandoned scratch directories; keeps every evidence, ledger, sealed and log record. See "Removing a run's working files". |

There is no `--allowlist` and no `--qualifications` file. The approver allowlist is part of the reviewed contract, and qualification records are read from the encrypted evidence vault (`.runs/apply/qualification`), where a record exists only if valid, decryptable evidence does.

Request files carry only `environment`, `target` (`account`, `backend`, `workspace`; `account` is the provider's account identifier) and `projectRoot` (seal and qualify also `policyVersion` and `resolved`). The command supplies the invocation, manifest and approvals; a file that carries them is refused.

### Preparing the request and manifest

`prepare` builds both files through the same schema and binding code `seal` uses (`buildManifest`, `verifyManifest`, `validateManifestForRequest`), so it is not a second implementation. Its journey: select the project folder, the engine and target come from the reviewed contract, missing values are asked for, a readable review is printed, the files are saved, and the next valid step (or the exact blocker) is named.

- **Engine and path.** The contract's engine is used; no flag names one and prepare never switches engines. A folder of the other kind (a `cdk.out` where Terraform is pinned, or the reverse) is refused. Paths per provider: AWS has Terraform (primary) and CDK (secondary); Azure has Terraform (primary) and Bicep (secondary, DEV only, owner decision E2: a `main.bicep` project, with the tested az pin as the engine version until it is qualified; `docs/act-pilot-bicep.md`).
- **Target.** Account, region (when the target has one), backend or stack, and workspace come from the contract's target for the environment, confirmed by the same check `seal` runs.
- **Values.** `policyVersion` comes from the contract's optional `policyVersion` field; when it is absent prepare stops with an owner prerequisite rather than guess. Providers and the lock file hash come from `.terraform.lock.hcl`, which must be present (and `.terraform/` absent). The engine version comes from a matching qualification record, else the tested Terraform pin in `config/tool-pins.json`, else (CDK) the AWS CLI version the operator supplies with `--aws-cli-version` or is asked for. The unit hash is a labeled convention: `sha256(canonicalJson({purpose: "pilot-preparation-unit", engine, environment, target, files}))`. Inputs (`src/apply/terraform-inputs.ts`):
  - **Terraform:** each root variable becomes an input. Its identity is a hash of where its value comes from, never the value. The sources follow Terraform's precedence: `*.auto.tfvars(.json)` (the last one, in lexical order, wins), then `terraform.tfvars.json`, then `terraform.tfvars`, then `ALZ_DISCOVERY_TF_VAR_<name>` (the seal plans as DISCOVERY), then the default. A variable with no value is refused (`INPUT_UNSET`), naming it and never asking for its value.
  - **CDK:** each template parameter becomes an input from its default. The pilot passes no parameter values, so a parameter without a default is refused.
  - **Environment values:** an input from an environment variable is named, not fingerprinted; the sealed plan binds what it produced.

  Dependencies: every module call is followed through local modules. Only `./` or `../` folders inside the project are accepted, and their code is fingerprinted with the project files. A remote module (registry, Git, HTTP, S3) is refused (`MODULE_REMOTE`), because neither the lock file nor the fingerprint binds its code. So is a folder outside the project (`MODULE_OUTSIDE_PROJECT`). `dependencies` is therefore empty for every accepted project.
- **Files.** `.runs/pilot/<ENV>/request-<id>.json`, `manifest-<id>.json` and `preparation-<id>.json`, where `<id>` is the first 16 characters of the manifest hash; mode 0600 in a 0700 folder, written all-or-nothing.
- **Evidence.** Every output is labeled `LOCAL_PREPARATION`. Prepared files are not qualification evidence and do not show that anything works in a cloud.
- **Refusals.** Owner prerequisites (contract not enabled or not authorizing, kill switch, policy version missing, target not in the contract) never offer an alternative. A missing tool (`TOOL_UNAVAILABLE`) may name the other supported path, which needs its own reviewed contract, preview and approvals. Exit 0 prepared, 1 a CLI error, 2 blocked.

### The deletion unit

Every pilot run into one environment's state container belongs to one deletion unit (`src/apply/unit.ts`, reusing `src/teardown/unit.ts`): `alz-managed-by=alz`, `alz-unit=alzu-<20 hex>`, `alz-build=alz-pilot-<env>-<contract12>`. `prepare` prints the unit and the required tags; the operator declares them in the project's own provider configuration (AWS: `default_tags` in the `aws` provider block; Azure: `tags` on each resource). `seal` reads the plan's `after` for each created resource: a type whose plan carries a tag attribute (`tags_all` or `tags` for AWS, `tags` for Azure) must carry exactly the unit's tags, or the seal is `ARTIFACT_INVALID` with `UNIT_TAG_MISSING` (absent or another build), `UNIT_TAG_FOREIGN` (another unit) or `UNIT_TAG_UNVERIFIABLE` (computed at apply time); only the unit's own tag keys are read, no other value leaves the plan. Created resources with no tag attribute are listed as `untagged` in the sealed artifact and the review bundle. The sealed `unit` is bound by the artifact hash, shown to approvers at the terminal and in the console, written into the blueprint record at apply, and swept by the observation and the leftover check. The CDK engine seals `unit: null`.

### Source-bound evidence

Every seal and apply names the product source commit it ran from.

- **Where the commit comes from.** In a git checkout, the commit is `HEAD`, and only while `git status --porcelain` is empty (ignored files such as `.runs/` do not count). Without a checkout (the packaged image, which `./alz` builds only from a clean commit), it is the image's `ALZ_SOURCE_COMMIT` stamp. The stamp never overrides a checkout. Anything else is `SOURCE_UNVERIFIED`. The CLI resolves the commit (`src/util/source-commit.ts`); the driver starts no process to find it.
- **Seal.** An unknown or uncommitted source stops `seal` and `qualify` before any phrase is asked. The commit is shown on the seal screen and bound into the artifact hash and the review bundle (`sourceCommit`), so approvers sign that version. The console shows it on the review as "App version that prepared it".
- **Apply.** A plan applies only from the commit that sealed it. A different running commit is `SOURCE_CHANGED`, refused before the apply phrase is asked and again by the driver, and nothing is consumed. The evidence records `sourceCommit`, and the console's Results page shows it.
- **Not covered.** A native checkout runs the compiled `dist/`, so a `dist/` built from an older commit is not detected. Run `npm run build` (or `./alz bootstrap`) after changing commits.

Plans and review bundles sealed before this field existed fail verification as malformed. Seal them again.

### Preview provenance

Every seal records which engine program made its preview and whether real-engine evidence covers that program (`provenance` in `src/apply/types.ts`).

- **What is recorded.** `engineBinarySha256` is the SHA-256 of the program the runner resolves from the approved tool directories (Terraform's `terraform`, the aws CLI for CDK), read once before the plan runs. `qualification` is `QUALIFIED`, with the evidence hash and date, only when the vault's real-engine qualification evidence for the preview adapter covers this adapter version, argument digest, engine version, the contract's DEV target, the attested client ids and this exact program hash. The check is the same one an apply passes (`verifyApplyQualification`). Otherwise it is `UNQUALIFIED` with the reason. The seal still needs a qualification record for the preview adapter, as before; the provenance says whether that record's evidence stands behind this program.
- **Why not the tool pin.** `config/tool-pins.json` pins the checksum of the downloaded archive, not of the program inside it, so the program hash cannot be compared to the pin. The qualification evidence records the hash of the program it actually ran, so that is the comparison made.
- **Bound and shown.** The provenance is inside the artifact hash and the review bundle, so approvers sign it and an edited claim is `ARTIFACT_TAMPERED`. `approve` and `apply` show it as `preview engine` and `qualified`. The console review shows "Build tool that made this preview" and "Tested on the real cloud"; when the answer is no, the exact reason is under Details.
- **Apply.** A plan applies only with the program that made its preview. Another program, or none, is `ENGINE_BINARY_CHANGED`, refused before the apply phrase is asked and again by the driver, before anything is reserved or consumed. Restore that program, or seal and approve a new plan. The apply's own qualification check still runs, so an `UNQUALIFIED` preview made by a program the apply evidence does not cover is also refused (`ENGINE_NOT_QUALIFIED`).
- **Not covered.** As for the qualification check, the same-uid operator who can replace the program between this read and the run is inside the trust boundary.

Plans and review bundles sealed before this field existed fail verification as malformed. Seal them again.

### Recording live acceptance of the execute step

After an owner-supervised apply has SUCCEEDED against the real account, the person who ran it records it:

```
./alz apply record-live --sealed SEALED_PLAN
```

The command reads that plan's apply evidence from the encrypted ledger, so it needs the evidence key, and shows the environment, target, artifact, product commit and outcome. The person then types `LIVE <ENV> <first 12 characters of the artifact hash>` to attest that it ran against the real account, not a test or a fake engine. That phrase is the person's attestation, as in `qualify`; the code cannot tell a real account from a fake engine.

It then writes `config/acceptance/evidence/<cloud>-<engine>-execute-<env>-<artifact>.json`. The file holds identifiers and hashes only (source commit, cloud, engine, target, artifact, outcome, evidence hash, contract hash, who attested and when) and is never overwritten. The owner reviews it, commits it, and cites it as `liveEvidence` on the execute step in `config/acceptance/journeys.json`. The matrix then accepts `LIVE_PASS` for that step only. The row is live only when every step passes.

It refuses an artifact that was never applied, a failed, partial or killed apply, and an apply under another contract or authorization than the one committed now. It starts no engine and changes nothing in any cloud.

### Recording an interrupted apply's recovery

The `act-run-recovery` release gate (docs/production-release-admission.md) asks for an interrupted real pilot apply reconciled from its ledger and never resumed without new approval. The product's own producer of that evidence is:

```
./alz apply record-recovery --sealed INTERRUPTED_SEALED_PLAN --resumed RESUMED_SEALED_PLAN --target-hardware-id HOST
```

It reads two apply evidences from the encrypted ledger: the interrupted plan's (its outcome must be `PARTIAL_REQUIRES_REVIEW` or `KILLED`, the ledger's own record of how the run ended, with any recovery files it kept by count and hash) and the plan that followed it (another sealed artifact, since a reserved artifact is never applied again, under the same contract, environment and target, that `SUCCEEDED` with at least the contract's required number of distinct approvals, every one issued after the interruption ended and the run started after it, since an approval is consumed once). The gate's four fields (`interruptedArtifactSha256`, `interruptedOutcome`, `reconciledFromLedger`, `resumedWithoutApproval`) and every condition are derived from those records and the reviewed contract (`src/qualification/recovery-gate.ts`, shared with the admission review, which recomputes them all); nothing is typed but the host name and the attestation `RECOVERY LIVE <ENV> <interrupted artifact, 12 characters> <resumed artifact, 12 characters>`, which the person types only if both runs reached the real account and the interrupted run was reviewed from its ledger evidence before the new plan was sealed and approved. A pair of runs that does not show a recovery is refused by name before the phrase is asked for and nothing is written (`RECOVERY_NOT_INTERRUPTED`, `RECOVERY_RESUME_MISMATCH`, `RECOVERY_APPROVAL_REUSED`, `CONTRACT_MISMATCH`, `SOURCE_CHANGED`; `RECOVERY_RECORD_UNAVAILABLE` when a plan has no finished ledger entry), so no synthetic recovery record exists to relabel. The evidence is written once to `.runs/release/preview/act-run-recovery-<interrupted artifact>.json` (`RECOVERY_RECORD_EXISTS` otherwise), with identifiers, hashes and times only, together with the admission manifest record that cites it. It starts no engine and reads no cloud.

### Channels: the terminal or the console, never both

A workflow runs wholly in the `CLI` channel (a person at the terminal) or the `UI` channel (a person in the console wizard, `src/cli/ui-channel.ts`). The calling code sets it (`ApplyCliDeps.channel`, default `CLI`; the driver's `SealRequest.channel` and `ApplyRequest.channel`), never a flag, file or environment variable. It is a field of the sealed plan, of the artifact hash (`computeArtifactSha256`) and of the review bundle, so editing it breaks the hash (`ARTIFACT_TAMPERED`) and a record without it is `ARTIFACT_INVALID`. `approve` and `apply` refuse with `CHANNEL_MISMATCH` (exit 2) when their channel differs from the plan's: `approve` before it asks anything, `apply` before the final question, and the driver again before any approval is consumed. Nothing is spent by that refusal; the same sealed plan and approvals work in the right channel.

The UI channel changes who may answer a phrase, not what is checked. The adapter asks exactly the phrases the CLI asks (target, `RUN PROJECT CODE`, `EMBED STATE_WRITE <ENV>`, `APPROVE ...`, `APPLY ...`) and answers none of them: a dialog waits for the person, one at a time, and a timeout (10 minutes) or a cancel ends the command at its own mismatch check, so nothing runs and nothing is spent. Console requests need the session token printed at console start, a same-origin `Origin` and `Host`, a JSON body under 16 KB, and no CORS; the token is compared in constant time, is never in a page, URL, response or log, and ends with the process. The approver key stays a file, checked by `readApproverKey` exactly as at the terminal.

### The review bundle

`seal` also writes a review bundle beside the sealed plan, at `<sealed plan path>.review.json` (mode 0600), and prints its path. It holds `artifactSha256`, `planSha256`, `manifestHash`, `releaseIdentity`, `environment`, `target`, `channel`, `engineVersion`, `policyVersion`, `contractSha256`, `sourceCommit`, `createdAt`, `changes`, `changesSha256` and `provenance`. It holds no plan bytes and no plan, state or variable values, so it is not secret and the operator can send it to approvers on any channel.

`approve` reads only that file. It checks the exact field set, recomputes `changesSha256` and the artifact hash from the bundle's fields with the same function the sealer uses (`computeArtifactSha256`), and refuses on any mismatch (`ARTIFACT_TAMPERED`) or malformed field (`ARTIFACT_INVALID`) before it asks anything. It then shows the changes, the target and the preview provenance, and the approver types the environment and the first 12 hex characters of the artifact hash. A bundle that was edited cannot get a signature for another plan, because the change list and target are inside the hash. What the check does not prove is that the vault holds a plan with that hash; if it does not, `apply` refuses (`ARTIFACT_INVALID`) and the approval is wasted, not misused. The approver reads a change list, not the plan; the apply re-derives the list from the plan bytes (see "Plaintext on disk").

### What the change list shows

One list, derived in one place by the engine (Terraform: from `terraform show -json`; CDK: from `describe-change-set`) and bound by `changesSha256` into the artifact hash, so the seal, the review bundle, `approve` and `apply` all show and hash the same thing. Each line has an action, an address and a type. For Terraform it also says when a resource is being **imported** (`importing`), **moved** (`previousAddress`, a plan that renames state), or **forgotten** (action `FORGET`: dropped from state while the real resource is left running). Each output whose value changes is a line with address `output.<name>` and type `output` (its name and action only, never its value). Bidi and zero-width control characters (U+200B-200F, U+202A-202E, U+2060-2064, U+2066-2069, U+FEFF) are stripped from addresses and types when the list is derived, so what is hashed is what is shown; a stored list that still has one is `ARTIFACT_INVALID`, and every display strips them again.

### Exit codes

| Code | Meaning | What to do |
| --- | --- | --- |
| 0 | Done. | |
| 1 | Error, and nothing was spent: bad input, no terminal, a wrong confirmation, a stop signal before the engine started, or the engine could not start (`APPLY_FAILED` with "no approval was consumed"). | Fix the cause and run again. |
| 2 | BLOCKED: the contract refused before any action (disabled or unauthorized contract, a changed contract or authorization, kill switch, wrong target, `CHANNEL_MISMATCH`, unverified or insufficient approvals, artifact already applied, engine not qualified, identities, missing promotion evidence, a bundle or sealed plan that does not verify). | Read the code in the message. |
| 3 | SPENT, in two cases. The engine ran and the sealed plan and its approvals are used up, whatever happened (failed, partial, killed, stale, or evidence that could not be written). Or the approvals were consumed and the engine did not start: `KILL_SWITCH_AFTER_APPROVALS` (the switch appeared) or `APPROVALS_SPENT` (the plan file could not be written, or the engine could not be spawned, for example a full disk). Nothing ran, the approvals are gone and the sealed plan is available again. | Read "When an apply fails". After an engine run, never rerun the same files. After either refusal, fix the cause (lift the switch, free the disk) and collect new approvals for the same sealed plan. |

`test/apply-cli.test.ts` pins this mapping.

## The contract is the authorization

The contract (`config/act-pilot-contract.json`, shapes in `config/act-pilot-contract.example.json` for Azure and `config/act-pilot-contract.aws.example.json` for AWS) names the provider (`AZURE`, `AWS` or `GCP`), the engine (`TERRAFORM`, or `CDK` with `AWS` only; any other pairing is `CONTRACT_INVALID`; `BICEP` with `AZURE` only, admitted for DEV only (owner decision E2): a Bicep contract needs `"enabledEnvironments": ["DEV"]` and each target adds `resourceGroup` and `location`, see `config/act-pilot-contract.azure-bicep-dev.example.json` and `docs/act-pilot-bicep.md`; `GCP` with `TERRAFORM` only, admitted for DEV only (owner decision 6481421924): a GCP contract needs `"enabledEnvironments": ["DEV"]` and each target names `projectId`, `region` and an optional `parent`, see "GCP" below; the planned GCP API-native path is `NOT_IMPLEMENTED` until its lane lands; `config/act-pilot-contract.aws-cdk.example.json` shows the CDK shape), and for DEV, QA and PROD the account fields and backend its spec defines (different pairwise in account and backend, compared case-insensitively; for CDK the backend is the stack name, which may repeat because the account differs, the workspace is `default`, and each target adds `capabilities`, see "CDK"), the required approvals (DEV at least 1, QA at least 1, PROD at least 2), the approval lifetime, the kill switch path, the approver allowlist (id, Ed25519 public key, environments), and `authorize`.

`authorize` is the ACT switch (owner decisions of 2026-10-27, issue #39, "Unpin the ACT decision"; it replaces the old `config/act-pilot-contract.sha256` pin and `./alz apply pin`, which are removed with no fallback). It is default deny: an object keyed by environment, each listing the operations ACT may run there, from `APPLY`, `CLEANUP` and `REMOVE`, for the contract's own provider, engine and that environment's account. For example `"authorize": { "DEV": ["APPLY", "CLEANUP"] }`. Only environments the contract enables may appear. Absent or empty means ACT is disabled (`ACT_DISABLED`), which is how the repository ships (there is no contract at all); an operation it does not list for the environment is `ACT_NOT_AUTHORIZED`. A Terraform contract never authorizes CDK, nor the reverse, and each engine has its own qualification.

**Cleanup and removal follow the contract committed now** (review of #313, N3). A cleanup proposal keeps the run's own contract hash (the one its apply ran under, which binds the run's account, backend and workspace) and binds, besides, the current committed contract and its `CLEANUP` entry. So revoking `APPLY` while keeping `CLEANUP`, or adding `CLEANUP` after an APPLY-only run, never strands a run's cleanup; an edit of the contract after the proposal still refuses it (`ACT_AUTHORIZATION_CHANGED`) before anything is consumed. Removal of a run's working files is authorized the same way, by the current contract's `REMOVE` entry. The current contract's target for the environment must still be the run's exact target: the sealed plan and the apply evidence carry `targetSha256` (provider, every account field including tenant and region, backend and workspace), and `propose-cleanup`, `approve`, the cleanup gate, the late re-check and the removal commands refuse any move (`TARGET_NOT_IN_CONTRACT`); only the `authorize` entry may differ. The proposal output and the approval preview show the target fields (tenant, region). For CDK the cleanup also acts only on the run's own stack, by the stack id its blueprint recorded (`CLEANUP_STACK_NOT_IN_CONTRACT`).

There is no hash to compute or paste. The product derives two hashes itself: the contract's canonical SHA-256, and the hash of the authorizing entry (provider, engine, environment, account and operations). Both are sealed into every plan and so into the artifact hash every approver signs; a cleanup proposal carries both the same way; `approve` refuses to sign under a different contract or entry; the driver derives both again at the gate and right before anything is consumed and refuses with `ACT_AUTHORIZATION_CHANGED` if either changed; the apply and cleanup evidence record them under `decisions` (AUTHORIZED, READY, EXECUTE); the removal record carries the `REMOVE` decision and both hashes; and the live record that release admission reads carries the entry's hash, which must equal the candidate contract's APPLY entry for that environment. A contract that states any key twice is refused (`CONTRACT_INVALID`), so the reviewed text cannot hide a second `authorize`. So editing the contract (another region, tenant, approver, operation or any other field) means a new seal and new approvals, and the evidence shows which contract and entry ran.

To enable the pilot, change a target or an approver, or disable it:

1. Edit `config/act-pilot-contract.json` by hand. To enable, set `enabled` to `true` and add the `authorize` entry the owner decided; to disable, empty `authorize` (or set `enabled` to `false`). `./alz apply contract-check --file` checks a draft offline.
2. Commit it in one reviewed change. Reviewers check the targets, the `authorize` entry and each approver's key against what the owner supplied. Every command that seals, proposes or runs a change (seal, qualify, apply, propose-cleanup, cleanup, propose-removal, remove-workspace) refuses a checkout with uncommitted changes, and also one whose contract bytes differ from the committed file (a skip-worktree, assume-unchanged or locally excluded edit), so an edit nobody committed never runs.
3. `./alz apply status --environment DEV` shows AUTHORIZED (each entry and its hash), READY and the per-run APPROVED requirement; the console's pilot status block shows the same.

No product code path, flag, environment variable or agent writes the contract (`test/apply-contract.test.ts`), and the console reaches `src/apply` only through `src/cli/ui-channel.ts`, which has no writer either. The kill switch below still stops everything at once, independently of `authorize`. Paths are anchored to the repository root found from the module, never to the working directory. Review makes a change visible; it does not stop the operator described above.

## Canary allowlist

Owner decision E1: each execution path names, in the same reviewed contract, the exact resource types and counts an APPLY may create, and everything else is refused. There is no other policy file. Each target takes an optional `canary`:

```json
"targets": {
  "DEV": {
    "accountId": "111111111111", "region": "us-east-2", "backend": "examplefake-dev-state/pilot/dev.tfstate", "workspace": "default",
    "canary": { "resources": [{ "type": "aws_cloudwatch_log_group", "count": 1 }] }
  }
}
```

- **Shape.** `resources` is a list of 1 to 50 entries. Each entry has `type`, `count` and, optionally, `retain`; no other key at any level is accepted. `type` is one exact resource type in the engine's own naming, and each type may appear once. For Terraform that is the provider schema name (`aws_cloudwatch_log_group`, `azurerm_virtual_network`). For CDK it is the CloudFormation type (`AWS::Logs::LogGroup`). A wildcard or a pattern never matches the type rule. `count` is an integer from 1 to 10,000. An entry may also carry `"retain": true` (see below). Anything else is `CONTRACT_INVALID`. An engine with no type rule yet takes no canary.
- **The examples.** AWS Terraform names 1 `aws_cloudwatch_log_group`. Azure Terraform names 1 `azurerm_virtual_network`. AWS CDK names 1 `AWS::Logs::LogGroup` and 1 `AWS::CloudFormation::WaitConditionHandle` with `"retain": true`. The second CDK resource is a no-cost sentinel: a CDK cleanup never empties a stack (`CLEANUP_WOULD_EMPTY_STACK`), so the stack needs one resource the cleanup keeps.
- **`retain: true`.** The type is created at APPLY and intentionally kept at CLEANUP. Only a small reviewed list of no-cost, inert sentinel types may carry it. Today that is exactly `AWS::CloudFormation::WaitConditionHandle` (`RETAINABLE_CANARY_TYPES`, `src/apply/canary.ts`). `retain` on any other type, or any value but `true`, is `CONTRACT_INVALID`. At cleanup, a run-created resource of a retained type, within the declared count, is kept as `CANARY_RETAINED` by the pilot owner. The proposal lists it with its reason and names the retained sentinel among its risks. The leftover check records it as `INTENTIONALLY_RETAINED` on the basis `RETENTION_DECISION`, never as an unreviewed type, so the lifecycle report can pass and shows the retention. More run-created resources of a retained type than the declared count make no proposal (`OWNERSHIP_AMBIGUOUS`). The seal's exact counts already keep that from happening. Without `retain`, the sentinel is held as `TYPE_UNREVIEWED`, as before, and the leftover check stays `INCOMPLETE`. The owner confirmed this sentinel on 2026-10-28 (#39, 6480066863): the CDK canary's `AWS::CloudFormation::WaitConditionHandle` stays in the stack with `retain: true`, and cleanup keeps it as `CANARY_RETAINED` on the basis `RETENTION_DECISION`.
- **Bound like the target.** The canary is part of the target hash (`pilotTargetSha256`), and so of the contract hash. Every sealed plan, approval, cleanup proposal and evidence record binds both. Changing the allowlist is a target change: a sealed plan made under the old allowlist is refused, and a run's cleanup or removal is refused under a contract whose allowlist for that environment changed (`TARGET_NOT_IN_CONTRACT`). A target that names no canary hashes exactly as before.
- **`CANARY_ALLOWLIST_MISSING`.** `authorize` names `APPLY` for an environment whose target has no `canary`. This is checked wherever `authorize` is evaluated for `APPLY`: seal, qualify, approve, apply, readiness and the live record. It fails closed, and nothing runs. `CLEANUP` and `REMOVE` do not need a canary.
- **`RESOURCE_NOT_IN_CANARY`.** The engine's own artifact does anything but create exactly the allowlist. The reason names the resource address, its type, its action and the counts, never a value. The judge runs at the seal, at the qualification plan, and again when an apply derives the change list from the sealed bytes before any approval is consumed.
  - **Terraform** reads `terraform show -json` of the plan file. Every managed `resource_changes` entry must have actions exactly `["create"]`. It must not be an import or a move, and its type must be listed. The managed entries must number exactly the listed count per type. Refused: an update, a delete, a replace (`["delete","create"]` or `["create","delete"]`), a `forget`, a managed `no-op`, an unknown action, an extra or missing resource, a wrong count, and an unlisted type (an `aws_iam_role` or an `azurerm_role_assignment` included). A data source entry may be `["read"]` or `["no-op"]` and nothing else; which data sources may be read stays the provider's reviewed list (`PROVIDER_DATA_SOURCE_NOT_IN_CONTRACT`). Output changes are not resources and are not judged here. The provider, denied-type, provisioner and unsafe-construct checks run first and are unchanged.
  - **CDK** judges twice. First, before any change set exists, the synthesized template's `Resources` must be exactly the listed types and counts. Then CloudFormation's change set must consist only of `Add` changes (CREATE, not an import) of listed types, matching the counts. A Modify (UPDATE, REPLACE, REPLACE_CONDITIONAL or UNKNOWN), a Remove, a Dynamic or an Import is refused. An action the reader does not know is refused earlier as `CHANGE_ACTION_UNKNOWN`. The existing CDK judge does not strip `AWS::CDK::Metadata` (it reads every resource the template declares), so a template with CDK version reporting is refused unless the allowlist names that type. Synthesize with version reporting off. A refusal after the change set was created leaves it unexecuted for a person to clear, as any seal refusal after creation does.
- **Brownfield previews (dropped by the owner, 2026-10-28).** Every seal is admitted as APPLY, so an environment authorized for APPLY seals creates only. A brownfield plan, one that updates or adopts a pre-existing resource, is refused at seal with `RESOURCE_NOT_IN_CANARY`. So `./alz apply preview-evidence` cannot produce brownfield preview evidence under E1. The owner dropped these gates from this release (#39, 6480066863): `preview:terraform-aws-brownfield`, `preview:terraform-azure-brownfield`, `preview:cdk-aws-brownfield` and `preview:bicep-azure-brownfield`, and `preview:terraform-gcp-brownfield`. The GCP brownfield preview is dropped; GCP Terraform ACT and GCP API-native ACT are in scope for this DEV release (#39, 6481421924). `config/release/scope.json` excludes them, `config/release/status.json` lists them as `OUT_OF_SCOPE`, the evidence runner reports them `OUT_OF_SCOPE`, and the admission review refuses a record for one (`RELEASE_RECORD_FOR_OUT_OF_SCOPE_GATE`). No preview gate is in this release's scope. The producer is unchanged, and its own rules are still tested on the record such a seal would have made (`test/apply-preview-evidence.test.ts`). Bringing a gate back is the owner's scope change.
- **Cleanup is not create-only.** A cleanup's destroy plan (Terraform) or removal change set (CDK) is not judged against the allowlist. It keeps its own rules: only run-owned resources, exactly the approved list. The one thing the allowlist adds at cleanup is `retain`, above.
- **Why the counts are exact.** "At most" would let a plan create fewer resources than reviewed and still pass. A missing resource usually means a module changed, a count or `for_each` resolved differently, or a resource was replaced by another. An exact count makes the reviewed allowlist the whole statement of what the apply does: one extra resource, one fewer, or one changed existing resource are each a refusal the owner reads, never a silent difference. It also means an apply runs only against a fresh workspace or stack. A second apply over existing resources plans updates or no-ops, and those are refused.

## Promotion: DEV, then QA, then PROD

Each stage has its own sealed plan, artifact hash and approvals, and an approval signed for one environment is `APPROVAL_MISBOUND` for another. DEV needs no earlier evidence. QA needs a successful, encrypted DEV apply record for the same release identity. PROD needs a successful QA apply record for the same release identity, and DEV evidence alone is refused (`PROMOTION_EVIDENCE_MISSING`). Identity checks are per environment: each environment's credentials must match its own contract target, and the account in an AWS role ARN is the environment's own. `qualify` runs only against the DEV target; QA and PROD are not qualified separately and are refused.

## Identities

Each engine needs its own set of separate principals (`EngineSpec.identities`): four for Terraform, three for CDK. They are set as `ALZ_<IDENTITY>_<VAR>` in the environment of the person running the command. None inherits the operator's credentials and none falls back to another (APPLY is never a state fallback). The driver refuses if one the engine needs is missing; if one it does not need is configured (a privileged credential nothing uses: STATE or STATE_WRITE with a CDK contract, CHANGESET with a Terraform contract; `IDENTITY_NOT_CONFIGURED`); if two share a principal-like value (client id, role ARN, secret, token file, client certificate or config directory) even under different variable names, compared after normalizing (case, padding, path spelling, symlinks and hard links); if any carries a variable that would let a child fall back to a CLI, instance or ambient credential; if a principal-like value equals the operator's own ambient variable of the same kind; or if any names an account other than the contract's for that environment (the identities that write, `APPLY`, `STATE_WRITE` and `CHANGESET`, must set every such variable). The variable names and the fallback list are the provider's (see "Providers"), and the other cloud's credential variables are on it. Apply children receive none of the dropped variables at all. A token file copied to a second path, or linked to after the check, is not detectable.

| Identity | Engine | Used for |
| --- | --- | --- |
| `DISCOVERY` | both | Terraform: plan, during seal and qualify. CDK: `describe-stacks` of the target stack at seal |
| `STATE` | Terraform | Reading state and its serial, and taking the state lock |
| `STATE_WRITE` | Terraform | `init` and workspace selection (state write and lock) |
| `APPLY` | both | Terraform: the provider writes in `terraform apply`. CDK: `execute-change-set`, the stack polls and `cancel-update-stack` |
| `CHANGESET` | CDK | `create-change-set`, its wait and `describe-change-set` (also at apply, to prove the change set is still the sealed one). It has no way to execute |

## Providers

The requirements on this page hold for any provider; the provider's facts live in one spec per provider, chosen by the contract's `provider` id (`src/apply/provider.ts`; `AZURE` in `src/apply/providers/azure.ts`, `AWS` in `src/apply/providers/aws.ts`). A contract naming a provider with no spec is `CONTRACT_INVALID`. There is no provider flag on any command: `./alz apply` follows the reviewed contract. A spec owns:

- the target shape and its validation, and the account identifier a `ResolvedTarget` carries as `account`;
- the identity checks: the variables that would let a child fall back to a CLI, ambient or other-cloud credential, the operator's own credential variables an identity may not equal, and the variables that must name the contract's account;
- the partial backend configuration `init` saves for STATE_WRITE, the check that the backend `init` saved equals the contract's, and the backend settings the apply process fills in (`filledAtApply`);
- the backend type the product pins (`backendType`: `s3` for AWS, `azurerm` for Azure) and the contract's backend location (`backendLocation`), under the backend rule below;
- the checks on the provider blocks in `terraform show -json`;
- the account fields and principals that bind qualification evidence to the DEV target.

**The backend rule (the backend pin).** The project's own backend block is never read or judged. `init` already sends credentials to whatever a backend names, so the pilot makes sure `init` can only build the contract's backend (docs/act-pilot-backend-pinning.md, SYNTHETIC proof). In the frozen work copy, before any `init` (seal, qualification, apply and cleanup alike):

1. Any root entry named `override.tf`, `override.tf.json`, `*_override.tf` or `*_override.tf.json`, in any letter case and whether file, folder or link, is refused by name (`BACKEND_OVERRIDE_NOT_ALLOWED`). So is any `.terraform`, `terraform.tfstate`, `terraform.tfstate.backup` or `terraform.tfstate.d` (`WORKSPACE_STATE_NOT_ALLOWED`); the snapshot already refuses state files, and this is the second layer. Every Terraform child also gets `TF_DATA_DIR=.terraform` from the apply profile, so the data directory is always `init`'s own fresh one. Both codes are mapped like every `_NOT_IN_CONTRACT` code: nothing is spent.
2. The product writes exactly one override file, `zzzz_alz_backend_override.tf`, containing `terraform { backend "<type>" {} }` and nothing else. Terraform merges override files last and replaces the backend wholesale (it also drops any `cloud` or `state_store` block), even when other files fail to parse. Every setting comes only from the product's `-backend-config` file: the contract's location (`backendLocation`) at a seal, plus the STATE_WRITE settings at an apply, a cleanup, a qualification, or a seal that embeds them. `-migrate-state` and `-reconfigure` are never passed. The file is bound like a project file: after it is written, every bound check expects it byte for byte, and the plan file Terraform writes embeds the configuration it was planned with.
3. Any `init` exit other than 0 stops the run, and after `init` the saved backend's type and settings must still equal the contract's (`BACKEND_NOT_IN_CONTRACT`).

The child environment stays sanitized: it starts empty, so no `TF_CLI_ARGS*`, `TF_WORKSPACE`, user `TF_DATA_DIR` or user `TF_CLI_CONFIG_FILE` reaches it (an `ALZ_<IDENTITY>_` variable naming one is refused).

The generic modules (contract, identities, driver, seal, evidence, the CLI) hold each requirement's one enforcement point and call the spec for the facts. Every apply child's Terraform profile (`TERRAFORM_APPLY_PROFILE`) drops what a spec refuses: `TF_CLI_CONFIG_FILE`, `TF_PLUGIN_CACHE_DIR`, `AZURE_*`, the static AWS credentials (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_PROFILE`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_CONFIG_FILE`), and `AWS_ENDPOINT_URL` (a web identity token goes wherever an endpoint points, and a host allowlist cannot tell an attacker's `*.amazonaws.com` API Gateway or load balancer host from AWS), `AWS_CA_BUNDLE` and `AWS_DEFAULT_REGION`, and sets `AWS_EC2_METADATA_DISABLED=true` so no child can fall back to an instance profile. The other profiles are unchanged.

### Azure (`AZURE`, Terraform with the AzureRM backend)

Target: `tenantId`, `subscriptionId`, `backend` (`<storage-account>/<container>/<key>`), `workspace`; `account` is the subscription id. Variables: `ARM_CLIENT_ID`, `ARM_TENANT_ID`, `ARM_SUBSCRIPTION_ID`, `ARM_USE_OIDC` and `ARM_OIDC_TOKEN_FILE`, for example `ALZ_APPLY_ARM_CLIENT_ID`. The tenant and subscription must be the contract's. Refused as fallbacks: `AZURE_*`, `ARM_USE_*` other than `ARM_USE_OIDC`, `ARM_MSI_*`, `ARM_CLIENT_CERTIFICATE*`. A per-identity `ARM_CLIENT_SECRET` is accepted (it is that identity's own explicit credential), so "OIDC token file only" is the recommended setup and is not enforced for secrets. Qualification attests the client ids, and the same client ids must be used in every environment.

Provider uses (RB2, review of #322, N3; narrowed by the review of #327, B2): every resource and data source the plan names, in any module, is judged, not only the provider blocks, as on AWS. Its provider must be `hashicorp/azurerm`, the built-in provider (`terraform_data` only) or `hashicorp/random`, `null`, `time` or `tls`, by exact source. A lookalike namespace or host, another cloud, an `http` or `external` reader, and a use whose provider the plan does not name are refused (`PROVIDER_CONFIG_NOT_IN_CONTRACT`). **`azure/azapi` and `hashicorp/azuread` are not admitted in this release** (`PROVIDER_NOT_ADMITTED`, for any use and any provider block): azapi writes any ARM type under any parent and subscription while the change list shows only `azapi_resource`, and azuread mints directory credentials and grants. Admitting either is the owner's reviewed decision, with the subscription and tenant binding extended to its blocks. Types that run code or deploy a template instead of holding a resource are refused (`PROVIDER_TYPE_NOT_ALLOWED`, review of #327, N1 and round 2 B1): `azurerm_virtual_machine_extension`, `azurerm_virtual_machine_scale_set_extension`, `azurerm_virtual_machine_run_command`, `azurerm_arc_machine_extension`, `azurerm_stack_hci_extension`, the two `azurerm_resource_deployment_script_*` types, and the four template deployments (`azurerm_resource_group_template_deployment`, `azurerm_subscription_template_deployment`, `azurerm_management_group_template_deployment`, `azurerm_tenant_template_deployment`), whose one plan row hides arbitrary ARM content, deployment scripts and other subscriptions; and, from a sweep of the full schema (round 3), `azurerm_managed_application`, `azurerm_blueprint_assignment`, the four `*_policy_remediation` types (they deploy deployIfNotExists templates), `azurerm_kubernetes_cluster_extension`, `azurerm_arc_kubernetes_cluster_extension` and `azurerm_kusto_script`. The list was reviewed against the full hashicorp/azurerm 4.81.0 schema, and the project's lock file must pin exactly that version (see "Provider versions are bound to the review").

Data sources (review of #320, N7): only the reviewed ones may be read: `azurerm_client_config`, `azurerm_subscription`, `azurerm_resource_group` and `azurerm_virtual_network` (`AZURE_DATA_SOURCES`). Every other one, of any provider, is refused (`PROVIDER_DATA_SOURCE_NOT_IN_CONTRACT`): that keeps out SAS minting (`azurerm_storage_account_sas`, `azurerm_storage_account_blob_container_sas`), secret reads (`azurerm_key_vault_secret`), the storage account data source with its access keys and connection strings, and `terraform_remote_state`. The read itself happened during the plan; DISCOVERY's roles bound it.

State prerequisites (owner supplies): a storage account and container per environment, with blob versioning and soft delete on, shared-key and SAS access disabled (`bootstrap/azure` does this), and role assignments scoped to that container for STATE and STATE_WRITE and to the target subscription for APPLY. Exact roles are the owner's least-privilege decision.

State authentication is Entra ID only:
- The product's backend file sets `use_azuread_auth = true` for every init (seal, qualification, apply). Init saves the setting and the sealed plan embeds it, so the apply uses it too.
- A saved backend is refused (`BACKEND_NOT_IN_CONTRACT`) when that setting is not `true`, or when it holds any setting the product did not write: a shared key, a SAS token, `resource_group_name`, `lookup_blob_endpoint`, or another endpoint, cloud or credential.
- The STATE_WRITE settings init saved are bound to that identity's actual values, not only to their shapes: a saved `client_id` or `oidc_token_file_path` must be exactly the `ALZ_STATE_WRITE_ARM_CLIENT_ID` or `ALZ_STATE_WRITE_ARM_OIDC_TOKEN_FILE` of the environment that init's backend file was written from, and a saved value with no STATE_WRITE value to match is refused (`BACKEND_NOT_IN_CONTRACT`). The saved `tenant_id` and `subscription_id` must be the contract's.
- `ARM_ACCESS_KEY`, `ARM_SAS_TOKEN` and the environment forms of the switch never reach a Terraform child. `ARM_USE_AZUREAD` on an identity is refused as a fallback. `ARM_STORAGE_USE_AZUREAD` is the azurerm provider's variable, and the Terraform 1.16.4 backend never reads it.
- No resource group is configured. The backend needs one only to list shared keys through ARM, or for `lookup_blob_endpoint`. With Entra ID it builds the blob endpoint from the storage account name, so the contract's `<storage-account>/<container>/<key>` is the whole location.

The emulated G1b run (`docs/act-pilot-simulation.md`, SYNTHETIC/EMULATED) shows what real init saves. Entra ID token exchange against Azure is proven only in the supervised DEV qualification.

### GCP (`GCP`, Terraform with the gcs backend; DEV only)

Admitted in code for DEV only (owner decision 6481421924 on issue #39). The full design is `docs/act-pilot-gcp-terraform-g0.md`; the spec is `src/apply/providers/gcp.ts`. In short:
- **Target:** `projectId`, `region`, `backend` (`<bucket>/<prefix>`), `workspace`, an optional `parent` (`organizations/<n>` or `folders/<n>`; a DISCOVERY readiness check with no authority) and the canary allowlist. Every field, `parent` when stated included, is in the run's target hash. `account` is the project id. The contract must state the DEV-only scope; QA and PROD are refused.
- **Canary (owner decision E1):** an APPLY creates exactly what the target's `canary` names. The GCP canary is one `google_pubsub_topic` (`{ "resources": [{ "type": "google_pubsub_topic", "count": 1 }] }`); a subscription, an IAM member, binding or policy of the topic or the project, a second topic, or any update, delete or import is `RESOURCE_NOT_IN_CANARY`.
- **Identities:** four workload identity federation principals, each `ALZ_<IDENTITY>_GOOGLE_APPLICATION_CREDENTIALS` (an `external_account` file-source configuration) with `GOOGLE_IMPERSONATE_SERVICE_ACCOUNT`, `GOOGLE_PROJECT` and `GOOGLE_REGION`. Any other Google, gcloud, metadata or other-cloud variable on an identity is refused by name, and so is a Google variable on an AWS or Azure identity. Only the pilot's Terraform apply profile hands a child those four variables; the general `terraform` profile hands none. Every pilot Terraform child gets `GCE_METADATA_HOST=metadata.invalid` (a reserved name that never resolves; the Go auth library has no switch that disables the metadata server), `GCE_METADATA_IP` likewise and `NO_GCE_CHECK=True`, so the metadata server is never a credential fallback.
- **Backend:** the product pins `backend "gcs" {}`. The saved backend is an allowlist (`bucket` and `prefix`, each compared on its own, and `credentials` and `impersonate_service_account` only when they are STATE_WRITE's own values); anything else, a token, an endpoint or an encryption key among them, is refused (`BACKEND_NOT_IN_CONTRACT`).
- **Provider:** `hashicorp/google` at exactly the reviewed 8.9.0 with HashiCorp's own package hashes (`src/apply/lockfile.ts`; a lock or an init selection of any other version is `PROVIDER_VERSION_NOT_REVIEWED`, another hash `PROVIDER_HASH_NOT_OFFICIAL`), and the providers that reach no cloud; `google-beta`, another registry host and any use whose provider is unnamed are refused. Credentials, tokens, impersonation, scopes, endpoints and billing overrides are refused in a google block; `default_labels` must be set; a constant `project` must be the contract's. Types that run code or deploy a template at apply (`GCP_DENIED_TYPES`: Deployment Manager, Infrastructure Manager, Cloud Functions, Cloud Run jobs, Cloud Build triggers, Composer, Dataflow, Dataproc and BigQuery jobs, OS Config, GKE Hub features and others) are `PROVIDER_TYPE_NOT_ALLOWED`. Only the reviewed data sources `google_project` and `google_pubsub_topic` may be read, each naming the contract's project as a constant (`project_id` and `project`); any other data source, an unstated project or an expression is `PROVIDER_DATA_SOURCE_NOT_IN_CONTRACT`, and another project `PROVIDER_ACCOUNT_NOT_IN_CONTRACT`.
- **Observation and cleanup:** DISCOVERY reads through Google's REST APIs in process (`GCP_REST`, with its own leftover bases `GCP_REST_ABSENT` and `GCP_REST_PRESENT`); the only reviewed cleanup leaf is `google_pubsub_topic`; the state bucket in every identifier form, identities, containers and every other type are kept (`src/apply/cleanup-gcp.ts`).
- **Not yet:** the `act:gcp-terraform` release path and its journey row, the driver-level emulated run (S6b) and every live gate.

### AWS (`AWS`, Terraform with the S3 backend)

The AWS formats, the S3 backend and aws provider attribute names, and the Terraform features named here are from memory and unverified against AWS or Terraform documentation, which was unreachable when this was written; a comment next to the validators says so. A rule that is wrong refuses a good value and is corrected in a reviewed change. Nothing here has run against a real Terraform or a real AWS account.

- **Target:** `accountId` (12 digits), `region` (like `us-east-1`), `backend` (`<bucket>/<key>`; bucket 3 to 63 characters of lowercase letters, digits, hyphens and dots, starting and ending with a letter or digit), `workspace`. `account` is the account id. The three environments differ pairwise in account and backend.
- **Identities:** four distinct IAM roles assumed through web identity, no static keys. Per identity: `ALZ_<IDENTITY>_AWS_ROLE_ARN` (`arn:aws:iam::<account>:role/<name>`), `ALZ_<IDENTITY>_AWS_WEB_IDENTITY_TOKEN_FILE` and `ALZ_<IDENTITY>_AWS_REGION`. Each role ARN's account id and each region must be the environment's own contract values. Role ARNs are compared case-insensitively, trimmed, and as account plus role name (a role name is unique in its account whatever the ARN's path, so `role/name` and `role/team/name` are one role); token files by path, symlink and inode, like every other principal, and each must be an absolute path (a relative one means the runner's directory to the check and the work directory to the child). Refused on any identity: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_SECURITY_TOKEN`, `AWS_PROFILE`, `AWS_DEFAULT_PROFILE`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_CONFIG_FILE`, `AWS_CONTAINER_*`, `AWS_EC2_METADATA*`, `ARM_*` and `AZURE_*`; and any role ARN or token file equal to the operator's own ambient `AWS_ROLE_ARN` or `AWS_WEB_IDENTITY_TOKEN_FILE`. `AWS_REGION` is checked against the contract wherever it is set and must be set for STATE_WRITE and APPLY. Under an Azure contract `AWS_*` is refused the same way.
- **Backend:** S3 with native locking (`use_lockfile = true`; no DynamoDB table). The partial backend configuration `init` saves for STATE_WRITE holds the contract's `bucket`, `key` and `region`, `use_lockfile = true`, and `assume_role_with_web_identity` with the STATE_WRITE role ARN and token file path (neither is a secret). What `init` saved is an allowlist (review of #320, N3): the contract's `bucket` and `key`, each compared on its own, its `region`, `use_lockfile = true`, and, when saved, an `assume_role_with_web_identity` holding exactly STATE_WRITE's own `AWS_ROLE_ARN` and `AWS_WEB_IDENTITY_TOKEN_FILE`; every other setting must be absent or `null` (`BACKEND_NOT_IN_CONTRACT`). The project's own backend block, whatever it says, is replaced by the product's `backend "s3" {}` override (the backend rule above). What the plan embeds is the seal-time `init`'s `bucket`, `key`, `region` and `use_lockfile` from the product's backend file, which must be the contract's (below); the backend credentials stay null, and the apply process fills them from its own environment, which is the APPLY role (`filledAtApply`).
- **Provider blocks:** only `hashicorp/aws` and the providers that reach no cloud (`random`, `null`, `time`, `tls`) may appear in the plan (`PROVIDER_CONFIG_NOT_IN_CONTRACT`). In any `aws` provider block, whether constant or an expression: no `access_key`, `secret_key`, `token`, `profile`, `shared_credentials_files`, `shared_config_files`, `endpoints`, proxy, `custom_ca_bundle`, `ec2_metadata_service_endpoint*`, `insecure` or `skip_*`, and no `web_identity_token` or `web_identity_token_file` in `assume_role*` (`PROVIDER_CONFIG_NOT_IN_CONTRACT`). A constant `allowed_account_ids` must include the contract's account, a constant `forbidden_account_ids` must not, and a constant `role_arn` in `assume_role` or `assume_role_with_web_identity` must be the APPLY identity's own role, and in the contract's account (`PROVIDER_ACCOUNT_NOT_IN_CONTRACT` for another account). Expressions for an account or a role are not checkable from the plan and are not judged. A constant `region` is not judged: a second region is ordinary and the account is what the credentials bound.
- **Provider uses and data sources (review of #320, N1 and N2):** every resource and data source the plan names, in any module, is judged, not only the provider blocks: its provider must be one of the allowed ones, and a use whose provider the plan does not name is refused (`PROVIDER_CONFIG_NOT_IN_CONTRACT`; `data.http` from `hashicorp/http` is refused this way). Only the reviewed data sources may be read: `aws_caller_identity`, `aws_region`, `aws_partition`, `aws_default_tags`, `aws_iam_policy_document` and `aws_cloudwatch_log_group` (`AWS_DATA_SOURCES`); every other one, of any provider, is refused (`PROVIDER_DATA_SOURCE_NOT_IN_CONTRACT`), which keeps token and secret readers (`aws_ecr_authorization_token`, `aws_eks_cluster_auth`, `aws_secretsmanager_secret_version`, `aws_ssm_parameter`, `aws_redshift_cluster_credentials`, `aws_api_gateway_api_key`, `aws_s3_object`, `aws_instance` with its `password_data`, `aws_glue_connection` and the like) out of the sealed plan and the state. A type joins the list by review. A use whose mode the plan leaves unsaid is judged as a data source. Managed types that run code or deploy a template instead of holding a resource are refused (`PROVIDER_TYPE_NOT_ALLOWED`, review of #327, N1 and round 2 B1): `aws_lambda_invocation` (it invokes a function at apply, as APPLY), `aws_ssm_association` (it runs a document on instances), `aws_cloudformation_stack`, `aws_cloudformation_stack_set`, `aws_cloudformation_stack_set_instance`, `aws_cloudformation_stack_instances`, `aws_servicecatalog_provisioned_product`, and every other stack container family the cleanup keeps (`src/observe/aws-containers.ts`: Serverless Application Repository, SageMaker projects, Proton, Elastic Beanstalk environments, SSM Quick Setup, DataZone environments, Control Tower), because one plan row hides a whole template; and, from a sweep of the full schema (round 3), `aws_imagebuilder_image`, `aws_sagemaker_training_job`, `aws_sagemaker_hyper_parameter_tuning_job` and `aws_sagemaker_labeling_job`, which run code at apply. The list was reviewed against the full hashicorp/aws 6.68.0 schema, and the project's lock file must pin exactly that version (see "Provider versions are bound to the review"). The CDK engine is separate and has its own judge. At apply and cleanup these refusals, and a refused Terraform construct, surface by the judge's own code (`TARGET_NOT_IN_CONTRACT` or `ARTIFACT_INVALID`, naming it), not as a failed plan.
- **The refusal comes after the plan ran.** A data source is read while `terraform plan` runs as DISCOVERY, so the refusal keeps its result out of the sealed plan and the state but cannot undo the read. The planning identity's IAM is what bounds the read itself: DISCOVERY must never hold `lambda:InvokeFunction` (an `aws_lambda_invocation` data source runs a function at plan time) or any secret or data read. `bootstrap/aws` grants it neither: `discovery-policy.json` does not list `lambda:InvokeFunction`, none of the three accepted managed policies (ViewOnlyAccess, SecurityAudit, ReadOnlyAccess) is meant to grant it, and the DISCOVERY inline policy denies `lambda:InvokeFunction`, `lambda:InvokeAsync`, `lambda:InvokeFunctionUrl` and `lambda:InvokeWithResponseStream` on every resource whatever the managed policy grants (`denyAlways`, review of #322, N4). No data-read exception can lift that deny.
- **Qualification:** the evidence binds the DEV `accountId`, `region`, backend and workspace, the attested STATE_WRITE and APPLY role ARNs (trimmed, lowercase), and the terraform binary hash, with the usual 30 day limit. A role ARN names its account, so QA and PROD cannot use DEV's roles: the role binding applies to DEV runs, and each QA and PROD run is bound by its own account check instead.
- **Prerequisites (owner supplies):** per environment, an S3 bucket with versioning on; the lock file is an object next to the state object, so STATE needs read access and permission to create and delete the lock object, STATE_WRITE needs state object write as well, and APPLY needs the provider write permissions in that account. An IAM OIDC identity provider per account and a trust policy per role that lets only that identity's token assume it. Exact policies are the owner's least-privilege decision.

## Engines

The same split holds for the engine. One spec per engine, chosen by the contract's `engine` id (`src/apply/engine-spec.ts`; `TERRAFORM` in `src/apply/engines/terraform.ts`, `CDK` in `src/apply/engines/cdk.ts`), owns what only that engine knows:

- the providers it is valid with (Terraform: either; CDK: AWS only), the identities it needs (Terraform: DISCOVERY, STATE, STATE_WRITE, APPLY; CDK: DISCOVERY, CHANGESET, APPLY) and the two whose principals qualification attests;
- how the sealed artifact is produced from a request (Terraform: init, workspace, `plan -out`, with `show -json` read only for the redacted change list; CDK: a CloudFormation change set that is created and not executed) and how the change list is derived again from the artifact at apply;
- how the exact sealed artifact is prepared and run (Terraform: `apply <planfile>`; CDK: `execute-change-set` for the sealed change set), how the run ends is classified, and what it leaves for a person to recover (Terraform: the first `Error:` match and the state serial, `errored.tfstate` and `crash.log`; CDK: nothing is written, the stack is the record), with the message for each unsuccessful outcome;
- the argument allowlist and the adapters whose digest a qualification record pins, the binary hash qualification evidence binds, and what the CLI tells the person (the project-code warning, the attestation text);
- optionally its own qualification run (CDK: read-only, no change set) and the shape of a target's `backend` and extra fields.

The driver's ordering of gates, the ledger, approvals, promotion, evidence, the kill switch and cleanup stay engine-agnostic and call the spec. A contract naming an engine with no spec, or an engine with a provider it is not valid with, is `CONTRACT_INVALID`, and a manifest that is not the contract engine's project manifest is refused before sealing or applying. `terraform.ts` keeps Terraform's pinned argument lists, digest and outcome classification. The evidence's `authority.mutation` says what the engine did (`TERRAFORM_APPLY_OF_SEALED_PLAN` or `CLOUDFORMATION_EXECUTE_OF_SEALED_CHANGE_SET`). Two field names in the qualification evidence are Terraform-shaped and published, so they keep their names: `terraformSha256` holds the engine binary's hash (the `aws` CLI's for CDK), and `stateWriteClientId` and `applyClientId` hold the two attested principals (CHANGESET's role ARN and APPLY's for CDK).

### CDK (`CDK`, AWS only)

**Every AWS CLI, CloudFormation and CDK fact below is from memory and unverified against AWS documentation, which was unreachable when this was written. No real AWS CLI or CloudFormation has run any of it; the tests use a fake `aws`.** This is the one list of the assumptions; `src/apply/engines/cdk.ts` marks where it relies on one with `UNVERIFIED (n)`. Each is checked against AWS's documentation and a real DEV run before live use. Most fail closed (a refusal or `PARTIAL_REQUIRES_REVIEW`); the ones that may not are named in "Open real-AWS questions".

**Emulated results (SYNTHETIC, not G2).** `test/apply-emulated-cdk.test.ts` is an opt-in test that runs the real pinned AWS CLI 2.38.6 against a local moto CloudFormation. `docs/act-pilot-simulation-cdk.md` records, for each item below, whether that run showed it (VERIFIED (emulated)), or whether moto cannot show it, so it stays UNVERIFIED for the live G2. The run found one defect, now fixed: the CLI prints `null` for a list CloudFormation leaves out of `describe-change-set`, such as `"Capabilities": null`. No item is verified against AWS itself until the owner-supervised DEV run.

1. The AWS CLI v2 subcommands and flags the argument lists use: `cloudformation create-change-set` (`--stack-name`, `--change-set-name`, `--change-set-type`, `--template-body file://...`, `--capabilities`), `wait change-set-create-complete`, `describe-change-set`, `get-template` (`--change-set-name`, `--template-stage Original`), `execute-change-set`, `describe-stacks`, `describe-stack-events`, `cancel-update-stack`, `--region`, `--output json`, `--no-cli-pager`, and `aws --version` printing `aws-cli/<x.y.z> ...`.
2. That the CLI reads `AWS_ROLE_ARN` with `AWS_WEB_IDENTITY_TOKEN_FILE` for its credentials (as the Terraform AWS provider is assumed to), that it honors `--region` for the STS call, and that the apply profile's `AWS_EC2_METADATA_DISABLED` switches the instance metadata fallback off.
3. The JSON they print (a change set that holds a `NextToken` after the CLI's own pagination is `CHANGE_SET_TRUNCATED`; one with no changes is `NO_CHANGES_TO_APPLY`): `Id` and `StackId` from create; `ChangeSetId`, `StackId`, `StackName`, `Status`, `ExecutionStatus`, `Capabilities`, `Parameters[]` and `Changes[].ResourceChange` with `Action` (`Add`, `Modify`, `Remove`, `Import`, `Dynamic`), `LogicalResourceId`, `ResourceType` and `Replacement` (`True`, `False`, `Conditional`) from describe-change-set; `TemplateBody` from get-template (an object for a JSON template, or a string); `Stacks[].StackId`, `StackStatus`, `EnableTerminationProtection`, `CreationTime`, `LastUpdatedTime`, `RoleARN`, `NotificationARNs` and `RollbackConfiguration`; `StackEvents[].ResourceType` and `Timestamp`; and the template keys `Transform`, `Fn::Transform` and `Fn::ImportValue`.
4. The statuses. For a stack: those named in the code (in progress, updatable, rolled back, failed), that a stack not found is told apart by "does not exist" in the error text, that a `CREATE` change set leaves the stack in `REVIEW_IN_PROGRESS` (and a second seal for it is again `CREATE`), and that creating a change set does not change the stack's status, last change time, role, topics or rollback setting. For a change set: executable when `Status` is `CREATE_COMPLETE` and `ExecutionStatus` is `AVAILABLE` (the brief named this `EXECUTE_AVAILABLE`; no such value is assumed); `EXECUTE_COMPLETE` after a completed execution; still `AVAILABLE` after an execute that CloudFormation refused; and `OBSOLETE` or `UNAVAILABLE` when the stack changed after it was made. The last is an extra only: the apply compares the stack's state itself (below).
4a. That a change set with nothing to change, and one that could not be built, both end `Status: FAILED` with a `StatusReason`, which `wait change-set-create-complete` reports as a non-zero exit. The engine reads the reason once: "didn't contain changes" (or "No updates are to be performed") is `NO_CHANGES_TO_APPLY`, any other `FAILED` is `CHANGE_SET_CREATION_FAILED`, and neither creates anything to execute. The failed change set is left for a person to clear (the pilot has no delete). AWS's documentation says a change set does not guarantee a successful deployment, which is why the apply judges the outcome from the stack and the change set after the execute, not from the change set alone.
5. That `cancel-update-stack` is valid only while the stack is `UPDATE_IN_PROGRESS`, that CloudFormation then rolls back, and that a create cannot be canceled.
6. That `CreateChangeSet` cannot turn termination protection on, so a person enables it after the first create, and the next update is refused until they do.
7. The 51,200 byte limit on an inline template body, and the cloud assembly layout read from `manifest.json`: artifact types `aws:cloudformation:stack`, `cdk:asset-manifest`, `cdk:tree` and `cdk:feature-flag-report`; a stack's `properties.templateFile`, `stackName`, `terminationProtection` and `environment` (`aws://<account>/<region>`, `unknown-account` and `unknown-region` for an environment-agnostic stack); an asset manifest's `files[].source.path` and `dockerImages`; and that a stack without assets lists only its own template as a file asset (the default synthesizer's), which is sent inline instead.
8. That `create-change-set --tags Key=<k>,Value=<v> ...` sets the stack's tags, that `describe-change-set` echoes them as `Tags[].Key/Value`, and that CloudFormation stamps a stack's tags on every resource of the stack whose type takes tags. The engine passes exactly the deletion unit's three tags (`alz-managed-by`, `alz-unit`, `alz-build`; `src/apply/unit.ts`) and refuses any other key, and the seal binds their hash (`tagsSha256`). Which types take no tags is not known to the engine (`untagged` is empty), so a resource outside the tag sweep is traceable through the stack's own resource list only.
9. That `describe-stack-resources` prints `StackResources[].LogicalResourceId`, `PhysicalResourceId`, `ResourceType` and `ResourceStatus`, that the physical id is the Cloud Control primary identifier for the types `CLOUD_CONTROL_TYPES` names (`src/observe/verify.ts`), and the ARN formats `src/observe/blueprint.ts` derives from a physical id for those types (an S3 bucket name, a log group name, a role name without a path, a queue URL, a KMS key id, a table name, a function name, VPC, subnet and security group ids). A type outside that table keeps no ARN, so its tagged ARN would be reported as unexpected by the sweep and a person reviews it.

**Input.** A pre-synthesized cloud assembly directory (`cdk.out`), captured and hashed exactly like a project snapshot (`captureProjectFiles`, the sealed manifest with `engine: "CDK"` and no lock file, `createImmutableSnapshot`, and a work copy checked against the manifest after every process). Synthesis is a separate dev-mode step on the build machine (the CDK toolchain is Node based). The pilot never runs `cdk synth`, the CDK CLI, `npm`, `npx` or any app code: it reads the assembly's files and calls only the `aws` CLI with the argument lists in `src/apply/engines/cdk.ts`. `engineVersion` in the manifest and in `resolved` is the `aws` CLI's version, checked with `aws --version`. The request and manifest are the same files as for Terraform.

**What is refused (fail closed, with a code).** More or fewer than one stack (`ASSEMBLY_STACK_COUNT`); a dependency of the stack on anything but the asset manifest, tree or feature-flag report, which is a cross-stack dependency (`ASSEMBLY_DEPENDENCY`); an artifact of any other kind, such as a nested assembly (`ASSEMBLY_ARTIFACT_UNSUPPORTED`); a `manifest.json` or asset manifest that is not readable JSON of the expected shape (`ASSEMBLY_UNREADABLE`); a stack environment that is not `aws://<account or unknown-account>/<region or unknown-region>` (`ASSEMBLY_ENV_INVALID`); a file or docker asset other than the stack's own template (`ASSEMBLY_NEEDS_ASSETS`: the pilot publishes nothing, it has no S3 or ECR step and no publishing role); a template that is missing or not JSON (`TEMPLATE_UNREADABLE`), over the inline limit (`TEMPLATE_TOO_LARGE`), or that repeats a key in any object (`TEMPLATE_DUPLICATE_KEY`: the last one wins here and CloudFormation parses the text itself); a `Transform` or `Fn::Transform`, which expands the template where no hash sees it (`ASSEMBLY_TRANSFORM`); a `Custom::*`, `AWS::CloudFormation::CustomResource` or `AWS::CloudFormation::Macro` resource, which runs code in the account (`ASSEMBLY_CUSTOM_RESOURCE`); a nested stack resource (`ASSEMBLY_NESTED_STACK`); an `Fn::ImportValue` (`ASSEMBLY_CROSS_STACK_IMPORT`); a stack name that is not the target's `backend` (`STACK_NOT_IN_CONTRACT`); an assembly synthesized for another account or region than the target (`ASSEMBLY_ENV_NOT_IN_CONTRACT`; an environment-agnostic assembly is what promotes, since a release identity is the same only if the files are); a stack whose assembly does not declare termination protection, or whose live stack has it off when it is updated (`TERMINATION_PROTECTION_OFF`, the pilot's policy, because it never deletes a stack and the protection stops anyone else doing it by accident); a live stack not in a stable state (`STACK_STATE_UNSUITABLE`); and an AWS CLI whose version output cannot be read (`VERSION_UNREADABLE`) or is not the manifest's (`ENGINE_VERSION_MISMATCH`). Parameter values cannot be supplied: the change set uses the template's defaults. Output cut off at the runner's limit (`OUTPUT_TRUNCATED`), a change set document that cannot be read (`CHANGE_SET_UNREADABLE`, `CHANGE_UNREADABLE`, `CHANGE_ACTION_UNKNOWN`) and a change set that is not the one just created (`CHANGE_SET_MISMATCH`) also stop the seal.

**Capabilities.** Each target in the contract has `capabilities`, a list of `CAPABILITY_IAM` and `CAPABILITY_NAMED_IAM` (empty in the example; `CAPABILITY_AUTO_EXPAND` is not accepted, because it is for the macros and transforms the engine refuses). Sealing passes that list to `create-change-set` only when the template has an `AWS::IAM::*` resource, and passes none otherwise, so a capability granted once for a release that needed a role is not carried into a later release that does not. A stack that needs IAM resources fails to create a change set until the owner puts the capability in the reviewed contract for that environment; one environment's decision is not another's. A capability is a standing grant for the stack, so list only what it needs. The change set's own capabilities must be among those passed, and are sealed. Approvers see an IAM resource as a line of the change list (its type and action), not its policy statements; that limit is inherent (see "Open real-AWS questions").

**Seal (as DISCOVERY and CHANGESET; APPLY is not in the runner's environment).** Version check; the assembly checks above; `describe-stacks` (DISCOVERY) decides `CREATE` (no stack, or one still in `REVIEW_IN_PROGRESS`) or `UPDATE`; `create-change-set` (CHANGESET); `wait change-set-create-complete`; `describe-change-set`; `get-template` for the change set (CHANGESET), whose template must equal the assembly's (`CHANGE_SET_TEMPLATE_MISMATCH`; the local file's hash alone says nothing about what CloudFormation holds); and `describe-stacks` again (DISCOVERY) for the state of the stack the change set was made against. The change set's id and stack id must name the contract's account and region (`CHANGESET_NOT_IN_CONTRACT`), and it must be `CREATE_COMPLETE` and `AVAILABLE`. Nothing is executed and nothing is deleted: a change set that is not applied stays in CloudFormation, for a person to clear. The sealed record (the artifact bytes, encrypted in the vault) holds the account, region, stack name and id, change set id and name, `CREATE` or `UPDATE`, the template file and its sha256, the parameters hash, the capabilities, the change list hash and a hash of the stack's state (id, status, last change time, service role, notification topics and rollback configuration). The artifact hash approvers sign binds that record and the contract's hash, environment, target and release identity, so the change set, the template, the capabilities, the change list and the stack state it was made against cannot change after approval. The redacted change list is one line per resource: logical id, resource type, and action (`CREATE`, `UPDATE`, `DELETE`, `REPLACE`, `REPLACE_CONDITIONAL`, `IMPORT`, `DYNAMIC`); never a property, a parameter value or an output.

**Apply.** After the gates and before any approval is consumed: the work copy equals the manifest; `describe-stacks` (APPLY) records the stack's state; the sealed change set is described again (CHANGESET) and its id, stack id, stack name, capabilities, parameters hash and change list hash must equal the sealed values (`ARTIFACT_TAMPERED`), and it must still be executable (`PLAN_STALE`: the change set was used or expired, or CloudFormation marked it obsolete); the assembly's template must still hash to the sealed value, and the change set's own template (`get-template`) must equal it (`ARTIFACT_TAMPERED`); the stack's id must be the sealed one (`ARTIFACT_TAMPERED`) and its state hash the sealed one (`PLAN_STALE`: the stack changed after sealing, or was given another role, topic or rollback setting, whatever CloudFormation says about the change set). Then the usual approvals and kill switch checks. Immediately before `execute-change-set` the stack is read once more and must still have the sealed state (a stack that moved in between is `APPROVALS_SPENT`, exit 3: nothing executed, the approvals gone, the sealed plan available again), the APPLY and CHANGESET variables are checked once more for any the runner would drop, and the artifact the engine is given must equal the record it rederived. Then `execute-change-set` for exactly that change set's ARN, then `describe-stacks` every poll (2 seconds by default) until the stack settles, with the kill switch read each poll, then `describe-change-set` once more. Never `delete-stack`, never `delete-change-set`, never a retry, never a second execute. From the `execute-change-set` call on, the engine throws nothing: CloudFormation may have accepted the execution, so any later failure is an outcome, never "nothing was applied".

The outcome is judged from the execute call, the stack and the sealed change set together, never from the stack alone, because a stack can move for reasons that are not this execution:

| Outcome | When |
| --- | --- |
| `SUCCEEDED` | All of: `execute-change-set` exited 0; the stack moved to `CREATE_COMPLETE` (create) or `UPDATE_COMPLETE` (update); and the sealed change set reports `EXECUTE_COMPLETE`. Only this promotes the release |
| `FAILED_NO_CHANGE` | `execute-change-set` did not exit 0, the stack did not move, and the sealed change set is still reported unexecuted (`AVAILABLE`); or the stack rolled back (`ROLLBACK_COMPLETE`, `UPDATE_ROLLBACK_COMPLETE`) after an execute that exited 0 and `describe-stack-events` shows no event for a resource after the execution began |
| `PARTIAL_REQUIRES_REVIEW` | Anything else that is not a stop: an execute that did not exit 0 when the change set cannot be shown unexecuted (a lost response or a timeout, which CloudFormation may have accepted) or when the stack moved anyway (someone else's update); an execute that exited 0 but never showed; `UPDATE_ROLLBACK_FAILED`, `ROLLBACK_FAILED`, `UPDATE_FAILED`, a rollback after resources were touched, a status this does not know, or a stack that could not be read |
| `KILLED` | A stop was requested (kill switch, the 60 minute limit, SIGINT, SIGTERM, SIGHUP or SIGQUIT) and the run had not succeeded first |

**Kill switch semantics.** The switch is read before `execute-change-set` runs (then nothing ran: `KILL_SWITCH_AFTER_APPROVALS`) and every poll after it. When it appears, an update in progress gets one `cancel-update-stack`, only while the last status read was `UPDATE_IN_PROGRESS` and only if this command's `execute-change-set` exited 0 (a stack moving under someone else's update, or an execute whose acceptance is unknown, is never canceled by this command); CloudFormation then rolls the update back, and the engine waits (the driver's grace period, ten minutes by default) for the stack to settle before it classifies, always `KILLED` unless the stack had already succeeded. A create cannot be canceled: nothing is sent, the create runs on, and `KILLED` records that the engine stopped watching. Either way the stack may be partly changed or still changing, and a person reviews it before anything else. CloudFormation, not this command, decides what a rollback restores. **The 60 minute time limit is the same stop: it cancels, and so rolls back, an update that is still running however healthy it is.** An update that can take longer than an hour does not belong in the pilot. SIGINT and SIGTERM do the same, and neither is the kill switch.

**Stack lifecycle limits (inherent to CloudFormation).** `CreateChangeSet` cannot turn termination protection on, so the first `CREATE` leaves the stack unprotected until a person enables it, and the engine does not check it again at apply (the next seal for an update refuses an unprotected stack). A failed `CREATE` ends in `ROLLBACK_COMPLETE`, which deletes the stack's resources; a stack in that state cannot be updated and needs a person (`STACK_STATE_UNSUITABLE` at the next seal).

**Evidence and messages.** Counts, hashes, statuses and codes only. The template body, parameter values, outputs, resource attributes, stack event text and AWS CLI error text are never carried, because stack events and errors can quote them; the profile also keeps output excerpts out of diagnostics. `test/apply-cdk.test.ts` plants a value in each and pins that none reaches evidence, the review bundle, a result or the vault records.

**Qualification.** `./alz apply qualify` (DEV only) runs the version check, reads the assembly, and runs `describe-stacks` as DISCOVERY, CHANGESET and APPLY, and nothing else: no change set, no `sts get-caller-identity`, no argument list beyond the pinned ones. A role that cannot describe the stack fails it, so CHANGESET and APPLY need `cloudformation:DescribeStacks` for this. **It exercises no create, execute, get-template or cancel call.** The adapter descriptors it records carry the digests of all the argument lists, but only `--version` and `describe-stacks` ran against the real CLI. That CHANGESET cannot execute and APPLY cannot create a change set is shown by the roles' IAM policies and the cloud's logs, never by this run (a negative probe would need an execute argument list for CHANGESET, which the allowlist deliberately does not have). The person checks CloudTrail and types `SEPARATED <CHANGESET role ARN> <APPLY role ARN>` only if the logs show the stack read and, in later runs, change set creation only by CHANGESET and execution only by APPLY. The evidence binds the DEV account, region, stack name (the `backend`) and workspace, the `aws` binary's sha256, the CLI version, the attested role ARNs (DEV runs only, as for Terraform on AWS), the two adapters' argument digests, and the usual 30 day limit. **Like the Terraform qualification, it does not exercise the step that changes infrastructure, so the first supervised DEV apply is the qualifying apply.** The binary hash covers the file the runner resolves for `aws` (for AWS CLI v2, its launcher or main executable), not the rest of the install directory (its libraries and service models). It refuses an honest upgrade; a change inside the install by the same-user operator is inside the trust boundary, as for Terraform, but this pin is narrower than Terraform's single binary.

**The DEV-only example and what cleanup leaves (RB6).** `config/act-pilot-contract.aws-cdk-dev.example.json` is the DEV-only CDK shape (`enabledEnvironments: ["DEV"]`, one target, empty `capabilities`). Its account, stack name, policy version and approver are placeholders or fake, so `./alz apply contract-check` reports it BLOCKED and it can never enable ACT; it carries no `authorize` entry. A CDK cleanup never deletes the stack, and it refuses a removal that would leave the stack with no resource (`CLEANUP_WOULD_EMPTY_STACK`, nothing destroyed and no approval consumed), because CloudFormation does not hold an empty stack. So after a cleanup of the one-resource DEV canary, the stack and its last resource are still in the account. The owner records them as a retained-resource disposition (who keeps them and why) at the live cleanup. Retiring the stack is the owner's separate, reviewed decision: the pilot has no stack-delete authority, and the APPLY role has no `cloudformation:DeleteStack`.

**Recommended minimum IAM actions (unverified; the owner decides least privilege).** Per environment's account, one role per identity, assumable only by that identity's web identity token:

| Identity | Actions |
| --- | --- |
| `DISCOVERY` | `cloudformation:DescribeStacks` on the stack |
| `CHANGESET` | `cloudformation:CreateChangeSet`, `DescribeChangeSet`, `GetTemplate`, `DeleteChangeSet` (for a person's manual clean-up; the pilot never calls it) and `DescribeStacks` (qualification) on the stack, and no `ExecuteChangeSet`. `CreateChangeSet` on a new stack may also need the permissions of the resources it validates, and a template that needs `iam:PassRole` does not belong in the pilot without an owner decision |

No `DeleteStack`, and no `CreateChangeSet` |

**Open real-AWS questions.** (1) Whether the stack state hash catches every out-of-band change that matters. The apply compares the stack's id, status, last change time, service role, notification topics and rollback configuration with the sealed values; a change that alters none of them, if one exists, is caught only by CloudFormation marking the change set `OBSOLETE` or `UNAVAILABLE`, which is itself unverified (assumption 4). If neither holds, the apply would execute against a stack that differs from the one approvers saw, and nothing here would catch it. (2) The retention of un-executed change sets, which this never deletes, and whether a long gap between seal and apply (the approval lifetime is up to a day) leaves one executable. (3) Per-environment role attestation: the cloud-log check is a person's, and QA and PROD roles are bound only by their account, not by an attested record. (4) Whether `wait change-set-create-complete` and the 15 minute process limit suit a large change set. (5) Which of the roles CloudFormation actually uses when `execute-change-set` runs (the caller's, or the stack's service role, which the stack state hash keeps unchanged but does not judge), and so what APPLY must be allowed. (6) What `REVIEW_IN_PROGRESS` leftovers from sealed-but-never-applied creates do to a later seal. **Inherent limits no code here removes:** approvers see a logical id, a resource type and an action, not properties, IAM statements or capabilities, so a modified role policy looks like any other modification; `{{resolve:ssm}}` and `{{resolve:secretsmanager}}` dynamic references resolve at execution, outside every hash; and the separation of the CHANGESET and APPLY roles is enforced only by the cloud-side configuration and a person's attestation.

## Open item that blocks live apply (G2)

This item and its subsections are Terraform's (state backend, `init`, `terraform apply`). The CDK engine has no state backend; its CHANGESET and APPLY principals are attested the same way, and what its qualification does and does not show is in "CDK" (Qualification).

For `terraform apply <planfile>`, Terraform configures the backend from the plan, and backend attributes the plan leaves unset fall back to the apply process's own provider variables (`ARM_*` for Azure, `AWS_ROLE_ARN` and `AWS_WEB_IDENTITY_TOKEN_FILE` for AWS), which are APPLY's. If so, the state write would authenticate as APPLY, collapsing the two identities. A fake engine cannot detect this and it is **not asserted anywhere in the code**. This is an open real-cloud question for each provider.

What the code does to give separation a chance: `init` runs as STATE_WRITE with a partial backend configuration (`-backend-config=../alz-backend.tfbackend`: the provider spec's STATE_WRITE settings, from the contract and the `ALZ_STATE_WRITE_*` variables, never a secret value, strict patterns before anything is written, mode 0600, deleted as soon as `init` ends), so the backend settings Terraform saves name STATE_WRITE; `terraform apply` then runs with the APPLY identity only. `state pull` runs as STATE, but if Terraform prefers the saved backend settings it authenticates as STATE_WRITE; that is also unproven. The apply adapter's argument lists, and so its argument digest, include that `init`. Every step (including sealing and the qualification plan) uses the apply Terraform profile (see "Providers"): a variable it drops that would redirect where providers are installed from is refused (`ENVIRONMENT_REFUSED`), and the step does not run. The `Saved plan is stale` text match is likewise unverified.

The only gate is attested qualification evidence: `verifyApplyQualification` requires an encrypted vault file, named by the record's hash, for exactly this adapter version, argument digest and engine version, whose account fields equal the contract's DEV target, dated in the past and at most 30 days old. Until it exists, `ENGINE_NOT_QUALIFIED` blocks every apply. Evidence written without the provider's account fields is rejected; run `./alz apply qualify` again.

What the fields are: `realEngine` and `backendIdentitySeparated` are **human attestations**, not machine proof. The code checks neither; nothing stops an operator with the evidence key from writing them without a run. The only machine-checked prerequisite is that `qualify` refuses to reach the attestation prompt unless the pinned steps (version, init, workspace, throwaway plan, state read) succeeded behind the usual gates; it cannot tell a real Terraform from an executable of that name on the tool path, so the real engine is the person's responsibility. **The qualification does not exercise `terraform apply`, so the first supervised DEV apply is the qualifying apply**: it is the first time the separation is observable for the write, and the owner should watch the cloud logs during it.

### Qualifying against a real engine

`./alz apply qualify` is how that evidence is produced. **For Terraform it must be run by a person against the real engine, on a DEV target the owner supplied. It has not been run: this work tested it with the fake engine only.** It applies nothing and stores no plan. It runs the pilot's own steps in order: `terraform version`, `init` and workspace selection with the STATE_WRITE backend configuration, a throwaway plan of the pinned project as DISCOVERY (never stored, so it cannot be approved or applied), and the state serial read as STATE. It refuses outside DEV and with any of the usual gates unmet (contract, pin, kill switch, identities).

The code cannot see which principal the cloud authenticated for state and which for resources. So after the run the command asks the person to check the provider's logs for it (Azure sign-in and storage logs; AWS CloudTrail STS and S3 data events), and to type `SEPARATED <STATE_WRITE client id or role ARN> <APPLY client id or role ARN>` only if the logs show state access by STATE_WRITE, provider access by APPLY, and no state access by APPLY. Anything else writes nothing. That attestation is an operator control, not machine proof. It then writes encrypted evidence for the apply adapter and for the preview adapter, and prints each adapter version, argument digest, engine version and evidence hash. `seal` and `apply` read those records from the vault.

The evidence also records the Terraform binary's sha256, the attested STATE_WRITE and APPLY principals (client ids, or role ARNs for AWS), and the DEV backend and workspace; `apply` refuses with `ENGINE_NOT_QUALIFIED` if any differ, so a changed binary or different principals need a new qualification. For AWS the principal binding applies to DEV runs only, because each environment's roles live in its own account. The binary hash is read once at apply time; a same-user operator who swaps the binary after that read is inside the trust boundary.

Rerun it when the engine version or either adapter's argument list changes (the digest changes with it). The `terraform apply` step itself is not exercised by qualification, since that would change infrastructure; its behavior is covered only by the first supervised DEV apply, which the owner should watch.

### Backend and identity ordering at apply (G2): partly answered by the simulation

The real Terraform 1.16.4 against the Azurite emulator (`docs/act-pilot-simulation.md`, DEV MODE ONLY) showed: `terraform apply <planfile>` uses the backend settings **embedded in the plan**, not the settings that `init` saved in the apply directory. Attributes embedded as null are filled from the apply process's own `ARM_*` variables, and an environment variable with the same name does not override an embedded value. The plan file also embeds a `-backend-config` `sas_token` in plaintext, so a sealed plan is secret-bearing (it is encrypted at rest). Tested with SAS and access-key auth only; Entra and OIDC are inferred, not run. The S3 backend was not simulated: the same behavior is assumed for it, and the AWS spec is written on that assumption (`filledAtApply`).

Consequences for this design, still to be settled with a real run:

- The STATE_WRITE partial backend configuration passed to `init` at apply time is probably not what authenticates the state write. Which principal writes state follows from the seal-time settings plus the apply process's own provider variables (APPLY's).
- Keeping STATE_WRITE and APPLY distinct for the state write needs the seal-time `init` to embed STATE_WRITE's non-secret settings (Azure: client id, tenant, subscription, token file path; AWS: `assume_role_with_web_identity`). That is an owner decision with a cost, and the code offers it as an opt-in, off by default: the contract's `embedStateWrite` field, described next. It is **UNVERIFIED on a real backend**.

#### Embedding STATE_WRITE in the plan (`embedStateWrite`, opt-in, default off)

`embedStateWrite` is an optional boolean in the contract. Absent or `false` is the behavior described everywhere else on this page, unchanged: sealing runs the preview adapter's `init` with no backend file. It is valid only with the `TERRAFORM` engine; `true` with `CDK` is `CONTRACT_INVALID`. It is part of the reviewed contract, so the contract hash binds it: a plan sealed with it off is refused under a contract with it on, and the reverse (`ARTIFACT_INVALID`, before any engine step). The shipped examples do not mention it and the shipped pin stays empty.

When `true`:

- The seal-time `init` (and the throwaway plan of `qualify`) runs the apply `init` argument list, with the same partial `-backend-config` file the apply-time `init` uses, rendered from STATE_WRITE's non-secret settings only (Azure: client id, tenant, subscription and the token file **path**; AWS: role ARN and the token file **path**). The rendering allowlist names those variables and no others, so no secret and no token content can reach the file. The file is written 0600 beside the plan, deleted as soon as `init` ends, and is never part of the sealed plan, the review bundle or the evidence.
- The seal process renders the file itself. The engine's environment while sealing still holds no STATE_WRITE and no APPLY variable, and the backend the `init` saved is judged against the contract as before. Only this one extra argument list is allowed, and only when the contract opts in.
- The plan then names the state writer in its embedded backend settings, which is what `terraform apply <planfile>` reads, so STATE_WRITE (not APPLY's environment) is what the plan points at for state.

The cost: the seal step now carries the STATE_WRITE principal's settings, so the seal-time state read names the state writer and sealing becomes write-capable at the backend (the principal can write state, even though sealing only reads). The plan stays secret-bearing and encrypted at rest. Because of this, `seal` and `qualify` print a plain-language warning and require the exact phrase `EMBED STATE_WRITE <ENVIRONMENT>` (for example `EMBED STATE_WRITE DEV`) after the target and project-code confirmations and before any engine runs. A wrong or missing phrase runs no engine and seals nothing, and no flag skips it. The confirmation goes through the same terminal abstraction as the other prompts, which is how the console wizard asks it in a dialog (see "Channels"). `./alz apply preflight` adds an informational line, `plan will embed STATE_WRITE settings: yes` or `no`.

**Still UNVERIFIED:** whether a real Terraform authenticates state reads and writes as STATE_WRITE from the embedded settings, whether the seal-time `init` accepts the STATE_WRITE client id while the process holds STATE's variables, and whether the AWS `assume_role_with_web_identity` block embeds as assumed. The tests use a fake engine and pin this program's logic only. Authentication stays SIMULATED until a real-backend run, and the attestation at `qualify` remains an operator control, not proof.

- Until a real run shows which principal wrote state, `qualify` records an attestation and not proof, and the first supervised DEV apply is where it becomes observable. Do not rely on the separation before then.

Known, not changed: Terraform contacts the HashiCorp checkpoint service on every run (the runner profile does not set `CHECKPOINT_DISABLE`; production network policy should block it), and a failed state save writes `errored.tfstate` with mode 0644 and quotes the full backend URL in its error text, which is why engine output is withheld from messages.

### Provider versions are bound to the review

The denied-type lists (`AWS_DENIED_TYPES`, `AZURE_DENIED_TYPES`) were reviewed against the full schemas of hashicorp/aws 6.68.0 and hashicorp/azurerm 4.81.0 (`AWS_DENIED_TYPES_REVIEWED_AGAINST`, `AZURE_DENIED_TYPES_REVIEWED_AGAINST`, the one source of truth). A newer schema can add a type that deploys a template or runs code at apply, which the lists would not name. So the project's `.terraform.lock.hcl` must pin `registry.terraform.io/hashicorp/aws` and `registry.terraform.io/hashicorp/azurerm`, when it names them, at exactly those versions. Any other version, newer or older, is refused (`PROVIDER_VERSION_NOT_REVIEWED`). **The authoritative check runs after init** (review of #327, round 5): at seal, apply, cleanup and qualify, right after `init -lockfile=readonly` and before any plan runs provider code, `terraform version -json` reports `provider_selections`, what init actually selected whatever the lock file's layout. Every selected source must be one this cloud path allows, by exact registry host and namespace (another registry such as `registry.opentofu.org`, another namespace, the other cloud, azapi or azuread are `PROVIDER_NOT_ADMITTED`), aws and azurerm must be exactly the reviewed versions, and missing or malformed selections are `PROVIDER_SELECTIONS_UNREADABLE`. A built-in-only project selects nothing and passes. `./alz apply prepare` gives the same answers early from a strict lock reader, naming the locked and the reviewed version: it refuses carriage returns, any `provider` text it did not read as a block (an indented block, a mention that parses to nothing) and a source this cloud path does not allow. Other providers are not judged by this rule. The committed AWS canary (`qualification/aws/act-dev1-canary`) pins `hashicorp/aws` at `= 6.68.0` and commits its `.terraform.lock.hcl`, with `h1:` hashes for linux_amd64 and darwin_arm64 generated by `terraform providers lock` from the release zips (checked against HashiCorp's signed SHA256SUMS); an operator on another platform adds that platform's hashes with `terraform providers lock -platform=...` in a reviewed commit. No Azure pilot project is committed; `docs/act-pilot-azure-terraform-g0.md` shows `azurerm` pinned at `= 4.81.0`. **Bumping either provider** means re-reviewing the denied types against the new schema, then changing the reviewed version beside the list, in one reviewed commit; only then can a lock pin the new version.

### Providers install only from the official registry

With no CLI configuration, Terraform also installs providers from implicit local mirrors, `terraform.d/plugins` in the working directory among them, and that directory is the project copy (review of #327, round 6). A project could ship its own package named `hashicorp/aws 6.68.0`, pass every version check, and run it with DISCOVERY's environment at plan and APPLY's at apply. So:

- **The product's own CLI configuration.** Every Terraform step (init, version, plan, show, apply, the destroy plan) runs with `TF_CLI_CONFIG_FILE` set to a file the product writes into its private scratch directory, outside the project copy, one per session. It holds an explicit `provider_installation { direct { include = ["registry.terraform.io/hashicorp/*"] } }`, which turns every implicit mirror off, plus `disable_checkpoint = true`. There is no plugin cache (`TF_PLUGIN_CACHE_DIR` is empty), no `dev_overrides` and no credentials block. The value is set after anything injected, so neither the project, the operator's own environment nor an `ALZ_<IDENTITY>_` variable can point elsewhere (an injected one is refused, `ENVIRONMENT_REFUSED`). Every step first checks that the file is still exactly the product's. No filesystem mirror is configured: the emulated runs use only the built-in provider, and qualification and the live run install from the registry.
- **No project-shipped plugins or CLI configuration.** A `terraform.d` or `.terraform` directory, or a `.terraformrc` or `terraform.rc` file, at any depth, is refused at `./alz apply prepare` and again in the seal, apply and cleanup scan (`TERRAFORM_LOCAL_PLUGIN_DIR_REFUSED`).
- **HashiCorp's own packages.** A lock entry for a reviewed version must name at least one hash, and every hash must be HashiCorp's published one (`OFFICIAL_PROVIDER_HASHES`, `src/apply/lockfile.ts`): `zh:` for every platform from the signed `SHA256SUMS`, and `h1:` for linux_amd64 and darwin_arm64, computed by Terraform from the signature-verified zips. Anything else is refused (`PROVIDER_HASH_NOT_OFFICIAL`), at prepare and before init. Init with `-lockfile=readonly` then installs only a package matching those hashes. A further platform's `h1:` is added by a reviewed commit.

### Provisioners, actions and ephemeral resources (RB1)

Every Terraform path (seal, apply and cleanup, AWS and Azure) refuses three constructs, because each one reaches past the reviewed change list (review of #322, N2; `src/apply/terraform-constructs.ts`):

- **`provisioner` blocks** (`local-exec`, `remote-exec`, `file`), on any resource and in a `removed` block, in any module: they run commands on the runner or a host it reaches, with APPLY's credentials (`TERRAFORM_PROVISIONER_NOT_ALLOWED`).
- **Terraform `action` blocks and their invocations** (Terraform 1.14+): an action calls a provider operation at apply, outside the resource changes the approvers read (`TERRAFORM_ACTION_NOT_ALLOWED`).
- **`ephemeral` resources**: they are opened at plan (as DISCOVERY) and at apply, many read secrets or mint tokens, and none appears in the change list (`TERRAFORM_EPHEMERAL_RESOURCE_NOT_ALLOWED`).

Where each is seen, checked against real Terraform 1.16.4: `terraform show -json` lists provisioners on resources, declared actions and action invocations, and the plan check refuses them. It lists neither ephemeral resources nor `removed` blocks (a `removed` block's destroy-time provisioner shows only as an ordinary delete), so the work copy bound to the manifest is also read before init, at seal, apply and cleanup.

- **`.tf` files: a lexical rule, not an HCL parser.** The words `provisioner` and `ephemeral` are refused anywhere, comments and strings included, unless an `=` follows (`ephemeral = true` on a variable or output is allowed). The codes say the match is lexical (`TERRAFORM_PROVISIONER_WORD_IN_SOURCE`, `TERRAFORM_EPHEMERAL_WORD_IN_SOURCE`), and the seal refusal tells the operator the word may be in a comment or a string. It fails closed: rename the comment or the string.
- **`.tf.json` files: strict JSON, never `JSON.parse`.** `JSON.parse` keeps only the last of two same-named keys, while Terraform keeps every block under a repeated block-type key. Two `"removed"` keys, the first with a destroy-time `local-exec`, hid the command from both halves and Terraform ran it (review of #327, B1; reproduced with real Terraform 1.16.4 in `test/fixtures/live/terraform/removed-duplicate-key.*`). An object that repeats a key, compared after escapes are decoded, is refused (`TERRAFORM_CONFIGURATION_DUPLICATE_KEY`), and so is anything that is not strict JSON. Then a `provisioner` key at any depth and a top-level `ephemeral` key are refused, and the `provisioner` word rule also runs over the raw text.

The emulated simulations' kill-switch scenario uses no provisioner; it holds the apply busy with many built-in values instead.

### The backend and provider binding

The contract's `backend` and account fields are checked against what the project itself configures, because a project can name any backend or provider:

- **Backend.** After `init`, for both providers, the driver reads `.terraform/terraform.tfstate` in the work directory and applies the spec's saved-backend check (Azure: `azurerm` with `storage_account_name`, `container_name` and `key`; AWS: `s3` with `bucket`, `key`, `region` and `use_lockfile` true) against the contract's DEV, QA or PROD target. It runs after the seal-time `init`, whose settings the plan embeds (a mismatch is `ARTIFACT_INVALID` with `BACKEND_NOT_IN_CONTRACT`, and nothing is sealed), and after the STATE_WRITE `init` at `apply` and `qualify`. At apply anything else, including a value that is not a string, is `TARGET_NOT_IN_CONTRACT` before the approvals are consumed. A file that cannot be read is `APPLY_FAILED` ("no approval was consumed"), not a pass.
- **Provider.** From the plan's `terraform show -json` `configuration` (at `seal`, and again at `apply` when the list is re-derived), the spec judges the constants in its provider blocks, in any module or alias: Azure `subscription_id` and `tenant_id` must equal the contract's (`PROVIDER_SUBSCRIPTION_NOT_IN_CONTRACT`, `PROVIDER_TENANT_NOT_IN_CONTRACT`); AWS as described in its section (`PROVIDER_ACCOUNT_NOT_IN_CONTRACT`, `PROVIDER_CONFIG_NOT_IN_CONTRACT`). **Limit:** a value that is an expression (a variable, including one fed by an injected `TF_VAR_*`, a data source, a local) is *not checkable* from the plan and is not judged, not silently accepted as safe. For those, the only controls are the identity checks (each credential must name the contract's account, and the provider runs as APPLY only) and the cloud-side role assignments. Owners should keep the provider's account out of expressions in the pilot project.

## Kill switch

Create the file named by `killSwitchPath` (example: `.runs/apply/KILL`). A switch that cannot be read counts as on. It is read at exactly these points:

1. At the start of `seal`, `qualify` and `apply` (the shared admission step, before any file or engine).
2. In `apply`, again after the engine is prepared and the change list re-derived, together with the contract, authorization, target and approval re-checks, and before the approvals are consumed. A switch seen here is `KILL_SWITCH_ACTIVE`: nothing is consumed (exit 2).
3. Immediately before the `terraform apply` process (or, for CDK, `execute-change-set`) is spawned. A switch seen here, after the approvals were consumed, is `KILL_SWITCH_AFTER_APPROVALS` (exit 3, nothing ran, the artifact is given back).
4. Every second while `terraform apply` runs. Terraform is sent SIGINT (its graceful stop), then SIGKILL to its process group after a grace period (60 seconds). For CDK, at every poll of the stack (2 seconds by default); see "CDK" for what a stop does there.
5. `status` reports it; it enforces nothing.

It is not read between `init`, `workspace` and the state reads (for CDK, between the steps before the execute). The same stop (SIGINT, then SIGKILL) happens at the 30 minute limit (for CDK, a stop at the 60 minute limit) and when this command receives SIGINT, SIGTERM, SIGHUP or SIGQUIT while the apply is held: the signal is intercepted, the engine is stopped gracefully and the evidence is written, so the CLI does not exit mid-run. A stopped apply ends as `KILLED` whatever exit code Terraform reports. A signal before the engine starts ends the run as `APPLY_FAILED` ("interrupted", exit 1) without consuming approvals; after they are consumed, any failure before the engine starts is `APPROVALS_SPENT` (exit 3). The owner removes the file; the code never does.

## When an apply fails

Engine output is withheld everywhere because it can hold secrets. Every outcome closes the artifact: a retry needs a new preview and new approvals. These end with exit code 3. (`APPROVALS_SPENT` and `KILL_SWITCH_AFTER_APPROVALS` are not outcomes: nothing ran, the artifact is given back, the approvals are spent.)

| Outcome | Meaning | Action |
| --- | --- | --- |
| `FAILED_NO_CHANGE` | Only for a state-lock refusal (`Error acquiring the state lock`) with the state serial unmoved | Fix the cause, seal a new preview, get new approvals. |
| `PLAN_STALE` | `Saved plan is stale`, with the serial unmoved; nothing applied | Seal a new preview. |
| `PARTIAL_REQUIRES_REVIEW` | Any other non-zero exit once the apply began, or a moved serial. Terraform exits 1 for every apply error, so the exit code cannot tell a refusal from a failure halfway through | **Do not retry.** A person reviews state and resources by hand first. |
| `KILLED` | Stopped mid-apply; the state lease may still be held | **Do not retry.** Review state, the lease and resources by hand. |

The artifact is reserved in the ledger (an exclusive-create entry in state `RESERVED`) after the gates pass and before any engine step, and the evidence replaces the reservation when the run ends, so two runs holding different approval sets cannot both proceed. A reservation is given back only if the engine never started. If the process dies after the engine started (SIGKILL, power loss, an evidence write that fails), the entry stays `RESERVED`: `status` and every later apply report the artifact as already applied, and an owner reviews the state, the lease and the resources by hand, then seals a new preview. Nothing ever makes a reserved artifact applicable again.

The table is Terraform's. For CDK the outcomes and their meaning are in "CDK" (`FAILED_NO_CHANGE`, `PARTIAL_REQUIRES_REVIEW` and `KILLED` close the artifact the same way; a change set that is no longer the sealed one is refused as `PLAN_STALE` or `ARTIFACT_TAMPERED` before any approval is consumed, which is exit 2, nothing spent), and there is no recovery file: the stack and its events in CloudFormation are the record, and a person reads them there.

The two text matches above (`Saved plan is stale`, `Error acquiring the state lock`) are read only from the **first** `Error:` diagnostic in Terraform's output, never from a later line, because a provider error body can quote either phrase; a run whose first error is anything else, however it ends, is `PARTIAL_REQUIRES_REVIEW`. They come from documented Terraform output and the fake engine; they are not verified against a real engine, and anything else fails safe to `PARTIAL_REQUIRES_REVIEW`.

**Recovery attachment.** After any non-success outcome the driver looks for `errored.tfstate` and `crash.log` in the engine's work directory, before the scratch directory is deleted. Found files go into the encrypted evidence vault under purpose `apply-recovery`, and the apply evidence carries `recovery: { files, sha256 }` (a count and a hash only, never contents). If the vault write fails, the result message says the files were lost with the scratch directory. That location is Terraform's documented behavior and is not verified against a real engine. The files are encrypted at rest under the same evidence key the operator holds, so this protects them from other accounts and backups, not from the operator.

## Plaintext on disk

The decrypted plan and the backend configuration exist only in a private scratch directory, are removed by their own cleanup on every normal exit and on SIGINT, SIGTERM, SIGHUP and SIGQUIT (and the plan the moment a stop is requested), and are deleted as soon as they have been used. A SIGKILL or a crash cannot run a handler. `qualify`, `seal` and `apply` therefore start with the same stale-directory sweep as the teardown CLI (`status` and `approve` never sweep, and make no scratch): directories of the running account in the system temporary directory named `alz-preview-*`, `alz-snapshot-*` or `alz-child-*` and older than one hour are removed. Younger directories (a run in another terminal) and other accounts' directories are left alone. **The sweep is skipped, with a printed notice and nothing removed, whenever the apply ledger holds a `RESERVED` entry (or an entry that cannot be read), or any `alz-preview-*` directory holds `errored.tfstate` or `crash.log`:** those may be the only record of what an apply did, and an owner reviews them by hand first. Remove the cause (finish the review, then seal a new preview, and clear the directory) and the sweep resumes. The change list approvers read is bound into the artifact hash; `runApply` re-verifies a sealed plan it is handed rather than trusting the caller's earlier check, and after `init` it re-derives the change list from the decrypted plan bytes with the pinned `terraform show -json` (no identity in the environment). A difference from the sealed list is `ARTIFACT_TAMPERED` and nothing is consumed.

## What the tests control, and what they do not

The driver trusts what the CLI hands it only as far as it re-verifies it, but the process boundary is not a security boundary: **in-process callers can forge a terminal.** Any code that runs in the same process can build a `HumanInvocation`, an `ApplyRequest` or a terminal object that says it is interactive. `checkHumanInvocation` catches mistakes and an agent that does not know the contract, not a caller that does. The control is that nothing an agent can reach imports the apply path, the console adapter or the console server that mounts it, and that from the console side only `src/cli/ui-channel.ts` reaches `src/apply`; `test/apply-boundary.test.ts` pins that, and it is the control, so a change that weakens it is a change to the authority and needs the owner. The console process itself holds the same user ID and the operator's identity variables, so the session token and the loopback bind are what keep another local program or web page from driving it.

## Cleanup

Cleanup of what a pilot apply created is its own governed action under the same contract (docs/act-pilot-plan.md, "Cleanup of pilot-created resources"; operations in `docs/observe-and-cleanup.md`). It exists for both Terraform providers: the AWS row reads Cloud Control through the aws CLI as DISCOVERY; the Azure row reads Azure Resource Manager in process as DISCOVERY, exchanging the identity's federated token in an HTTPS body and never through a process argument (`docs/observe-and-cleanup.md`, "The Azure reader"). The CDK engine has the observe step, the proposal (logical ids; CloudFormation's own resource list is the blueprint, read as DISCOVERY; Cloud Control reads by CloudFormation type; the stack itself is never deleted and the proposal says so) and the removal change set, which refuses to leave the stack with no resource (`CLEANUP_WOULD_EMPTY_STACK`; see "CDK", "The DEV-only example and what cleanup leaves"). The APPLY identity executes the destroy, bound to the approved list (owner decision 1); there is no CLEANUP role. Never deleted by a cleanup, directly or as a dependent: the state backend bucket or storage account and its settings, every identity and authorization object (on AWS anything in the IAM or identity service, `aws_iam_*`, `awscc_iam_*`, `aws_ssoadmin_*`, `AWS::IAM::*` and `AWS::SSO::*`, credentials included, the run's own among them, owner policy #39; on Azure everything under Microsoft.Authorization and Microsoft.ManagedIdentity; the one exception is a run-created policy that meets every condition of `src/observe/run-created-policies.ts`, owner decision "Unpin the ACT decision" item 2 (c), and principals are never part of it), deployment history (`Microsoft.Resources/deployments`), every Azure resource group (retained by the pilot owner; retiring the environment is a separate, reviewed action), on AWS anything that deploys a CloudFormation stack or a provisioned product, and anything the sealed plan did not create. On AWS a run-created resource is deleted only when its type is on the reviewed leaf allowlist (`src/observe/aws-leaf-types.ts`); any other type is kept and named (`TYPE_UNREVIEWED`, kept by the environment's owner), and the leftover check stays INCOMPLETE while one remains (`docs/observe-and-cleanup.md`).

A cleanup that ends `PARTIAL_REQUIRES_REVIEW` or `KILLED` spends the proposal and its approvals, keeps `errored.tfstate` and `crash.log` in the vault as an apply does, and is followed by `verify-cleanup` (which reads and changes nothing) and a person's review; a new proposal needs a new observation and new approvals. The pilot apply tags nothing, so resources outside the engine's state are never searched for, and every record says `inventory: NOT_AVAILABLE`.

### Removing a run's working files

Removing the local working files the product generated for one run goes through the same proposal, approval quorum and kill-switch path as a cleanup (owner decision 6443062568, "Unpin the ACT decision", item 2; `src/apply/workspace-removal.ts`). It touches local files only, never a cloud resource.

| --- | --- | --- |
| Propose | `./alz apply propose-removal --sealed SEALED_PLAN --requester ID --key REQUESTER_KEY.pem` | Plans the run's working files from the disk as it is now and writes a removal proposal (`<proposal12>.removal-proposal.json` beside the cleanup proposals). The proposal's hash binds the run, its manifest hash, environment, target, channel and contract, and the exact list (paths, sizes, the SHA-256 of each preparation file and removed plan). The requester (an allowlisted id with that entry's own key) signs the hash under the cleanup request domain, as a cleanup's requester does. No phrase: a proposal authorizes nothing. |
| Approve | `./alz apply approve --bundle REMOVAL_PROPOSAL.json --key KEY.pem --approver ID` | The same command, key, allowlist and signature domain as a cleanup approval. The cleanup quorum for the environment applies (in PROD two distinct approvers, neither the requester). An apply approval never verifies here. |

The planner judges ownership, name and age before it looks into anything. Another account's entry, a young directory and a name that is not the driver's are ignored. A link, or a directory with a link anywhere inside it (a planted entry, or a plugin cache link under `.terraform`), is skipped and reported (`skipped`), never followed, and it never blocks the rest. A folder the product owns that is itself a link is refused (`REMOVAL_PATH_REFUSED`). Each path is judged again right before it goes (`REMOVAL_PATH_CHANGED`).

A removal record cannot widen a removal. A forged or edited record can only narrow a resumed one, because the fresh plan and the signed proposal decide what may go.

The removal record `<artifact>.workspace-removal.json` in the evidence directory is written before the first removal (`IN_PROGRESS`) and after each one. It names the proposal, the requester, the approvers, every path with its size and file count, the SHA-256 of each preparation file and removed plan, and what was held or skipped. A removal that stops part-way (`REMOVAL_FAILED`, `REMOVAL_STOPPED`) has spent its approvals. New approvals for the same proposal resume it, and only what is left (and still this run's) goes. Each removal is appended to the record; none is overwritten. A malformed record is refused (`REMOVAL_RECORD_INVALID`).

**Follow-up (not in this change):** a run sealed in the console channel cannot be removed yet. The commands refuse `CHANNEL_MISMATCH`, and the console wizard has no removal step. Adding one belongs with the console's pilot steps (`src/cli/ui-channel.ts`), under the same gates. A dedicated `REMOVE` signature domain would need `src/apply/approval.ts`. Until then a removal is signed under the cleanup domains; its proposal hash, which covers its own kind, binds every signature to the removal.

## What the owner supplies

For either provider: the reviewed `policyVersion` in the contract (so `prepare` can fill it in), the DEV, QA and PROD accounts, the region, tags, retention, budget and least-privilege scope, the provisioned state backend (one per environment) and the federated identities, the approver public keys (and the second production approver), the execution host, the pilot scope, the cleanup owner, and a person to run `./alz apply qualify` and attest from the cloud logs. For Azure also the tenant ID and the subscription IDs. For AWS also the 12 digit account IDs, and for the CDK engine instead of the state buckets and state roles the stack name, the three web-identity roles per account (DISCOVERY, CHANGESET, APPLY), the capabilities each environment may use, a synthesized environment-agnostic `cdk.out` that publishes no asset, and a person to enable termination protection after the first create. For Terraform on AWS also one S3 bucket per environment with versioning on, one IAM OIDC identity provider and the four web-identity roles per account, and the token files for them on the execution host. Their absence blocks live apply only; tests use explicit fixtures.
