# Pilot apply: operator runbook

Status: implemented and tested **with a fake engine only** (a fake `terraform`, and a fake `aws` for the CDK engine). It has never been run against a real Terraform engine, the real AWS CLI, CloudFormation, a real Azure subscription or a real AWS account, and the qualification and identity separation it depends on are only attested, by a person, once they complete the real-engine run below (G2); nothing in the code proves them. A fake-engine test pins logic, not behavior. Live apply stays blocked until the owner supplies the values at the end of this page and that evidence exists.

The plan is `docs/act-pilot-plan.md`. The preview driver this builds on is `docs/destroy-preview-driver.md`.

## Authority

The operator authorizes, the driver enforces, and agents never initiate. ACT stays DISABLED globally. It is enabled for the pilot only while `config/act-pilot-contract.json` is valid, has `enabled: true`, and hashes to the committed pin (see "The contract and its pin"). The console shows the command (`./alz apply`) as a handoff and never runs it. `test/apply-boundary.test.ts` pins that nothing the broker, agents, orchestration or the console can reach imports the apply path.

An apply runs exactly the sealed artifact that was previewed and approved (for Terraform, the plan file: `terraform apply <planfile>`; for CDK, the sealed CloudFormation change set: `aws cloudformation execute-change-set` for that change set's ARN). Nothing is regenerated between approval and apply. There is no `-auto-approve`, `-target`, `-replace`, `-refresh=false` or `-lock=false`, and locking stays on. Each stage (DEV, QA, PROD) is a separate target-bound sealed plan with its own approvals, bound to the qualified release through `releaseIdentity` (project files, lock file, engine and provider versions, shared inputs); see "Promotion". The earlier stage's manifest hash is not needed, because manifests are target-bound.

## What a person, a terminal and a signature each prove

A terminal is not authentication. Every subcommand needs a terminal on stdin and stdout, and that only means a person, or a script holding a pseudo-terminal, is typing; it proves nobody. Typed confirmations prevent mistakes (the wrong target, the wrong plan). They are not identity.

Signatures are the authentication. An approval is an Ed25519 signature, by a key in the contract's `approvers` list, over the artifact hash, environment, exact target, expiry and a one-time nonce. A typed name is never proof. The key is a file you name (mode 0600), never read from the environment. Whoever holds an approver's private key is that approver, so approver key custody is an operational control, not something the code enforces: each approver should keep their key on their own device, and the contract's allowlist is reviewed in the commit that changes it. The code cannot tell whether one person holds two keys.

An approver does not need the operator's evidence key, the vault or the sealed plan. They need the review bundle (below), the contract, and their own key file.

Production's two-person rule means two distinct allowlisted approvers with two distinct keys, both signing the same artifact. It is not a check on who runs `apply`: the operator's account name has no bearing, and the same person holding both keys defeats it. Approvals are consumed once, before the engine runs.

## Who is inside the trust boundary

The operator who runs the commands is the same user ID as the process, and holds the evidence key, the working tree, the contract and the pin file, and sets the identity variables. For key material that operator is inside the trust boundary. The pin, the encryption and the ledger make a change reviewable and tampering detectable by anyone who does not hold the key; they do not stop the operator, who could re-encrypt evidence, forge qualification evidence, edit the ledger, or edit the contract and its pin together. The pin is reviewable, not enforced, against a writer with that user ID. The identity checks below catch mistakes and crafted environments, not the operator. Independence comes from the second approver, the contract reviewed in version control, and the cloud-side role assignments, not from this code. The encrypted recovery files and evidence protect against other accounts and backups, not against the operator.

## Commands

Every subcommand refuses before reading any file unless it has a terminal on stdin and stdout. There are no flags that force, skip or pre-answer anything; an unknown flag is an error.

| Step | Command | Who |
| --- | --- | --- |
| Qualify | `./alz apply qualify --request REQUEST.json --manifest MANIFEST.json` | Operator, once per adapter or engine version, DEV only. See "Qualifying against a real engine". |
| Seal | `./alz apply seal --request REQUEST.json --manifest MANIFEST.json` | Operator. Types the target, then (Terraform only, which runs providers and modules) `RUN PROJECT CODE`; the CDK engine runs no project code and asks for the target only. Prints the artifact hash, the sealed plan path, the review bundle path and the redacted change list (address, type, action). |
| Approve | `./alz apply approve --bundle REVIEW_BUNDLE.json --key APPROVER_KEY.pem --approver ID` | Each approver, separately, with no evidence key. Reviews the changes, types `APPROVE <DEV, QA or PROD> <first 12 characters of the artifact hash>`. Prints a signed approval; no secret. |
| Apply | `./alz apply apply --request REQUEST.json --manifest MANIFEST.json --sealed SEALED_PLAN --approval A.json [--approval B.json]` | Operator, with the evidence key (it loads the sealed plan from the vault). Types one line: `APPLY <DEV, QA or PROD> <first 12 characters of the artifact hash> <account> \| <backend> \| <workspace>`. Prints redacted evidence. |
| Preflight | `./alz apply preflight --environment DEV\|QA\|PROD [--contract CONTRACT.json]` | Anyone at a terminal, before the first seal. Read-only and offline: checks the contract's shape (a draft or example that is not enabled or pinned too), whether it is pinned, that each identity the engine needs is configured, distinct, fallback-free and aimed at the environment's account, that the engine's program is in an approved tool directory, and the kill switch. Prints names, never values; exit 2 if anything is not ready. It always reports authentication as `SIMULATED` until `qualify` has run on a real backend. Setup of the accounts it checks is in `docs/act-pilot-bootstrap.md`, separate from any apply. |
| Status | `./alz apply status [--sealed SEALED_PLAN]` | Anyone at a terminal. Read-only: contract state, kill switch, and whether an artifact was applied. |

There is no `--allowlist` and no `--qualifications` file. The approver allowlist is part of the pinned contract, and qualification records are read from the encrypted evidence vault (`.runs/apply/qualification`), where a record exists only if valid, decryptable evidence does.

Request files carry only `environment`, `target` (`account`, `backend`, `workspace`; `account` is the provider's account identifier) and `projectRoot` (seal and qualify also `policyVersion` and `resolved`). The command supplies the invocation, manifest and approvals; a file that carries them is refused.

### The review bundle

`seal` also writes a review bundle beside the sealed plan, at `<sealed plan path>.review.json` (mode 0600), and prints its path. It holds `artifactSha256`, `planSha256`, `manifestHash`, `releaseIdentity`, `environment`, `target`, `engineVersion`, `policyVersion`, `contractSha256`, `createdAt`, `changes` and `changesSha256`. It holds no plan bytes and no plan, state or variable values, so it is not secret and the operator can send it to approvers on any channel.

`approve` reads only that file. It checks the exact field set, recomputes `changesSha256` and the artifact hash from the bundle's fields with the same function the sealer uses (`computeArtifactSha256`), and refuses on any mismatch (`ARTIFACT_TAMPERED`) or malformed field (`ARTIFACT_INVALID`) before it asks anything. It then shows the changes and the target, and the approver types the environment and the first 12 hex characters of the artifact hash. A bundle that was edited cannot get a signature for another plan, because the change list and target are inside the hash. What the check does not prove is that the vault holds a plan with that hash; if it does not, `apply` refuses (`ARTIFACT_INVALID`) and the approval is wasted, not misused. The approver reads a change list, not the plan; the apply re-derives the list from the plan bytes (see "Plaintext on disk").

### What the change list shows

One list, derived in one place by the engine (Terraform: from `terraform show -json`; CDK: from `describe-change-set`) and bound by `changesSha256` into the artifact hash, so the seal, the review bundle, `approve` and `apply` all show and hash the same thing. Each line has an action, an address and a type. For Terraform it also says when a resource is being **imported** (`importing`), **moved** (`previousAddress`, a plan that renames state), or **forgotten** (action `FORGET`: dropped from state while the real resource is left running). Each output whose value changes is a line with address `output.<name>` and type `output` (its name and action only, never its value). Bidi and zero-width control characters (U+200B-200F, U+202A-202E, U+2060-2064, U+2066-2069, U+FEFF) are stripped from addresses and types when the list is derived, so what is hashed is what is shown; a stored list that still has one is `ARTIFACT_INVALID`, and every display strips them again.

### Exit codes

| Code | Meaning | What to do |
| --- | --- | --- |
| 0 | Done. | |
| 1 | Error, and nothing was spent: bad input, no terminal, a wrong confirmation, a stop signal before the engine started, or the engine could not start (`APPLY_FAILED` with "no approval was consumed"). | Fix the cause and run again. |
| 2 | BLOCKED: the contract refused before any action (disabled or unpinned contract, kill switch, wrong target, unverified or insufficient approvals, artifact already applied, engine not qualified, identities, missing promotion evidence, a bundle or sealed plan that does not verify). | Read the code in the message. |
| 3 | SPENT, in two cases. The engine ran and the sealed plan and its approvals are used up, whatever happened (failed, partial, killed, stale, or evidence that could not be written). Or the approvals were consumed and the engine did not start: `KILL_SWITCH_AFTER_APPROVALS` (the switch appeared) or `APPROVALS_SPENT` (the plan file could not be written, or the engine could not be spawned, for example a full disk). Nothing ran, the approvals are gone and the sealed plan is available again. | Read "When an apply fails". After an engine run, never rerun the same files. After either refusal, fix the cause (lift the switch, free the disk) and collect new approvals for the same sealed plan. |

`test/apply-cli.test.ts` pins this mapping.

## The contract and its pin

The contract (`config/act-pilot-contract.json`, shapes in `config/act-pilot-contract.example.json` for Azure and `config/act-pilot-contract.aws.example.json` for AWS) names the provider (`AZURE` or `AWS`), the engine (`TERRAFORM`, or `CDK` with `AWS` only; any other pairing is `CONTRACT_INVALID`; `config/act-pilot-contract.aws-cdk.example.json` shows the CDK shape), and for DEV, QA and PROD the account fields and backend its spec defines (different pairwise in account and backend, compared case-insensitively; for CDK the backend is the stack name, which may repeat because the account differs, the workspace is `default`, and each target adds `capabilities`, see "CDK"), the required approvals (DEV at least 1, QA at least 1, PROD at least 2), the approval lifetime, the kill switch path, and the approver allowlist (id, Ed25519 public key, environments). It loads only if its canonical SHA-256 equals the hash in `config/act-pilot-contract.sha256`. That hash is sealed into every plan and recorded in the apply evidence, so a plan applies only under the contract it was sealed under: re-pinning the contract (another region, tenant, approver or any other field) means a new seal and new approvals, and the evidence shows which contract ran. An empty or absent pin means ACT is disabled, which is how the repository ships. A pin that does not match is `CONTRACT_INVALID`. Release admission checks the same pin.

To enable the pilot, or to change a target or an approver:

1. Edit `config/act-pilot-contract.json`.
2. Compute its hash with `./alz apply pin`. It prints the SHA-256 and whether the contract is valid, and writes nothing.
3. Write that hash to `config/act-pilot-contract.sha256`.
4. Commit both in one reviewed change. Reviewers check the targets and each approver's key against what the owner supplied.

Paths are anchored to the repository root found from the module, never to the working directory. The pin makes a change reviewable; it does not stop the operator described above.

## Promotion: DEV, then QA, then PROD

Each stage has its own sealed plan, artifact hash and approvals, and an approval signed for one environment is `APPROVAL_MISBOUND` for another. DEV needs no earlier evidence. QA needs a successful, encrypted DEV apply record for the same release identity. PROD needs a successful QA apply record for the same release identity, and DEV evidence alone is refused (`PROMOTION_EVIDENCE_MISSING`). Identity checks are per environment: each environment's credentials must match its own contract target, and the account in an AWS role ARN is the environment's own. `qualify` runs only against the DEV target; QA and PROD are not qualified separately and are refused.

## Identities

Each engine needs its own set of separate principals (`EngineSpec.identities`): four for Terraform, three for CDK. They are set as `ALZ_<IDENTITY>_<VAR>` in the environment of the person running the command. None inherits the operator's credentials and none falls back to another (APPLY is never a state fallback). The driver refuses if one the engine needs is missing; if one it does not need is configured (a privileged credential nothing uses: STATE or STATE_WRITE with a CDK contract, CHANGESET with a Terraform contract; `IDENTITY_NOT_CONFIGURED`); if two share a principal-like value (client id, role ARN, secret, token file, client certificate or config directory) even under different variable names, compared after normalizing (case, padding, path spelling, symlinks and hard links); if any carries a variable that would let a child fall back to a CLI, instance or ambient credential; if a principal-like value equals the operator's own ambient variable of the same kind; or if any names an account other than the contract's for that environment (the identities that write, `APPLY`, `STATE_WRITE` and `CHANGESET`, must set every such variable). The variable names and the fallback list are the provider's (see "Providers"), and the other cloud's credential variables are on it. Apply children receive none of the dropped variables at all. A token file copied to a second path, or linked to after the check, is not detectable.

| Identity | Engine | Used for |
| --- | --- | --- |
| `DISCOVERY` | both | Terraform: plan, during seal and qualify. CDK: `describe-stacks` of the target stack at seal |
| `STATE` | Terraform | Reading state and its serial, and taking the state lock |
| `STATE_WRITE` | Terraform | `init` and workspace selection (state write and lock) |
| `APPLY` | both | Terraform: the provider writes in `terraform apply`. CDK: `execute-change-set`, the stack polls and `cancel-update-stack` |
| `CHANGESET` | CDK | `create-change-set`, its wait and `describe-change-set` (also at apply, to prove the change set is still the sealed one). It has no way to execute |

## Providers

The requirements on this page hold for any provider; the provider's facts live in one spec per provider, chosen by the contract's `provider` id (`src/apply/provider.ts`; `AZURE` in `src/apply/providers/azure.ts`, `AWS` in `src/apply/providers/aws.ts`). A contract naming a provider with no spec is `CONTRACT_INVALID`. There is no provider flag on any command: `./alz apply` follows the pinned contract. A spec owns:

- the target shape and its validation, and the account identifier a `ResolvedTarget` carries as `account`;
- the identity checks: the variables that would let a child fall back to a CLI, ambient or other-cloud credential, the operator's own credential variables an identity may not equal, and the variables that must name the contract's account;
- the partial backend configuration `init` saves for STATE_WRITE, the check that the backend `init` saved equals the contract's, and the backend settings the apply process fills in (`filledAtApply`);
- optionally, the attributes the project's own backend block may set (`backendBlock`), judged from the project files before `init` reads them, because `init` already sends credentials to whatever the block names (`BACKEND_BLOCK_NOT_IN_CONTRACT`, mapped like every `_NOT_IN_CONTRACT` code). Only AWS defines one; the Azure backend block is not yet judged this way;
- the checks on the provider blocks in `terraform show -json`;
- the account fields and principals that bind qualification evidence to the DEV target.

The generic modules (contract, identities, driver, seal, evidence, the CLI) hold each requirement's one enforcement point and call the spec for the facts. Every apply child's Terraform profile (`TERRAFORM_APPLY_PROFILE`) drops what a spec refuses: `TF_CLI_CONFIG_FILE`, `TF_PLUGIN_CACHE_DIR`, `AZURE_*`, the static AWS credentials (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_PROFILE`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_CONFIG_FILE`), and `AWS_ENDPOINT_URL` (a web identity token goes wherever an endpoint points, and a host allowlist cannot tell an attacker's `*.amazonaws.com` API Gateway or load balancer host from AWS), `AWS_CA_BUNDLE` and `AWS_DEFAULT_REGION`, and sets `AWS_EC2_METADATA_DISABLED=true` so no child can fall back to an instance profile. The other profiles are unchanged.

### Azure (`AZURE`, Terraform with the AzureRM backend)

Target: `tenantId`, `subscriptionId`, `backend` (`<storage-account>/<container>/<key>`), `workspace`; `account` is the subscription id. Variables: `ARM_CLIENT_ID`, `ARM_TENANT_ID`, `ARM_SUBSCRIPTION_ID`, `ARM_USE_OIDC` and `ARM_OIDC_TOKEN_FILE`, for example `ALZ_APPLY_ARM_CLIENT_ID`. The tenant and subscription must be the contract's. Refused as fallbacks: `AZURE_*`, `ARM_USE_*` other than `ARM_USE_OIDC`, `ARM_MSI_*`, `ARM_CLIENT_CERTIFICATE*`. A per-identity `ARM_CLIENT_SECRET` is accepted (it is that identity's own explicit credential), so "OIDC token file only" is the recommended setup and is not enforced for secrets. Qualification attests the client ids, and the same client ids must be used in every environment.

State prerequisites (owner supplies): a storage account and container per environment, with blob versioning and soft delete on, Entra ID authorization for the backend (`use_azuread_auth` or `ARM_STORAGE_USE_AZUREAD`; it is not yet on the runner profile), and role assignments scoped to that container for STATE and STATE_WRITE and to the target subscription for APPLY. Exact roles are the owner's least-privilege decision.

### AWS (`AWS`, Terraform with the S3 backend)

The AWS formats, the S3 backend and aws provider attribute names, and the Terraform features named here are from memory and unverified against AWS or Terraform documentation, which was unreachable when this was written; a comment next to the validators says so. A rule that is wrong refuses a good value and is corrected in a reviewed change. Nothing here has run against a real Terraform or a real AWS account.

- **Target:** `accountId` (12 digits), `region` (like `us-east-1`), `backend` (`<bucket>/<key>`; bucket 3 to 63 characters of lowercase letters, digits, hyphens and dots, starting and ending with a letter or digit), `workspace`. `account` is the account id. The three environments differ pairwise in account and backend.
- **Identities:** four distinct IAM roles assumed through web identity, no static keys. Per identity: `ALZ_<IDENTITY>_AWS_ROLE_ARN` (`arn:aws:iam::<account>:role/<name>`), `ALZ_<IDENTITY>_AWS_WEB_IDENTITY_TOKEN_FILE` and `ALZ_<IDENTITY>_AWS_REGION`. Each role ARN's account id and each region must be the environment's own contract values. Role ARNs are compared case-insensitively, trimmed, and as account plus role name (a role name is unique in its account whatever the ARN's path, so `role/name` and `role/team/name` are one role); token files by path, symlink and inode, like every other principal, and each must be an absolute path (a relative one means the runner's directory to the check and the work directory to the child). Refused on any identity: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_SECURITY_TOKEN`, `AWS_PROFILE`, `AWS_DEFAULT_PROFILE`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_CONFIG_FILE`, `AWS_CONTAINER_*`, `AWS_EC2_METADATA*`, `ARM_*` and `AZURE_*`; and any role ARN or token file equal to the operator's own ambient `AWS_ROLE_ARN` or `AWS_WEB_IDENTITY_TOKEN_FILE`. `AWS_REGION` is checked against the contract wherever it is set and must be set for STATE_WRITE and APPLY. Under an Azure contract `AWS_*` is refused the same way.
- **Backend:** S3 with native locking (`use_lockfile = true`; no DynamoDB table). The partial backend configuration `init` saves for STATE_WRITE holds the contract's `bucket`, `key` and `region`, `use_lockfile = true`, and `assume_role_with_web_identity` with the STATE_WRITE role ARN and token file path (neither is a secret). The project's own `backend "s3"` block may set only `bucket`, `key`, `region` and `use_lockfile`: any other attribute (`endpoints`, `access_key`, `profile`, `assume_role`, `skip_*` and the rest), a `cloud` block, another backend type, or a file that cannot be parsed is refused before `init` runs, at seal and at apply (`BACKEND_BLOCK_NOT_IN_CONTRACT`). What the plan embeds is the seal-time `init`'s `bucket`, `key`, `region` and `use_lockfile`, which must be the contract's (below); the backend credentials stay null, and the apply process fills them from its own environment, which is the APPLY role (`filledAtApply`).
- **Provider blocks:** only `hashicorp/aws` and the providers that reach no cloud (`random`, `null`, `time`, `tls`) may appear in the plan (`PROVIDER_CONFIG_NOT_IN_CONTRACT`). In any `aws` provider block, whether constant or an expression: no `access_key`, `secret_key`, `token`, `profile`, `shared_credentials_files`, `shared_config_files`, `endpoints`, proxy, `custom_ca_bundle`, `ec2_metadata_service_endpoint*`, `insecure` or `skip_*`, and no `web_identity_token` or `web_identity_token_file` in `assume_role*` (`PROVIDER_CONFIG_NOT_IN_CONTRACT`). A constant `allowed_account_ids` must include the contract's account, a constant `forbidden_account_ids` must not, and a constant `role_arn` in `assume_role` or `assume_role_with_web_identity` must be the APPLY identity's own role, and in the contract's account (`PROVIDER_ACCOUNT_NOT_IN_CONTRACT` for another account). Expressions for an account or a role are not checkable from the plan and are not judged. A constant `region` is not judged: a second region is ordinary and the account is what the credentials bound.
- **Qualification:** the evidence binds the DEV `accountId`, `region`, backend and workspace, the attested STATE_WRITE and APPLY role ARNs (trimmed, lowercase), and the terraform binary hash, with the usual 30 day limit. A role ARN names its account, so QA and PROD cannot use DEV's roles: the role binding applies to DEV runs, and each QA and PROD run is bound by its own account check instead.
- **Prerequisites (owner supplies):** per environment, an S3 bucket with versioning on; the lock file is an object next to the state object, so STATE needs read access and permission to create and delete the lock object, STATE_WRITE needs state object write as well, and APPLY needs the provider write permissions in that account. An IAM OIDC identity provider per account and a trust policy per role that lets only that identity's token assume it. Exact policies are the owner's least-privilege decision.

## Engines

The same split holds for the engine. One spec per engine, chosen by the contract's `engine` id (`src/apply/engine-spec.ts`; `TERRAFORM` in `src/apply/engines/terraform.ts`, `CDK` in `src/apply/engines/cdk.ts`), owns what only that engine knows:

- the providers it is valid with (Terraform: either; CDK: AWS only), the identities it needs (Terraform: DISCOVERY, STATE, STATE_WRITE, APPLY; CDK: DISCOVERY, CHANGESET, APPLY) and the two whose principals qualification attests;
- how the sealed artifact is produced from a request (Terraform: init, workspace, `plan -out`, with `show -json` read only for the redacted change list; CDK: a CloudFormation change set that is created and not executed) and how the change list is derived again from the artifact at apply;
- how the exact sealed artifact is prepared and run (Terraform: `apply <planfile>`; CDK: `execute-change-set` for the sealed change set), how the run ends is classified, and what it leaves for a person to recover (Terraform: the first `Error:` match and the state serial, `errored.tfstate` and `crash.log`; CDK: nothing is written, the stack is the record), with the message for each unsuccessful outcome;
- the argument allowlist and the adapters whose digest a qualification record pins, the binary hash qualification evidence binds, and what the CLI tells the person (the project-code warning, the attestation text);
- optionally its own qualification run (CDK: read-only, no change set) and the shape of a target's `backend` and extra fields.

The driver's ordering of gates, the ledger, approvals, promotion, evidence, the kill switch and cleanup stay engine-agnostic and call the spec. A contract naming an engine with no spec, or an engine with a provider it is not valid with, is `CONTRACT_INVALID`, and a manifest that is not the contract engine's project manifest is refused before sealing or applying. `terraform.ts` keeps Terraform's pinned argument lists, digest and outcome classification. The evidence's `authority.mutation` says what the engine did (`TERRAFORM_APPLY_OF_SEALED_PLAN` or `CLOUDFORMATION_EXECUTE_OF_SEALED_CHANGE_SET`). Two field names in the qualification evidence are Terraform-shaped and published, so they keep their names: `terraformSha256` holds the engine binary's hash (the `aws` CLI's for CDK), and `stateWriteClientId` and `applyClientId` hold the two attested principals (CHANGESET's role ARN and APPLY's for CDK).

### CDK (`CDK`, AWS only)

**Every AWS CLI, CloudFormation and CDK fact below is from memory and unverified against AWS documentation, which was unreachable when this was written. No real AWS CLI or CloudFormation has run any of it; the tests use a fake `aws`.** This is the one list of the assumptions; `src/apply/engines/cdk.ts` marks where it relies on one with `UNVERIFIED (n)`. Each is checked against AWS's documentation and a real DEV run before live use. Most fail closed (a refusal or `PARTIAL_REQUIRES_REVIEW`); the ones that may not are named in "Open real-AWS questions".

1. The AWS CLI v2 subcommands and flags the argument lists use: `cloudformation create-change-set` (`--stack-name`, `--change-set-name`, `--change-set-type`, `--template-body file://...`, `--capabilities`), `wait change-set-create-complete`, `describe-change-set`, `get-template` (`--change-set-name`, `--template-stage Original`), `execute-change-set`, `describe-stacks`, `describe-stack-events`, `cancel-update-stack`, `--region`, `--output json`, `--no-cli-pager`, and `aws --version` printing `aws-cli/<x.y.z> ...`.
2. That the CLI reads `AWS_ROLE_ARN` with `AWS_WEB_IDENTITY_TOKEN_FILE` for its credentials (as the Terraform AWS provider is assumed to), that it honors `--region` for the STS call, and that the apply profile's `AWS_EC2_METADATA_DISABLED` switches the instance metadata fallback off.
3. The JSON they print (a change set that holds a `NextToken` after the CLI's own pagination is `CHANGE_SET_TRUNCATED`; one with no changes is `NO_CHANGES_TO_APPLY`): `Id` and `StackId` from create; `ChangeSetId`, `StackId`, `StackName`, `Status`, `ExecutionStatus`, `Capabilities`, `Parameters[]` and `Changes[].ResourceChange` with `Action` (`Add`, `Modify`, `Remove`, `Import`, `Dynamic`), `LogicalResourceId`, `ResourceType` and `Replacement` (`True`, `False`, `Conditional`) from describe-change-set; `TemplateBody` from get-template (an object for a JSON template, or a string); `Stacks[].StackId`, `StackStatus`, `EnableTerminationProtection`, `CreationTime`, `LastUpdatedTime`, `RoleARN`, `NotificationARNs` and `RollbackConfiguration`; `StackEvents[].ResourceType` and `Timestamp`; and the template keys `Transform`, `Fn::Transform` and `Fn::ImportValue`.
4. The statuses. For a stack: those named in the code (in progress, updatable, rolled back, failed), that a stack not found is told apart by "does not exist" in the error text, that a `CREATE` change set leaves the stack in `REVIEW_IN_PROGRESS` (and a second seal for it is again `CREATE`), and that creating a change set does not change the stack's status, last change time, role, topics or rollback setting. For a change set: executable when `Status` is `CREATE_COMPLETE` and `ExecutionStatus` is `AVAILABLE` (the brief named this `EXECUTE_AVAILABLE`; no such value is assumed); `EXECUTE_COMPLETE` after a completed execution; still `AVAILABLE` after an execute that CloudFormation refused; and `OBSOLETE` or `UNAVAILABLE` when the stack changed after it was made. The last is an extra only: the apply compares the stack's state itself (below).
4a. That a change set with nothing to change, and one that could not be built, both end `Status: FAILED` with a `StatusReason`, which `wait change-set-create-complete` reports as a non-zero exit. The engine reads the reason once: "didn't contain changes" (or "No updates are to be performed") is `NO_CHANGES_TO_APPLY`, any other `FAILED` is `CHANGE_SET_CREATION_FAILED`, and neither creates anything to execute. The failed change set is left for a person to clear (the pilot has no delete). AWS's documentation says a change set does not guarantee a successful deployment, which is why the apply judges the outcome from the stack and the change set after the execute, not from the change set alone.
5. That `cancel-update-stack` is valid only while the stack is `UPDATE_IN_PROGRESS`, that CloudFormation then rolls back, and that a create cannot be canceled.
6. That `CreateChangeSet` cannot turn termination protection on, so a person enables it after the first create, and the next update is refused until they do.
7. The 51,200 byte limit on an inline template body, and the cloud assembly layout read from `manifest.json`: artifact types `aws:cloudformation:stack`, `cdk:asset-manifest`, `cdk:tree` and `cdk:feature-flag-report`; a stack's `properties.templateFile`, `stackName`, `terminationProtection` and `environment` (`aws://<account>/<region>`, `unknown-account` and `unknown-region` for an environment-agnostic stack); an asset manifest's `files[].source.path` and `dockerImages`; and that a stack without assets lists only its own template as a file asset (the default synthesizer's), which is sent inline instead.

**Input.** A pre-synthesized cloud assembly directory (`cdk.out`), captured and hashed exactly like a project snapshot (`captureProjectFiles`, the sealed manifest with `engine: "CDK"` and no lock file, `createImmutableSnapshot`, and a work copy checked against the manifest after every process). Synthesis is a separate dev-mode step on the build machine (the CDK toolchain is Node based). The pilot never runs `cdk synth`, the CDK CLI, `npm`, `npx` or any app code: it reads the assembly's files and calls only the `aws` CLI with the argument lists in `src/apply/engines/cdk.ts`. `engineVersion` in the manifest and in `resolved` is the `aws` CLI's version, checked with `aws --version`. The request and manifest are the same files as for Terraform.

**What is refused (fail closed, with a code).** More or fewer than one stack (`ASSEMBLY_STACK_COUNT`); a dependency of the stack on anything but the asset manifest, tree or feature-flag report, which is a cross-stack dependency (`ASSEMBLY_DEPENDENCY`); an artifact of any other kind, such as a nested assembly (`ASSEMBLY_ARTIFACT_UNSUPPORTED`); a `manifest.json` or asset manifest that is not readable JSON of the expected shape (`ASSEMBLY_UNREADABLE`); a stack environment that is not `aws://<account or unknown-account>/<region or unknown-region>` (`ASSEMBLY_ENV_INVALID`); a file or docker asset other than the stack's own template (`ASSEMBLY_NEEDS_ASSETS`: the pilot publishes nothing, it has no S3 or ECR step and no publishing role); a template that is missing or not JSON (`TEMPLATE_UNREADABLE`), over the inline limit (`TEMPLATE_TOO_LARGE`), or that repeats a key in any object (`TEMPLATE_DUPLICATE_KEY`: the last one wins here and CloudFormation parses the text itself); a `Transform` or `Fn::Transform`, which expands the template where no hash sees it (`ASSEMBLY_TRANSFORM`); a `Custom::*`, `AWS::CloudFormation::CustomResource` or `AWS::CloudFormation::Macro` resource, which runs code in the account (`ASSEMBLY_CUSTOM_RESOURCE`); a nested stack resource (`ASSEMBLY_NESTED_STACK`); an `Fn::ImportValue` (`ASSEMBLY_CROSS_STACK_IMPORT`); a stack name that is not the target's `backend` (`STACK_NOT_IN_CONTRACT`); an assembly synthesized for another account or region than the target (`ASSEMBLY_ENV_NOT_IN_CONTRACT`; an environment-agnostic assembly is what promotes, since a release identity is the same only if the files are); a stack whose assembly does not declare termination protection, or whose live stack has it off when it is updated (`TERMINATION_PROTECTION_OFF`, the pilot's policy, because it never deletes a stack and the protection stops anyone else doing it by accident); a live stack not in a stable state (`STACK_STATE_UNSUITABLE`); and an AWS CLI whose version output cannot be read (`VERSION_UNREADABLE`) or is not the manifest's (`ENGINE_VERSION_MISMATCH`). Parameter values cannot be supplied: the change set uses the template's defaults. Output cut off at the runner's limit (`OUTPUT_TRUNCATED`), a change set document that cannot be read (`CHANGE_SET_UNREADABLE`, `CHANGE_UNREADABLE`, `CHANGE_ACTION_UNKNOWN`) and a change set that is not the one just created (`CHANGE_SET_MISMATCH`) also stop the seal.

**Capabilities.** Each target in the contract has `capabilities`, a list of `CAPABILITY_IAM` and `CAPABILITY_NAMED_IAM` (empty in the example; `CAPABILITY_AUTO_EXPAND` is not accepted, because it is for the macros and transforms the engine refuses). Sealing passes that list to `create-change-set` only when the template has an `AWS::IAM::*` resource, and passes none otherwise, so a capability granted once for a release that needed a role is not carried into a later release that does not. A stack that needs IAM resources fails to create a change set until the owner puts the capability in the pinned contract for that environment; one environment's decision is not another's. A capability is a standing grant for the stack, so list only what it needs. The change set's own capabilities must be among those passed, and are sealed. Approvers see an IAM resource as a line of the change list (its type and action), not its policy statements; that limit is inherent (see "Open real-AWS questions").

**Seal (as DISCOVERY and CHANGESET; APPLY is not in the runner's environment).** Version check; the assembly checks above; `describe-stacks` (DISCOVERY) decides `CREATE` (no stack, or one still in `REVIEW_IN_PROGRESS`) or `UPDATE`; `create-change-set` (CHANGESET); `wait change-set-create-complete`; `describe-change-set`; `get-template` for the change set (CHANGESET), whose template must equal the assembly's (`CHANGE_SET_TEMPLATE_MISMATCH`; the local file's hash alone says nothing about what CloudFormation holds); and `describe-stacks` again (DISCOVERY) for the state of the stack the change set was made against. The change set's id and stack id must name the contract's account and region (`CHANGESET_NOT_IN_CONTRACT`), and it must be `CREATE_COMPLETE` and `AVAILABLE`. Nothing is executed and nothing is deleted: a change set that is not applied stays in CloudFormation, for a person to clear. The sealed record (the artifact bytes, encrypted in the vault) holds the account, region, stack name and id, change set id and name, `CREATE` or `UPDATE`, the template file and its sha256, the parameters hash, the capabilities, the change list hash and a hash of the stack's state (id, status, last change time, service role, notification topics and rollback configuration). The artifact hash approvers sign binds that record and the contract's hash, environment, target and release identity, so the change set, the template, the capabilities, the change list and the stack state it was made against cannot change after approval. The redacted change list is one line per resource: logical id, resource type, and action (`CREATE`, `UPDATE`, `DELETE`, `REPLACE`, `REPLACE_CONDITIONAL`, `IMPORT`, `DYNAMIC`); never a property, a parameter value or an output.

**Apply.** After the gates and before any approval is consumed: the work copy equals the manifest; `describe-stacks` (APPLY) records the stack's state; the sealed change set is described again (CHANGESET) and its id, stack id, stack name, capabilities, parameters hash and change list hash must equal the sealed values (`ARTIFACT_TAMPERED`), and it must still be executable (`PLAN_STALE`: the change set was used or expired, or CloudFormation marked it obsolete); the assembly's template must still hash to the sealed value, and the change set's own template (`get-template`) must equal it (`ARTIFACT_TAMPERED`); the stack's id must be the sealed one (`ARTIFACT_TAMPERED`) and its state hash the sealed one (`PLAN_STALE`: the stack changed after sealing, or was given another role, topic or rollback setting, whatever CloudFormation says about the change set). Then the usual approvals and kill switch checks. Immediately before `execute-change-set` the stack is read once more and must still have the sealed state (a stack that moved in between is `APPROVALS_SPENT`, exit 3: nothing executed, the approvals gone, the sealed plan available again), the APPLY and CHANGESET variables are checked once more for any the runner would drop, and the artifact the engine is given must equal the record it rederived. Then `execute-change-set` for exactly that change set's ARN, then `describe-stacks` every poll (2 seconds by default) until the stack settles, with the kill switch read each poll, then `describe-change-set` once more. Never `delete-stack`, never `delete-change-set`, never a retry, never a second execute. From the `execute-change-set` call on, the engine throws nothing: CloudFormation may have accepted the execution, so any later failure is an outcome, never "nothing was applied".

The outcome is judged from the execute call, the stack and the sealed change set together, never from the stack alone, because a stack can move for reasons that are not this execution:

| Outcome | When |
| --- | --- |
| `SUCCEEDED` | All of: `execute-change-set` exited 0; the stack moved to `CREATE_COMPLETE` (create) or `UPDATE_COMPLETE` (update); and the sealed change set reports `EXECUTE_COMPLETE`. Only this promotes the release |
| `FAILED_NO_CHANGE` | `execute-change-set` did not exit 0, the stack did not move, and the sealed change set is still reported unexecuted (`AVAILABLE`); or the stack rolled back (`ROLLBACK_COMPLETE`, `UPDATE_ROLLBACK_COMPLETE`) after an execute that exited 0 and `describe-stack-events` shows no event for a resource after the execution began |
| `PARTIAL_REQUIRES_REVIEW` | Anything else that is not a stop: an execute that did not exit 0 when the change set cannot be shown unexecuted (a lost response or a timeout, which CloudFormation may have accepted) or when the stack moved anyway (someone else's update); an execute that exited 0 but never showed; `UPDATE_ROLLBACK_FAILED`, `ROLLBACK_FAILED`, `UPDATE_FAILED`, a rollback after resources were touched, a status this does not know, or a stack that could not be read |
| `KILLED` | A stop was requested (kill switch, the 60 minute limit, SIGINT, SIGTERM, SIGHUP or SIGQUIT) and the run had not succeeded first |

**Kill switch semantics.** The switch is read before `execute-change-set` runs (then nothing ran: `KILL_SWITCH_AFTER_APPROVALS`) and every poll after it. When it appears, an update in progress gets one `cancel-update-stack`, only while the last status read was `UPDATE_IN_PROGRESS` and only if this command's `execute-change-set` exited 0 (a stack moving under someone else's update, or an execute whose acceptance is unknown, is never canceled by this command); CloudFormation then rolls the update back, and the engine waits (the driver's grace period, ten minutes by default) for the stack to settle before it classifies, always `KILLED` unless the stack had already succeeded. A create cannot be canceled: nothing is sent, the create runs on, and `KILLED` records that the engine stopped watching. Either way the stack may be partly changed or still changing, and a person reviews it before anything else. CloudFormation, not this command, decides what a rollback restores. **The 60 minute time limit is the same stop: it cancels, and so rolls back, an update that is still running however healthy it is.** An update that can take longer than an hour does not belong in the pilot. SIGINT and SIGTERM do the same, and neither is the kill switch.

**Stack lifecycle limits (inherent to CloudFormation).** `CreateChangeSet` cannot turn termination protection on, so the first `CREATE` leaves the stack unprotected until a person enables it, and the engine does not check it again at apply (the next seal for an update refuses an unprotected stack). A failed `CREATE` ends in `ROLLBACK_COMPLETE`, which deletes the stack's resources; a stack in that state cannot be updated and needs a person (`STACK_STATE_UNSUITABLE` at the next seal).

**Evidence and messages.** Counts, hashes, statuses and codes only. The template body, parameter values, outputs, resource attributes, stack event text and AWS CLI error text are never carried, because stack events and errors can quote them; the profile also keeps output excerpts out of diagnostics. `test/apply-cdk.test.ts` plants a value in each and pins that none reaches evidence, the review bundle, a result or the vault records.

**Qualification.** `./alz apply qualify` (DEV only) runs the version check, reads the assembly, and runs `describe-stacks` as DISCOVERY, CHANGESET and APPLY, and nothing else: no change set, no `sts get-caller-identity`, no argument list beyond the pinned ones. A role that cannot describe the stack fails it, so CHANGESET and APPLY need `cloudformation:DescribeStacks` for this. **It exercises no create, execute, get-template or cancel call.** The adapter descriptors it records carry the digests of all the argument lists, but only `--version` and `describe-stacks` ran against the real CLI. That CHANGESET cannot execute and APPLY cannot create a change set is shown by the roles' IAM policies and the cloud's logs, never by this run (a negative probe would need an execute argument list for CHANGESET, which the allowlist deliberately does not have). The person checks CloudTrail and types `SEPARATED <CHANGESET role ARN> <APPLY role ARN>` only if the logs show the stack read and, in later runs, change set creation only by CHANGESET and execution only by APPLY. The evidence binds the DEV account, region, stack name (the `backend`) and workspace, the `aws` binary's sha256, the CLI version, the attested role ARNs (DEV runs only, as for Terraform on AWS), the two adapters' argument digests, and the usual 30 day limit. **Like the Terraform qualification, it does not exercise the step that changes infrastructure, so the first supervised DEV apply is the qualifying apply.** The binary hash covers the file the runner resolves for `aws` (for AWS CLI v2, its launcher or main executable), not the rest of the install directory (its libraries and service models). It refuses an honest upgrade; a change inside the install by the same-user operator is inside the trust boundary, as for Terraform, but this pin is narrower than Terraform's single binary.

**Recommended minimum IAM actions (unverified; the owner decides least privilege).** Per environment's account, one role per identity, assumable only by that identity's web identity token:

| Identity | Actions |
| --- | --- |
| `DISCOVERY` | `cloudformation:DescribeStacks` on the stack |
| `CHANGESET` | `cloudformation:CreateChangeSet`, `DescribeChangeSet`, `GetTemplate`, `DeleteChangeSet` (for a person's manual clean-up; the pilot never calls it) and `DescribeStacks` (qualification) on the stack, and no `ExecuteChangeSet`. `CreateChangeSet` on a new stack may also need the permissions of the resources it validates, and a template that needs `iam:PassRole` does not belong in the pilot without an owner decision |
| `APPLY` | `cloudformation:ExecuteChangeSet`, `DescribeStacks`, `DescribeStackEvents` and `CancelUpdateStack` on the stack, and the permissions CloudFormation uses to create, update and delete the stack's resources (through the role or the caller's own, as the owner configures it). No `DeleteStack`, and no `CreateChangeSet` |

**Open real-AWS questions.** (1) Whether the stack state hash catches every out-of-band change that matters. The apply compares the stack's id, status, last change time, service role, notification topics and rollback configuration with the sealed values; a change that alters none of them, if one exists, is caught only by CloudFormation marking the change set `OBSOLETE` or `UNAVAILABLE`, which is itself unverified (assumption 4). If neither holds, the apply would execute against a stack that differs from the one approvers saw, and nothing here would catch it. (2) The retention of un-executed change sets, which this never deletes, and whether a long gap between seal and apply (the approval lifetime is up to a day) leaves one executable. (3) Per-environment role attestation: the cloud-log check is a person's, and QA and PROD roles are bound only by their account, not by an attested record. (4) Whether `wait change-set-create-complete` and the 15 minute process limit suit a large change set. (5) Which of the roles CloudFormation actually uses when `execute-change-set` runs (the caller's, or the stack's service role, which the stack state hash keeps unchanged but does not judge), and so what APPLY must be allowed. (6) What `REVIEW_IN_PROGRESS` leftovers from sealed-but-never-applied creates do to a later seal. **Inherent limits no code here removes:** approvers see a logical id, a resource type and an action, not properties, IAM statements or capabilities, so a modified role policy looks like any other modification; `{{resolve:ssm}}` and `{{resolve:secretsmanager}}` dynamic references resolve at execution, outside every hash; and the separation of the CHANGESET and APPLY roles is enforced only by the cloud-side configuration and a person's attestation.

## Open item that blocks live apply (G2)

This item and its subsections are Terraform's (state backend, `init`, `terraform apply`). The CDK engine has no state backend; its CHANGESET and APPLY principals are attested the same way, and what its qualification does and does not show is in "CDK" (Qualification).

For `terraform apply <planfile>`, Terraform configures the backend from the plan, and backend attributes the plan leaves unset fall back to the apply process's own provider variables (`ARM_*` for Azure, `AWS_ROLE_ARN` and `AWS_WEB_IDENTITY_TOKEN_FILE` for AWS), which are APPLY's. If so, the state write would authenticate as APPLY, collapsing the two identities. A fake engine cannot detect this and it is **not asserted anywhere in the code**. This is an open real-cloud question for each provider.

What the code does to give separation a chance: `init` runs as STATE_WRITE with a partial backend configuration (`-backend-config=../alz-backend.tfbackend`: the provider spec's STATE_WRITE settings, from the contract and the `ALZ_STATE_WRITE_*` variables, never a secret value, strict patterns before anything is written, mode 0600, deleted as soon as `init` ends), so the backend settings Terraform saves name STATE_WRITE; `terraform apply` then runs with the APPLY identity only. `state pull` runs as STATE, but if Terraform prefers the saved backend settings it authenticates as STATE_WRITE; that is also unproven. The apply adapter's argument lists, and so its argument digest, include that `init`. Every step (including sealing and the qualification plan) uses the apply Terraform profile (see "Providers"): a variable it drops that would redirect where providers are installed from is refused (`ENVIRONMENT_REFUSED`), and the step does not run. The `Saved plan is stale` text match is likewise unverified.

The only gate is attested qualification evidence: `verifyApplyQualification` requires an encrypted vault file, named by the record's hash, for exactly this adapter version, argument digest and engine version, whose account fields equal the contract's DEV target, dated in the past and at most 30 days old. Until it exists, `ENGINE_NOT_QUALIFIED` blocks every apply. Evidence written without the provider's account fields is rejected; run `./alz apply qualify` again.

What the fields are: `realEngine` and `backendIdentitySeparated` are **human attestations**, not machine proof. The code checks neither; nothing stops an operator with the evidence key from writing them without a run. The only machine-checked prerequisite is that `qualify` refuses to reach the attestation prompt unless the pinned steps (version, init, workspace, throwaway plan, state read) succeeded behind the usual gates; it cannot tell a real Terraform from an executable of that name on the tool path, so the real engine is the person's responsibility. **The qualification does not exercise `terraform apply`, so the first supervised DEV apply is the qualifying apply**: it is the first time the separation is observable for the write, and the owner should watch the cloud logs during it.

### Qualifying against a real engine

`./alz apply qualify` is how that evidence is produced. **For Terraform it must be run by a person against the real engine, on a DEV target the owner supplied. It has not been run: this work tested it with the fake engine only.** It applies nothing and stores no plan. It runs the pilot's own steps in order: `terraform version`, `init` and workspace selection with the STATE_WRITE backend configuration, a throwaway plan of the pinned project as DISCOVERY (never stored, so it cannot be approved or applied), and the state serial read as STATE. It refuses outside DEV and with any of the usual gates unmet (contract, pin, kill switch, identities).

The code cannot see which principal the cloud authenticated for state and which for resources. So after the run the command asks the person to check the provider's logs for it (Azure sign-in and storage logs; AWS CloudTrail STS and S3 data events), and to type `SEPARATED <STATE_WRITE client id or role ARN> <APPLY client id or role ARN>` only if the logs show state access by STATE_WRITE, provider access by APPLY, and no state access by APPLY. Anything else writes nothing. That attestation is an operator control, not machine proof. It then writes encrypted evidence for the apply adapter and for the preview adapter, and prints each adapter version, argument digest, engine version and evidence hash. `seal` and `apply` read those records from the vault.

The evidence also records the Terraform binary's sha256, the attested STATE_WRITE and APPLY principals (client ids, or role ARNs for AWS), and the DEV backend and workspace; `apply` refuses with `ENGINE_NOT_QUALIFIED` if any differ, so a changed binary or different principals need a new qualification. For AWS the principal binding applies to DEV runs only, because each environment's roles live in its own account. The binary hash is read once at apply time; a same-user operator who swaps the binary after that read is inside the trust boundary.

Rerun it when the engine version or either adapter's argument list changes (the digest changes with it). The `terraform apply` step itself is not exercised by qualification, since that would change infrastructure; its behavior is covered only by the first supervised DEV apply, which the owner should watch.

### Backend and identity ordering at apply (G2): partly answered by the simulation

The real Terraform 1.16.4 against the Azurite emulator (`docs/act-pilot-simulation.md`, DEV MODE ONLY) showed: `terraform apply <planfile>` uses the backend settings **embedded in the plan**, not the settings that `init` saved in the apply directory. Attributes embedded as null are filled from the apply process's own `ARM_*` variables, and an environment variable with the same name does not override an embedded value. The plan file also embeds a `-backend-config` `sas_token` in plaintext, so a sealed plan is secret-bearing (it is encrypted at rest). Tested with SAS and access-key auth only; Entra and OIDC are inferred, not run. The S3 backend was not simulated: the same behavior is assumed for it, and the AWS spec is written on that assumption (`filledAtApply`).

Consequences for this design, still to be settled with a real run:

- The STATE_WRITE partial backend configuration passed to `init` at apply time is probably not what authenticates the state write. Which principal writes state follows from the seal-time settings plus the apply process's own provider variables (APPLY's).
- Keeping STATE_WRITE and APPLY distinct for the state write would therefore need the seal-time `init` to embed STATE_WRITE's non-secret settings (Azure: client id, tenant, token file path; AWS: `assume_role_with_web_identity`), which makes the seal-time state access write-capable. Sealing runs with DISCOVERY and STATE only, so the project's backend block would have to carry them. That is a trade-off for the owner, not something the code decides.
- Until a real run shows which principal wrote state, `qualify` records an attestation and not proof, and the first supervised DEV apply is where it becomes observable. Do not rely on the separation before then.

Known, not changed: Terraform contacts the HashiCorp checkpoint service on every run (the runner profile does not set `CHECKPOINT_DISABLE`; production network policy should block it), and a failed state save writes `errored.tfstate` with mode 0644 and quotes the full backend URL in its error text, which is why engine output is withheld from messages.

### The backend and provider binding

The contract's `backend` and account fields are checked against what the project itself configures, because a project can name any backend or provider:

- **Backend.** After `init`, for both providers, the driver reads `.terraform/terraform.tfstate` in the work directory and applies the spec's saved-backend check (Azure: `azurerm` with `storage_account_name`, `container_name` and `key`; AWS: `s3` with `bucket`, `key`, `region` and `use_lockfile` true) against the contract's DEV, QA or PROD target. It runs after the seal-time `init`, whose settings the plan embeds (a mismatch is `ARTIFACT_INVALID` with `BACKEND_NOT_IN_CONTRACT`, and nothing is sealed), and after the STATE_WRITE `init` at `apply` and `qualify`. At apply anything else, including a value that is not a string, is `TARGET_NOT_IN_CONTRACT` before the approvals are consumed. A file that cannot be read is `APPLY_FAILED` ("no approval was consumed"), not a pass.
- **Provider.** From the plan's `terraform show -json` `configuration` (at `seal`, and again at `apply` when the list is re-derived), the spec judges the constants in its provider blocks, in any module or alias: Azure `subscription_id` and `tenant_id` must equal the contract's (`PROVIDER_SUBSCRIPTION_NOT_IN_CONTRACT`, `PROVIDER_TENANT_NOT_IN_CONTRACT`); AWS as described in its section (`PROVIDER_ACCOUNT_NOT_IN_CONTRACT`, `PROVIDER_CONFIG_NOT_IN_CONTRACT`). **Limit:** a value that is an expression (a variable, including one fed by an injected `TF_VAR_*`, a data source, a local) is *not checkable* from the plan and is not judged, not silently accepted as safe. For those, the only controls are the identity checks (each credential must name the contract's account, and the provider runs as APPLY only) and the cloud-side role assignments. Owners should keep the provider's account out of expressions in the pilot project.

## Kill switch

Create the file named by `killSwitchPath` (example: `.runs/apply/KILL`). A switch that cannot be read counts as on. It is read at exactly these points:

1. At the start of `seal`, `qualify` and `apply` (the shared admission step, before any file or engine).
2. In `apply`, again after the engine is prepared and the change list re-derived, together with the contract, pin, target and approval re-checks, and before the approvals are consumed. A switch seen here is `KILL_SWITCH_ACTIVE`: nothing is consumed (exit 2).
3. Immediately before the `terraform apply` process (or, for CDK, `execute-change-set`) is spawned. A switch seen here, after the approvals were consumed, is `KILL_SWITCH_AFTER_APPROVALS` (exit 3, nothing ran, the artifact is given back).
4. Every second while `terraform apply` runs. Terraform is sent SIGINT (its graceful stop), then SIGKILL to its process group after a grace period (60 seconds). For CDK, at every poll of the stack (2 seconds by default); see "CDK" for what a stop does there.
5. `status` reports it; it enforces nothing.

It is not read between `init`, `workspace` and the state reads (for CDK, between the steps before the execute). The same stop (SIGINT, then SIGKILL) happens at the 30 minute limit (for CDK, a stop at the 60 minute limit) and when this command receives SIGINT, SIGTERM, SIGHUP or SIGQUIT while the apply is held: the signal is intercepted, the engine is stopped gracefully and the evidence is written, so the CLI does not exit mid-run. A stopped apply ends as `KILLED` whatever exit code Terraform reports. A signal before the engine starts ends the run as `APPLY_FAILED` ("interrupted", exit 1) without consuming approvals; after they are consumed, any failure before the engine starts is `APPROVALS_SPENT` (exit 3). The owner removes the file; the code never does.

## When an apply fails

Engine output is withheld everywhere because it can hold secrets. Every outcome closes the artifact: a retry needs a new preview and new approvals. These end with exit code 3. (`APPROVALS_SPENT` and `KILL_SWITCH_AFTER_APPROVALS` are not outcomes: nothing ran, the artifact is given back, the approvals are spent.)

| Outcome | Meaning | Action |
| --- | --- | --- |
| `FAILED_NO_CHANGE` | Only for a state-lock refusal (`Error acquiring the state lock`) with the state serial unmoved | Fix the cause, seal a new preview, get new approvals. |
| `PLAN_STALE` | `Saved plan is stale`, with the serial unmoved; nothing applied | Seal a new preview. |
| `PARTIAL_REQUIRES_REVIEW` | Any other non-zero exit once the apply began, or a moved serial. Terraform exits 1 for every apply error, so the exit code cannot tell a refusal from a failure halfway through | **Do not retry.** A person reviews state and resources by hand first. |
| `KILLED` | Stopped mid-apply; the state lease may still be held | **Do not retry.** Review state, the lease and resources by hand. |

The artifact is reserved in the ledger (an exclusive-create entry in state `RESERVED`) after the gates pass and before any engine step, and the evidence replaces the reservation when the run ends, so two runs holding different approval sets cannot both proceed. A reservation is given back only if the engine never started. If the process dies after the engine started (SIGKILL, power loss, an evidence write that fails), the entry stays `RESERVED`: `status` and every later apply report the artifact as already applied, and an owner reviews the state, the lease and the resources by hand, then seals a new preview. Nothing ever makes a reserved artifact applicable again.

The table is Terraform's. For CDK the outcomes and their meaning are in "CDK" (`FAILED_NO_CHANGE`, `PARTIAL_REQUIRES_REVIEW` and `KILLED` close the artifact the same way; a change set that is no longer the sealed one is refused as `PLAN_STALE` or `ARTIFACT_TAMPERED` before any approval is consumed, which is exit 2, nothing spent), and there is no recovery file: the stack and its events in CloudFormation are the record, and a person reads them there.

The two text matches above (`Saved plan is stale`, `Error acquiring the state lock`) are read only from the **first** `Error:` diagnostic in Terraform's output, never from a later line, because a provider error body can quote either phrase; a run whose first error is anything else, however it ends, is `PARTIAL_REQUIRES_REVIEW`. They come from documented Terraform output and the fake engine; they are not verified against a real engine, and anything else fails safe to `PARTIAL_REQUIRES_REVIEW`.

**Recovery attachment.** After any non-success outcome the driver looks for `errored.tfstate` and `crash.log` in the engine's work directory, before the scratch directory is deleted. Found files go into the encrypted evidence vault under purpose `apply-recovery`, and the apply evidence carries `recovery: { files, sha256 }` (a count and a hash only, never contents). If the vault write fails, the result message says the files were lost with the scratch directory. That location is Terraform's documented behavior and is not verified against a real engine. The files are encrypted at rest under the same evidence key the operator holds, so this protects them from other accounts and backups, not from the operator.

## Plaintext on disk

The decrypted plan and the backend configuration exist only in a private scratch directory, are removed by their own cleanup on every normal exit and on SIGINT, SIGTERM, SIGHUP and SIGQUIT (and the plan the moment a stop is requested), and are deleted as soon as they have been used. A SIGKILL or a crash cannot run a handler. `qualify`, `seal` and `apply` therefore start with the same stale-directory sweep as the teardown CLI (`status` and `approve` never sweep, and make no scratch): directories of the running account in the system temporary directory named `alz-preview-*`, `alz-snapshot-*` or `alz-child-*` and older than one hour are removed. Younger directories (a run in another terminal) and other accounts' directories are left alone. **The sweep is skipped, with a printed notice and nothing removed, whenever the apply ledger holds a `RESERVED` entry (or an entry that cannot be read), or any `alz-preview-*` directory holds `errored.tfstate` or `crash.log`:** those may be the only record of what an apply did, and an owner reviews them by hand first. Remove the cause (finish the review, then seal a new preview, and clear the directory) and the sweep resumes. The change list approvers read is bound into the artifact hash; `runApply` re-verifies a sealed plan it is handed rather than trusting the caller's earlier check, and after `init` it re-derives the change list from the decrypted plan bytes with the pinned `terraform show -json` (no identity in the environment). A difference from the sealed list is `ARTIFACT_TAMPERED` and nothing is consumed.

## What the tests control, and what they do not

The driver trusts what the CLI hands it only as far as it re-verifies it, but the process boundary is not a security boundary: **in-process callers can forge a terminal.** Any code that runs in the same process can build a `HumanInvocation`, an `ApplyRequest` or a terminal object that says it is interactive. `checkHumanInvocation` catches mistakes and an agent that does not know the contract, not a caller that does. The control is that nothing an agent can reach imports the apply path; `test/apply-boundary.test.ts` pins that, and it is the control, so a change that weakens it is a change to the authority and needs the owner.

## Cleanup

Actual destroy is out of scope. The named cleanup owner removes pilot resources by an approved manual procedure and records it; nothing in this path automates it. The pilot change is the one the owner scopes; for Azure it is a tagged resource group plus a Log Analytics workspace.

## What the owner supplies

For either provider: the DEV, QA and PROD accounts, the region, tags, retention, budget and least-privilege scope, the provisioned state backend (one per environment) and the federated identities, the approver public keys (and the second production approver), the execution host, the pilot scope, the cleanup owner, and a person to run `./alz apply qualify` and attest from the cloud logs. For Azure also the tenant ID and the subscription IDs. For AWS also the 12 digit account IDs, and for the CDK engine instead of the state buckets and state roles the stack name, the three web-identity roles per account (DISCOVERY, CHANGESET, APPLY), the capabilities each environment may use, a synthesized environment-agnostic `cdk.out` that publishes no asset, and a person to enable termination protection after the first create. For Terraform on AWS also one S3 bucket per environment with versioning on, one IAM OIDC identity provider and the four web-identity roles per account, and the token files for them on the execution host. Their absence blocks live apply only; tests use explicit fixtures.
